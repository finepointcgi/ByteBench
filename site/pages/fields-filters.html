Fields, filters and search

Model your own data with custom fields, components and versions, then find it again with saved filters, quick filters and GQL, GitBench's JQL-style query language.

Where to configure fields

Maintainers and Owners open /p/{KEY}/settings/fields (project Settings, then fields). It has tabs for custom fields, components, issue templates and estimates (hours per day). All definitions are audited as custom_field.*, component.* and version.* events.

Custom fields

Custom fields add your own data to issues, per project.

PropertyMeaning
TypeText, long text, number, date, single select, multi select, user, checkbox or URL. A field's type cannot change once issues have values.
KeyA short identifier such as severity. Used by the API, webhooks, GQL (cf[severity]) and the issue list's cf= filter.
RequiredRequired fields must have a value on the issue types they apply to; new issues get the default.
DefaultApplied to new issues.
Applies toOptional list of issue types (for example only Bug).
OrderDisplay order in the sidebar and form.

Values are validated: select options must exist, numbers must parse, dates are yyyy-MM-dd, URLs must be http(s), and user fields only accept people who can see the project. Fields appear in the issue sidebar (saved on change and logged: "changed Severity to Critical"), on the new-issue form and as optional columns in the issue list.

# Set custom fields through the API (PATCH changes only the keys you send; null clears)
curl -X PATCH -H "Authorization: Bearer $GITBENCH_TOKEN" -H "Content-Type: application/json" \
  -d '{"customFields":{"severity":"Critical","regression":true}}' \
  https://gitbench.example.com/api/v1/projects/WEB/issues/12

Components and versions

  • Components (name, description, lead, default assignee): parts of your product. An issue can have several. A new issue with no assignee gets its first component's default assignee.
  • Versions (name, description, start and release dates, released flag): used as fix versions and affects versions, both multi-valued. Manage them on the Versions page (/p/{KEY}/versions, Maintainer): unreleased first, with progress per version. A version named like a published release tag (1.0 or v1.0) links to that release. See Boards and sprints.

The issue list can filter by component, fix version and affects version (each also "none"), one custom field (cf=key:value; key: means no value), and choose columns from a columns menu. These are query-string properties, so saved filters and URLs keep them.

Saved filters and quick filters

The issue list keeps its whole filter in the URL (/p/WEB/issues?type=Bug&assigneeId=3&sort=priority), so every filtered view is a link. The status menu lists workflow statuses grouped by category, plus entries like "Any Done status".

  • Saved filter: a name plus that query string (or a GQL query, stored as gql=<query>). Filters on the issue list applies, stars and saves them and offers to update the last-applied one. Manage filters (/p/{KEY}/filters) renames, deletes, shares and unshares.
  • Sharing: filters are private to their owner. Sharing with the project needs Developer; Maintainers can also unshare or delete shared filters. Anyone who can see a filter can star it, and starred filters appear in the sidebar.
  • Quick filters belong to boards: named toggle chips above the board, each a query. Saved filters also feed dashboard gadgets (see Dashboards).

GQL, the advanced search language

Click Advanced on a project's issue list to switch to the GQL editor (the basic filter is converted to the equivalent query; Switch to basic goes back). /issues/search searches every project you can view. Example:

project = WEB AND status in ("In Progress", Blocked) AND assignee = currentUser()
  AND labels = bug AND created >= -14d ORDER BY priority DESC, updated DESC

The editor autocompletes fields, operators valid for the field, and values (statuses, users, labels, milestones, sprints, projects, epics, date shortcuts). Up/Down/Enter/Tab pick, Esc closes, Ctrl+Space asks for suggestions, Enter runs. Errors are shown with the offending text underlined.

Grammar

Keywords are case-insensitive.

query   := [or] [ORDER BY sort ("," sort)*]
or      := and (OR and)*
and     := not (AND not)*
not     := NOT not | "(" or ")" | clause
clause  := field ( ("=" | "!=" | "~" | "!~" | "<" | ">" | "<=" | ">=") value
                 | [NOT] IN "(" value ("," value)* ")"
                 | IS [NOT] (EMPTY | NULL) )
value   := "quoted" | 'quoted' | word | function "(" [value ("," value)*] ")"
sort    := field [ASC | DESC]
  • Precedence: NOT, then AND, then OR; use parentheses otherwise. = EMPTY and != EMPTY mean is EMPTY and is not EMPTY.
  • Quote values with spaces or that are keywords ("In Progress", "and"). \" and \\ escape inside quotes. Field names can be quoted too ("story points" > 3).
  • ~ matches when every word appears (case-insensitive). != and not in also match issues where the field is empty, so assignee != bob includes unassigned issues.
  • Limits: 4000 characters, 100 conditions, 32 levels of nesting, 200 values in a list.

The key is looked up in the projects being searched; an unknown key (or one only used in projects you cannot view) is the same error: "No project searched has a custom field". Custom fields cannot be used in ORDER BY.

Dates, functions and sorting

Dates are UTC. Use 2026-01-31 (a whole day: = matches that day, <= includes it), "2026-01-31 14:30", relative offsets from now (-7d, -2w, +1M, -1w2d; units y M w d h m) and functions now(), startOfDay(), endOfDay(), startOfWeek() (Monday), endOfWeek(), startOfMonth(), endOfMonth(), startOfYear(), endOfYear(), each with an optional offset such as startOfWeek(-1w). currentUser() is the signed-in user.

ORDER BY works with any field except text, comment, labels, watcher, parent, epic, component, the versions and cf[...]. The default is updated DESC, with the issue id breaking ties.

Examples

# My open work, most urgent first
assignee = currentUser() AND statusCategory != Done ORDER BY priority DESC

# Overdue and unassigned
due < startOfDay() AND assignee IS EMPTY AND statusCategory != Done

# Bugs created this week with a major custom severity
type = Bug AND created >= startOfWeek() AND cf[severity] in (Major, Critical)

# Everything in the current sprint that nobody has started
sprint = openSprints() AND statusCategory in (Backlog, "To Do")

# An epic's whole subtree, and issues with no charge code
epic = WEB-9
wbs IS EMPTY AND project = WEB

# Free text across title, description and comments
text ~ "avatar safari"

Security and permissions

Queries are parsed to a tree and translated into a database query with every value as a parameter, never as SQL text. Every query is first limited to the projects you can view, and names (projects, statuses, sprints, keys) are resolved only inside those projects, so an error for a private project reads the same as for one that does not exist.

CSV export and import

Export

Menu, Export CSV on the issue list (basic filters or GQL) and on /issues/search lets you pick columns: key, project, title, type, status, status category, priority, assignee, reporter, labels, milestone, sprint, parent, story points, due date, created, updated, resolved, description. Downloads come from GET /p/{key}/issues/export.csv?...&columns=... or GET /issues/export.csv?gql=...&columns=.... Files are UTF-8 with a byte-order mark, at most 10,000 rows, and cells starting like a spreadsheet formula (= + - @, tab, CR) are prefixed with '.

Import

Menu, Import CSV (/p/{KEY}/import, Maintainer):

  1. Upload a UTF-8 CSV whose first row names the columns. Limits: CsvImport:MaxBytes (default 2 MB) and CsvImport:MaxRows (default 1000).
  2. Map columns to title (required), description, type, priority, status, assignee, labels (comma or semicolon separated, existing labels), story points (0 to 100), due date (yyyy-MM-dd), parent and key. Headers from the export map automatically.
  3. Preview lists every row with its errors (unknown status, label or user, bad numbers or dates, hierarchy violations, duplicate keys). Import is disabled while any row has an error.
  4. Import creates everything in one transaction: all or nothing. Parent may be an existing issue (WEB-12) or the Key of another row, so an exported epic with its stories re-imports with its hierarchy.

Each imported issue gets the activity "imported from CSV" and the import is audited as issue.imported. Imports send no notifications or webhooks.

Search and fields API

curl -G -H "Authorization: Bearer $GITBENCH_TOKEN" \
  --data-urlencode 'gql=project = WEB AND type = Bug AND statusCategory != Done ORDER BY priority DESC' \
  --data-urlencode 'perPage=50' \
  https://gitbench.example.com/api/v1/search/issues

The response is a list of issues with X-Total-Count and Link paging headers. A query error is a 400 problem document with position (0-based), length and reason. Related endpoints under /api/v1/projects/{key}: /fields, /components, /versions, /issue-templates. Issues carry customFields, components, fixVersions, affectsVersions and estimates. See REST API and webhooks for tokens and paging.
