AI tools (MCP) and the command line

ByteBench speaks the Model Context Protocol, so AI assistants such as Claude Code can read your projects, issues, pull requests, code and CI runs, and (if you allow it) create and update issues. The bytebench command-line tool does the same from a terminal. Both act as you, with a personal access token, and see only what you can see.

Both use the same personal access tokens as the REST API. Create one under Profile, Access tokens. The profile page also has a Use with AI tools / CLI panel with these commands filled in with your server's address (never with a token).

Which token

Token scopeMCP and CLI
read_apiAll read tools and commands. Tools that change data are not even listed, and calling one is refused.
write_apiEverything, including creating, updating, commenting on and moving issues.
Git scopes onlyRefused (403): the token has no API scope.

Give an AI assistant the smallest scope that does the job, and set an expiry. Every action still goes through the project permissions: a viewer's token can read but never write, whatever its scope, and a project you cannot see answers "not found" as if it did not exist.

The MCP server

The server is part of ByteBench, at POST /mcp (Streamable HTTP transport, protocol version 2025-06-18, older 2025-03-26 and 2024-11-05 clients are answered too). It is stateless: each request is one JSON-RPC message answered with one JSON response, so there are no sessions and GET and DELETE answer 405. JSON-RPC batches are not accepted. Request bodies are limited to 256 KB.

  • Authentication: Authorization: Bearer gbp_… (a personal access token) or Bearer bbo_… (an OAuth access token, see Sign in with OAuth) only. Cookies are ignored, so a web page can never drive the endpoint with your browser session. Without a valid token the answer is 401 with a WWW-Authenticate: Bearer header that, while OAuth is on, names the protected resource metadata (resource_metadata="{site}/.well-known/oauth-protected-resource/mcp"). A request carrying an Origin header for a different host is refused (DNS-rebinding guard).
  • Rate limit: the REST API's per-token limit (RateLimiting:Api, 300 requests a minute by default) covers /mcp too; over the limit the answer is 429 with Retry-After.
  • Audit: each tool call records mcp.tool_called in the audit log with the tool name, the project key and the token id (or, for OAuth, the grant id). It never records arguments or any text you or the model wrote.
  • Switch off: set Mcp:Enabled to false and /mcp does not exist.

Claude Code

claude mcp add --transport http bytebench https://bytebench.example.com/mcp \
  --header "Authorization: Bearer <your-token>"

Or leave out the header and let Claude Code sign in with OAuth: claude mcp add --transport http bytebench https://bytebench.example.com/mcp, then /mcp in Claude Code and choose to authenticate. Your browser opens ByteBench's consent page.

Sign in with OAuth

MCP clients that implement the MCP authorization spec (such as Claude Code and Claude Desktop) can connect with only the server address and a Sign in in your browser, instead of a pasted token. ByteBench is its own OAuth 2.1 authorization server for this:

  1. The client calls /mcp, gets 401 and reads the protected resource metadata (RFC 9728) at /.well-known/oauth-protected-resource (also at /.well-known/oauth-protected-resource/mcp), then the authorization server metadata (RFC 8414) at /.well-known/oauth-authorization-server.
  2. It registers itself at POST /oauth/register (dynamic client registration, RFC 7591). Only public clients are accepted (token_endpoint_auth_method: none, no secret). Redirect URIs must be https://, http:// on a loopback host (127.0.0.1, localhost or [::1], any port), or a custom scheme for a native app (cursor://…); javascript:, data:, file: and similar schemes, fragments and user information are refused. At most 10 per client.
  3. Your browser opens /oauth/authorize. If you are not signed in to ByteBench you sign in first and come back. A consent page shows the application's name (chosen by the application and not verified, so check that you just started this), where you will be sent back to, and what it asks for. Nothing is approved without you pressing Approve; Deny sends the application an access_denied error.
  4. The application exchanges the one-time code at POST /oauth/token and gets an access token (bbo_…, valid 1 hour) and a refresh token (bbr_…, valid 30 days).
ScopeMeans
read (the default)Like a read_api token: the read tools only.
writeLike a write_api token: also creating and changing issues. The consent page says so.

The rules ByteBench enforces:

  • PKCE is required with S256; plain and requests without a challenge are refused. state is required: without it the request stops on an error page. The token request must send the matching code_verifier.
  • Codes are single use, valid 60 seconds, and bound to the client, the exact redirect URI, the PKCE challenge and the user who approved. Using a code twice fails, and revokes the tokens it was already exchanged for.
  • Redirect URIs are compared exactly (no prefix, case, port or trailing-slash leniency). An unknown client or an unregistered redirect URI gets an error page, never a redirect.
  • Refresh tokens rotate: each refresh returns a new pair and retires the old refresh token. Presenting a retired refresh token again revokes the whole grant (every token of it) and records oauth.refresh_reuse_detected. A refresh can narrow the scope but never widen it.
  • Resource indicators (RFC 8707): when the client sends resource, it must be this server's /mcp address, else invalid_target.
  • Where the tokens work: only at /mcp. The REST API refuses them, and so does everything else that takes personal access tokens. They act as the user who approved, with the approved scope and the user's project permissions.
  • When they stop: when the access token expires, when the grant is revoked (from the profile, by the client at POST /oauth/revoke (RFC 7009) with a refresh token, or by refresh-token reuse), or when the account is deactivated or locked.
  • Storage: only SHA-256 hashes of codes and tokens are kept. Responses from the token endpoint are Cache-Control: no-store.
  • CORS: the metadata, registration, token and revocation endpoints answer cross-origin requests (without credentials) so browser-based clients can use them; the authorization page never does, and it cannot be framed.
  • Registrations are limited to 20 an hour from one address and 1,000 clients in total (Mcp:OAuth:MaxRegistrationsPerIpPerHour, Mcp:OAuth:MaxClients). Client names are escaped wherever they are shown.

Connected apps: the Use with AI tools / CLI panel on your profile lists the applications you approved, with their access and when they were last used, and a Revoke button that signs one out at once.

Audit: oauth.client_registered, oauth.consent_granted, oauth.consent_denied, oauth.token_issued, oauth.token_refreshed, oauth.grant_revoked (with the reason) and oauth.refresh_reuse_detected. Tokens and codes are never recorded.

Switch off: set Mcp:OAuth:Enabled to false: the OAuth endpoints and metadata disappear, the 401 no longer names the metadata, and /mcp accepts only personal access tokens. Lifetimes are in Configuration.

Other MCP clients

Clients that read a JSON configuration take the same address and header:

{
  "mcpServers": {
    "bytebench": {
      "type": "http",
      "url": "https://bytebench.example.com/mcp",
      "headers": { "Authorization": "Bearer <your-token>" }
    }
  }
}

Keep the token out of files you commit: most clients can read the header value from an environment variable.

Tool reference

Tools are named in snake_case and each takes a JSON object. Unknown arguments, wrong types, over-long values and unknown enum values are returned to the model as an error result (isError: true) saying what to fix, never as a crash. Results are concise text plus structured content. Output is capped: text at 24,000 characters, files at 20,000, diffs at 16,000, logs at 16,000 characters from the end, lists at 100 items. When something is cut, the text says [truncated] and the structured content has truncated: true. Tokens, password hashes and secrets are never returned. Repositories are named PROJECT/slug, as list_repositories prints them.

Read tools are marked readOnlyHint and the write tools are not, so clients can ask you before running them. Text that comes back from tools (issue and comment text, file contents, logs) was written by people; the server tells the model to treat it as data and not as instructions, but you should still be careful which projects an assistant with write_api reads.

The command-line tool

bytebench is a .NET tool with no dependencies, built from cli/ByteBench.Cli. It needs the .NET 10 runtime and uses the REST API. Pack and install it from a checkout:

dotnet pack cli/ByteBench.Cli -c Release -o ./nupkg
dotnet tool install --global ByteBench.Cli --add-source ./nupkg

Installing a release

Released versions are published as the NuGet package ByteBench.Cli (when the project publishes to nuget.org) and as GitHub releases tagged cli-v<version>:

dotnet tool install -g ByteBench.Cli
dotnet tool update -g ByteBench.Cli
bytebench --version

Each GitHub release also carries self-contained single-file binaries that need no .NET installed (bytebench-<version>-osx-arm64, osx-x64, linux-x64, linux-arm64, win-x64.exe), a .sha256 file for each and a combined SHA256SUMS. Check a download before you run it, for example shasum -a 256 -c bytebench-1.2.3-linux-x64.sha256, then make it executable and put it on your PATH as bytebench.

bytebench --version prints the package version. Shell completion for commands, subcommands and options:

source <(bytebench completion bash)    # in ~/.bashrc
source <(bytebench completion zsh)     # in ~/.zshrc
bytebench completion fish | source     # in ~/.config/fish/config.fish

Releasing the CLI (maintainers)

The workflow .github/workflows/cli-release.yml runs when a tag cli-v<semver> is pushed (for example cli-v0.2.0; a version with a suffix such as -beta.1 becomes a pre-release). It builds the solution, runs the CLI tests, packs the tool with the tag's version, publishes the five self-contained binaries with their checksums, and creates the GitHub release with the binaries, the checksums and the .nupkg. It pushes the package to nuget.org only when the repository has a secret named NUGET_API_KEY: create a key on nuget.org with the Push scope limited to ByteBench.Cli, and add it under Settings, Secrets and variables, Actions. Without the secret that step is skipped. The package version defaults to 0.1.0 for local builds. Every pull request also checks that the tool still packs and installs (cli-pack in ci.yml).

Logging in

Pipe the token on standard input (or set BYTEBENCH_TOKEN), so it never appears in your shell history or the process list:

echo "$TOKEN" | bytebench login --server https://bytebench.example.com
bytebench whoami
bytebench logout

login checks the token against the server first and exits 3 if it is rejected. The token is saved in ~/.config/bytebench/config.json: the folder is created with mode 0700 and the file with mode 0600, it is replaced atomically, and the tool refuses to use the file (or the folder) if it is a symbolic link, and refuses to read a config file other users can read. The token is never printed. BYTEBENCH_TOKEN and BYTEBENCH_SERVER override the saved values and need no file at all, which suits CI.

HTTPS is required, except for localhost, 127.0.0.1 and ::1. For a trial server on plain HTTP you must pass --insecure to login, which warns and remembers the choice. The tool never follows redirects, so a misconfigured address cannot send your token to another host.

Managing projects from the command line

These commands need a token with write_api. Each is one call to the management API, so your role decides what works and the server's message is printed when it refuses (a duplicate exits 1 with Conflict: …). Dates are yyyy-MM-dd.

bytebench projects create --key KEY --name T [--description D] [--visibility private|internal] [--group ID]Create a project (you become Owner).
bytebench projects update KEY [--name T] [--description D] [--visibility V], projects delete KEY --confirm KEYChange settings (Owner), or delete the project for good.
bytebench members list KEY, add KEY USER --role R, role KEY USER --role R, remove KEY USERProject members; roles are viewer, developer, maintainer, owner.
bytebench labels list|create|delete KEY …create KEY --name N [--color #rrggbb], delete KEY ID.
bytebench versions list|create|release|unrelease KEY …create KEY --name N [--start D] [--end D], release KEY ID.
bytebench sprints list|create|start|complete|delete KEY …create KEY [--name N] [--goal G], start KEY ID --start D --end D, complete KEY ID [--to backlog|new|SPRINT_ID].
bytebench repos create --project KEY --name T [--slug S] [--description D]Create a repository with an initial README.
bytebench repos update KEY/slug [--name] [--description] [--branch DEFAULT] [--slug NEW], archive, unarchive, delete KEY/slug --confirm "NAME"Repository settings; deleting needs the repository's name.
bytebench protection list KEY/slug, set KEY/slug --pattern P [--approvals N] [--type block-pushes|require-checks|require-signed|allow-force-push|allow-delete]…, delete KEY/slug IDBranch protection rules; set creates the rule or updates the one for that pattern.
bytebench webhooks list KEY, create KEY --url U --type EVENT…, delete KEY IDProject webhooks; create prints the signing secret once.

Boards, workflow statuses, custom fields, components, groups, imports and mirrors are in the API only (use curl or any HTTP client).

bytebench completion bash|zsh|fish prints a shell completion script (see Installing a release).

Every command takes --json for machine-readable output (the API's JSON, unchanged) and --help. Text output is plain. Colour is used only when standard output is a terminal and NO_COLOR is not set. Text that came from the server (titles, comments, logs) has terminal control characters replaced with ?, so an issue cannot rewrite your screen.

CodeMeaning

1Error: not found, not allowed, server or network problem, invalid query
