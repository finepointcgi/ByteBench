AI tools (MCP) and the command line

ByteBench speaks the Model Context Protocol, so AI assistants such as Claude Code can read your projects, issues, pull requests, code and CI runs, and (if you allow it) create and update issues. The bytebench command-line tool does the same from a terminal. Both act as you, with a personal access token, and see only what you can see.

Both use the same personal access tokens as the REST API. Create one under Profile, Access tokens. The profile page also has a Use with AI tools / CLI panel with these commands filled in with your server's address (never with a token).

Which token

Token scopeMCP and CLI
read_apiAll read tools and commands. Tools that change data are not even listed, and calling one is refused.
write_apiEverything, including creating, updating, commenting on and moving issues.
Git scopes onlyRefused (403): the token has no API scope.

Give an AI assistant the smallest scope that does the job, and set an expiry. Every action still goes through the project permissions: a viewer's token can read but never write, whatever its scope, and a project you cannot see answers "not found" as if it did not exist.

The MCP server

The server is part of ByteBench, at POST /mcp (Streamable HTTP transport, protocol version 2025-06-18, older 2025-03-26 and 2024-11-05 clients are answered too). It is stateless: each request is one JSON-RPC message answered with one JSON response, so there are no sessions and GET and DELETE answer 405. JSON-RPC batches are not accepted. Request bodies are limited to 256 KB.

  • Authentication: Authorization: Bearer gbp_… only. Cookies are ignored, so a web page can never drive the endpoint with your browser session. Without a valid token the answer is 401 with a WWW-Authenticate: Bearer header. A request carrying an Origin header for a different host is refused (DNS-rebinding guard).
  • Rate limit: the REST API's per-token limit (RateLimiting:Api, 300 requests a minute by default) covers /mcp too; over the limit the answer is 429 with Retry-After.
  • Audit: each tool call records mcp.tool_called in the audit log with the tool name, the project key and the token id. It never records arguments or any text you or the model wrote.
  • Switch off: set Mcp:Enabled to false and /mcp does not exist.

Claude Code

claude mcp add --transport http bytebench https://bytebench.example.com/mcp \
  --header "Authorization: Bearer <your-token>"

Other MCP clients

Clients that read a JSON configuration take the same address and header:

{
  "mcpServers": {
    "bytebench": {
      "type": "http",
      "url": "https://bytebench.example.com/mcp",
      "headers": { "Authorization": "Bearer <your-token>" }
    }
  }
}

Keep the token out of files you commit: most clients can read the header value from an environment variable.

Tool reference

Tools are named in snake_case and each takes a JSON object. Unknown arguments, wrong types, over-long values and unknown enum values are returned to the model as an error result (isError: true) saying what to fix, never as a crash. Results are concise text plus structured content. Output is capped: text at 24,000 characters, files at 20,000, diffs at 16,000, logs at 16,000 characters from the end, lists at 100 items. When something is cut, the text says [truncated] and the structured content has truncated: true. Tokens, password hashes and secrets are never returned. Repositories are named PROJECT/slug, as list_repositories prints them.

search_issuesreadSearch issues with a GQL query, or list a project with text and status. Paged with limit and offset.
get_issuereadOne issue with description, labels, assignee, the last 20 comments, links, parent and children.
create_issuewriteCreate an issue (title, description, type, priority, assignee, labels, story points). Needs Developer or higher in the project.
update_issuewriteChange title, description, status, priority, assignee (none unassigns), labels or story points. Only what you pass changes.
comment_on_issuewriteAdd a Markdown comment.
transition_issuewriteMove an issue to a workflow status by name or category; moves the workflow forbids are refused.
my_workreadOpen issues assigned to you and your open pull requests.
list_repositoriesreadRepositories you can read, with default branch and open pull request count.
list_pull_requestsreadPull requests of a repository or project, filtered by state.
get_pull_requestreadDescription, state, review state, merge check, recent comments and a diff summary; include_diff adds the size-capped unified diff.

Read tools are marked readOnlyHint and the write tools are not, so clients can ask you before running them. Text that comes back from tools (issue and comment text, file contents, logs) was written by people; the server tells the model to treat it as data and not as instructions, but you should still be careful which projects an assistant with write_api reads.

The command-line tool

bytebench is a .NET tool with no dependencies, built from cli/ByteBench.Cli. It needs the .NET 10 runtime and uses the REST API. Pack and install it from a checkout:

dotnet pack cli/ByteBench.Cli -c Release -o ./nupkg
dotnet tool install --global ByteBench.Cli --add-source ./nupkg

Logging in

Pipe the token on standard input (or set BYTEBENCH_TOKEN), so it never appears in your shell history or the process list:

echo "$TOKEN" | bytebench login --server https://bytebench.example.com
bytebench whoami
bytebench logout

login checks the token against the server first and exits 3 if it is rejected. The token is saved in ~/.config/bytebench/config.json: the folder is created with mode 0700 and the file with mode 0600, it is replaced atomically, and the tool refuses to use the file (or the folder) if it is a symbolic link, and refuses to read a config file other users can read. The token is never printed. BYTEBENCH_TOKEN and BYTEBENCH_SERVER override the saved values and need no file at all, which suits CI.

HTTPS is required, except for localhost, 127.0.0.1 and ::1. For a trial server on plain HTTP you must pass --insecure to login, which warns and remembers the choice. The tool never follows redirects, so a misconfigured address cannot send your token to another host.

Commands

CommandWhat it does
bytebench projectsYour projects.
bytebench issues list [--project KEY] [--query GQL] [--status open|closed|all] [--limit N]Issues of a project, or search with GQL (with --project the search is limited to it). With neither, the issues assigned to you.
bytebench issues show KEY-NAn issue and its comments.
bytebench issues create --project KEY --title T [--description D | --description-file FILE|-] [--type T] [--priority P] [--assignee USER] [--label NAME]Create an issue (repeat --label). Prints its address.
bytebench issues comment KEY-N --body TEXT | --body-file FILE|-Comment on an issue.
bytebench issues move KEY-N --to STATUSMove to a workflow status (by name) or category.
bytebench issues assign KEY-N USER, … --noneAssign or unassign.
bytebench prs list [--project KEY] [--state open|merged|declined|all]Pull requests across your projects or one project.
bytebench prs show KEY/slug NA pull request with its reviews and comments (KEY/slug#N works too).
bytebench repos list [--project KEY]Repositories with their clone addresses.
bytebench pipelines list KEY/slug [--branch B] [--status S]CI pipelines of a repository.
bytebench pipelines logs KEY/slug ID [--step ID] [--tail CHARS]The end of a step's log (the first failed step unless you pick one).
bytebench open KEY-NPrints the issue's web address.

Every command takes --json for machine-readable output (the API's JSON, unchanged) and --help. Text output is plain. Colour is used only when standard output is a terminal and NO_COLOR is not set. Text that came from the server (titles, comments, logs) has terminal control characters replaced with ?, so an issue cannot rewrite your screen.

Exit codes

CodeMeaning
0Success
1Error: not found, not allowed, server or network problem, invalid query
2Usage: unknown command or option, a missing or malformed argument, a refused plain-HTTP address
3Authentication: not logged in, the token was rejected, or it lacks the needed scope
