AI overview and setup

ByteBench can use Claude to draft issues, review pull requests, triage new issues and assist in the web editor, and every AI feature stays hidden until you give the server an API key or a Claude Code login.

AI never changes your data by itself. Each feature returns text, filters, comments or proposals that a person reviews, accepts or ignores. The AI review bot is the one exception that writes on its own: it posts comments on pull requests, and it never approves or merges.

Set up the Anthropic API key

The key is read from the ANTHROPIC_API_KEY environment variable, or from the Ai:ApiKey setting. Provide it through the environment or user-secrets and never write it into appsettings.json or any other file that ends up in Git.

# environment variable (Docker, systemd, shell)
export ANTHROPIC_API_KEY=<your key>

# or .NET user-secrets in development (run "dotnet user-secrets init" once if needed)
dotnet user-secrets set "Ai:ApiKey" "<your key>"

In Docker Compose, pass it as an environment variable (ANTHROPIC_API_KEY) from a .env file that is not committed. Restart ByteBench afterwards. The key is read when the first AI call is made, and the configuration is read at start-up.

Treat the key like a password. The /admin/ai page never shows it, and ByteBench never sends it to the browser.

The Claude Code backend

Instead of an API key you can install the claude command-line tool on the server and sign it in once as the account ByteBench runs as (run claude interactively, or create a token with claude setup-token and set CLAUDE_CODE_OAUTH_TOKEN). The web editor and AI pull request review then use that account's Claude Code login or subscription for every user. Usage and billing belong to the server account, not to individual users.

How it is sandboxed

  • The user's workspace (or the pull request files for a review) is written to a fresh temporary directory with mode 700 and deleted afterwards. The repository's own .claude/ folder and .mcp.json are not copied, so a repository cannot add hooks, permissions or MCP servers.
  • claude -p runs headless there with the prompt on standard input (never on a command line), file tools only (Read, Grep, Glob, Edit, Write), and shell, web fetch, web search and sub-agent tools explicitly denied. Permission mode is dontAsk: nothing ever prompts, and anything not allowed is refused.
  • The environment is clean. None of the server's variables (database strings, API keys, cloud credentials) are passed. Only what Claude Code needs to find itself and its login: HOME, USER, PATH, locale and temp variables, plus CLAUDE_CONFIG_DIR and CLAUDE_CODE_OAUTH_TOKEN when set.
  • When the run ends, the directory is compared with what was written. Every changed file becomes a proposal in the editor. Nothing is applied automatically.
  • ByteBench reads claude --help at start-up and only passes the optional flags that version lists.
Ghost-text completions need the API backend, because the CLI is too slow for them. With the Claude Code backend the toggle is hidden.

The /admin/ai page

Site administrators find a read-only status page at /admin/ai. It shows three blocks:

  • Anthropic API: whether a key is configured, the model in use, and which features use it.
  • Claude Code on the server: installed or not, version, executable path, last check time, limits (concurrent runs, timeout, turns) and the model. The Check again button re-detects the CLI without restarting ByteBench. ByteBench only runs claude --version and claude --help from this page.
  • Web editor: the configured backend setting, the backend actually in use, whether inline completions are available, and the per-request and per-user limits.

To change anything, edit the Ai:* settings and restart. Other users who open the page see "Only site administrators can see the AI configuration."

What is sent to the provider

When you use a feature, the text it needs is sent to Anthropic (API backend) or to the Claude Code account's provider (Claude Code backend). Nothing is sent until someone uses a feature or an automatic trigger fires.

  • Issue helpers: the issue's title, description, recent comments and activity, plus names of existing labels, milestones and people where needed. For duplicates, titles and descriptions of up to 25 candidate issues.
  • Pull request review and description: the title, description, commit messages, file paths and the diff (minus ignored paths, lockfiles, binaries and generated files).
  • Triage: the issue text, up to five recent comments, the project's labels and components, Developer+ member names with short evidence (open assigned issues, related past issues, recent commits on files the issue mentions) and up to ten candidate duplicates.
  • Web editor: the open file and selection, files you attach, and files the assistant reads or searches in your workspace. It cannot read other repositories.

Content from users is always put in delimited data blocks and the system prompts tell the model to treat it as data and never follow instructions inside it. Output is rendered as plain text or Markdown with raw HTML disabled. If your repositories must not leave your network, leave AI unconfigured, or turn Ai:Enabled off.

Every API call records token counts (input, output, cache read and write), the feature name, model, user and project in the AiUsages table, never the prompt text. Use it for cost reporting.
