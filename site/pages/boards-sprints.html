Boards

Each project can have several boards. The sidebar Board link opens the project's default board at /p/{KEY}/board; other boards live at /p/{KEY}/boards/{id}. The arrow next to the board name switches boards and, for Maintainers, offers Create board and Board settings (/p/{KEY}/boards/{id}/settings).

The default board

Every project has exactly one default board, created the first time boards are read. It follows the workflow: one column per workflow status, in workflow order, updated whenever the workflow changes. It shows every issue including all Done ones, and its sprint picker starts on the active sprint. You can move the default flag to another board (Make default board), but you cannot delete the default board.

Kanban and Scrum boards

TypeWhat it shows
KanbanEvery issue matching the board's filter. Done-category issues appear only if closed in the last N days (14 for new boards; empty means all). A toolbar sprint picker narrows further.
ScrumOnly the project's active sprint. With no active sprint the board is empty and links to the backlog.

Columns and WIP limits

A column maps to one or more workflow statuses. A status can be in at most one column of a board; a status in no column is not on that board (the settings page lists such statuses). Customising columns stops a board following the workflow; Follow the workflow again restores it.

A column can have a WIP limit. It counts the column's issues within the board's own scope (filter and sprint), ignoring toolbar and quick filters. A column over its limit turns red. Tick Refuse drops that go past a column's WIP limit to make a full column refuse new cards (reordering inside it still works).

Filters, quick filters and swimlanes

  • Board filter: a query string in the issue list's format (copy it from a filtered issue list or choose a saved filter) plus simple pickers for labels, assignee, type and epic. Unlike the issue list, a board query without open= includes closed issues. assigneeId=me means whoever is viewing.
  • Quick filters: named toggle chips above the board, each a query (suggestions: Only my issues assigneeId=me, Bugs type=Bug). Several active chips must all match.
  • Swimlanes: none, assignee, epic, priority or type. An issue's epic is its parent, or its grandparent for a sub-task.
  • Card fields: key, type, labels, priority, story points, assignee, parent and blocked chips, epic, due date and milestone.

Moving cards

Drag a card to another column. The move goes through the normal issue code, so workflow transitions are enforced: a column that cannot take the dragged card is hatched and refuses the drop. Dropping on a column that already shows the card's status just reorders it; otherwise the card moves to the column's first status that the workflow allows. With swimlanes, dropping changes only the status, not the lane's field. Moving cards needs Developer; creating, configuring and deleting boards needs Maintainer. Two people on the same board see each other's moves live.

Backlog and planning

The backlog (/p/{KEY}/backlog, sidebar Backlog) lists the active sprint, then planned sprints, then the backlog proper: open issues in no sprint. Each section shows its issue count and story points. Drag issues between sections or within one to rank them; ranking uses the same order as the board. Each row also has a Move menu (top, up, down, bottom, or another sprint) for keyboards and touch screens. Moving issues in and out of sprints and ranking needs Developer.

Sprint lifecycle

A sprint is Planned, then Active, then Completed. At most one sprint per project is active (the database enforces it). Creating, editing, starting, completing and deleting sprints needs Maintainer.

  1. Create: Create sprint on the backlog suggests a name like "WEB Sprint 9".
  2. Plan: drag issues into the planned sprint.
  3. Start: Start sprint asks for start and end dates and a goal, and snapshots the committed scope (issue count and story points).
  4. Work: the Scrum board shows the sprint. Scope changes are tracked, so burndown reflects them.
  5. Complete: Complete sprint shows the done and open counts, snapshots what was completed, and asks where the open issues go: carry over to a planned sprint, to a new sprint, or back to the backlog. Done issues stay in the completed sprint.

Deleting a planned or active sprint sends its issues back to the backlog. Completed sprints are kept for reports.

Elsewhere, the issue page has a Sprint picker, the issue list a sprint filter, and GQL understands sprint = openSprints(), futureSprints() and closedSprints().

Burndown and velocity

The project's Reports page (/p/{KEY}/reports) draws:

  • Burndown: remaining work per day from start to end against an ideal line. History is rebuilt from issue activity: from each issue's current state it undoes status changes to and from Done, estimate changes and sprint membership changes, newest first. Unestimated issues count as 0 points. A toggle switches between story points and issue count.
  • Velocity: committed versus completed for the last 8 completed sprints, with the average completed.

More flow charts (cycle time, cumulative flow and so on) are on Dashboards and delivery reports. Sprint data in the API: GET /api/v1/projects/{key}/sprints?state=planned|active|completed and /sprints/{id}; issues carry sprintId and can be filtered with ?sprint= (an id, none or active).

Milestones

Milestones (/p/{KEY}/milestones, also showing sprints) group issues under a goal with a start and due date and show progress and a story-point burn-up. Maintainers manage them; groups can define milestones inherited by their projects. They are separate from versions, which describe releases.

Roadmap and timeline

The roadmap is a Gantt-style timeline of epics at /p/{KEY}/roadmap, and across a group's projects at /g/{path}/-/roadmap.

  • Dates: each issue has a start date and a due date (the target). A bar runs between them; with one date it is dashed for that day. Epics without dates have a Set dates button.
  • Progress: an epic's bar fills with the share of its children that are done. Expand an epic to see its children with their own bars.
  • Editing (Developer): drag a bar to move it or drag an end to change one date, snapping to whole days. Click a bar, or focus it and press Enter, for a dates dialog. Changes are recorded in the issue's activity and notify watchers; a start after the target is refused.
  • Markers: a red today line, sprint bands in the header, milestone flags, and arrows for "blocks" links.
  • Zoom and filters: weeks, months or quarters; filter by label or assignee.

Versions and releases of a project

Versions are named releases of a project that issues can be assigned to as fix version or affects version. The Versions page (/p/{KEY}/versions) lists unreleased versions first, each with the done/total progress of its fix-version issues, story points and issue list. Maintainers create, edit, mark released and delete versions there. A version whose name matches a published release tag in one of the project's repositories (1.0 or v1.0) links to that release; see Code browsing and tools for releases and tags. Versions are defined in Fields, filters and search.

Settings and limits

Boards and sprints have no site-wide configuration keys. Everything above is per project. Board changes are audited as board.* events. The demo seed gives the WEB project completed sprints, an active one and a planned one so the charts have data.
