REST API and webhooks

Everything you can do in the ByteBench web interface goes through the same services as the JSON API at /api/v1, and projects can push events to your own systems with signed webhooks.

Base URL, documentation and conventions

  • Base URL: https://bytebench.example.com/api/v1. Anything else under /api/ answers a JSON 404 ("No such API endpoint").
  • Interactive reference: /developers/api (the API link in the top bar) and the full OpenAPI 3.1 document at /api/v1/openapi.json. The OpenAPI document is always the most complete listing of fields and bodies.
  • JSON is camelCase. Enums are camelCase strings (inProgress, merged). Timestamps are ISO 8601 UTC, due dates are yyyy-MM-dd.
  • Responses are DTO records, never database entities. Links in responses use the request's host, or the PublicBaseUrl setting if set.
  • Responses are sent with Cache-Control: no-store.
  • Writes go through the same services as the UI, so activity entries, notifications, live updates, automation, AI review and webhooks all fire as usual.

Authentication and scopes

Create a personal access token under Profile, Access tokens (see Accounts). Tokens start with gbp_ and are shown once. Send one as a bearer token:

curl -H "Authorization: Bearer $BYTEBENCH_TOKEN" \
  https://bytebench.example.com/api/v1/user

A signed-in browser session (cookie) also works, which is how the UI itself can call the API.

ScopeAllows
read_apiGET and HEAD requests
write_apiEvery request, reads included
read_repository / write_repositoryGit over HTTP only. They do not grant API access
  • A token without an API scope gets 403 Insufficient scope, and an API-only token gets 403 from Git.
  • A missing, invalid, expired or revoked token (or a locked-out user) gets 401 with a WWW-Authenticate: Bearer header. Failures are logged with the client address.
  • CSRF protection: a cookie-authenticated write must send Content-Type: application/json or an X-Requested-With header, otherwise 403. Token requests are not affected.

The caller's project role decides everything else. A project you cannot see answers 404, exactly like one that does not exist. A visible project where you lack the permission answers 403 (for example a Viewer creating an issue, or a Developer merging).

Pagination

List endpoints take ?page= (default 1) and ?perPage= (default 30, maximum 100). They return an X-Total-Count header and an RFC 8288 Link header with first, prev, next and last relations.

curl -sD - -H "Authorization: Bearer $BYTEBENCH_TOKEN" \
  "https://bytebench.example.com/api/v1/projects?perPage=2" -o /dev/null

Errors

Errors are RFC 9457 problem details (application/problem+json) with status, title and detail.

StatusMeaning
400Bad input or malformed JSON
401Missing, invalid, expired or revoked token
403Missing scope, missing permission, or the CSRF rule above
404Not found, or you cannot see it
409Merge conflict or already merged (a merge conflict response carries conflictPaths)
415Body is not JSON
422Validation failed or the operation is refused (for example a rule not satisfied)
429Rate limit reached (see below), or an AI triage limit
500Unexpected error (logged on the server; the detail is generic)

Rate limiting

By default /api/* allows 300 requests per 60 seconds, counted per access token (else per signed-in user, else per client IP). Over the limit you get 429 with a Retry-After header and a problem+json body. Change it with RateLimiting:Api:PermitLimit and WindowSeconds, or switch it off with a limit of 0. Full details are on the Administration page. Rate limiting is off in the Development configuration.

Endpoint catalogue

All paths are under /api/v1. {key} is the project key (for example WEB), {slug} a repository slug and {number} an issue or pull request number. The role column lists the minimum role when it is not just "can view". Check /api/v1/openapi.json for the request and response shape of each operation.

Webhooks

A project can POST JSON events to your own services. Webhooks are managed by Maintainers and Owners (the manage-repositories permission) at Settings, Webhooks (/p/{KEY}/settings/webhooks). A project may have at most 20 generic webhooks. Slack and Teams integrations are separate (see Slack and Microsoft Teams).

Create a webhook

  1. Open the project, then Settings, Webhooks.
  2. Enter the URL (http or https, no credentials in the URL, at most 2,000 characters).
  3. Choose at least one event and leave Active ticked.
  4. Leave the secret blank to have ByteBench generate one, or enter your own. A generated secret is shown once and masked afterwards. New secret rotates it.
  5. Press Send test ping to check your receiver. Pings are limited to 5 per minute per user (RateLimiting:WebhookPing), and the ping event is sent even to an inactive hook.

Secrets are encrypted at rest with ASP.NET Core Data Protection. If the Data Protection keys are lost, stored secrets cannot be decrypted. Deliveries then fail with a message saying so, and New secret repairs the hook.

Headers and signature verification

Every request is a POST with a JSON body that starts with event, deliveryId, timestamp, project and sender, followed by the event's own fields. These headers are sent:

HeaderValue
X-ByteBench-EventThe event name, for example issue.created
X-ByteBench-DeliveryA GUID identifying the delivery (the same on redelivery)
X-ByteBench-Hook-IDThe webhook's numeric id
X-ByteBench-Signature-256sha256= followed by the lowercase hex HMAC-SHA256 of the raw body bytes, keyed with the webhook secret
X-ByteBench-Redeliverytrue, only on a manual redelivery

Verify the signature on the raw bytes, before parsing, and compare in constant time:

import hashlib, hmac

def verify(secret: str, body: bytes, header: str) -> bool:
    expected = "sha256=" + hmac.new(secret.encode(), body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, header or "")
var expected = "sha256=" + Convert.ToHexStringLower(HMACSHA256.HashData(Encoding.UTF8.GetBytes(secret), body));
var ok = CryptographicOperations.FixedTimeEquals(
    Encoding.ASCII.GetBytes(expected), Encoding.ASCII.GetBytes(header ?? ""));
Use the X-ByteBench-Delivery value to de-duplicate: a retried or redelivered event reuses its delivery id.

Delivery, retries and auto-disable

  • Events are put on an in-memory queue and sent by a background worker, so a user action never waits for your receiver. Up to 8 deliveries run in parallel.
  • Each attempt times out after 10 seconds. Network errors, timeouts and 5xx answers are retried up to 3 times, after 1, 5 and 15 seconds.
  • 4xx answers, redirects (never followed) and blocked addresses fail at once without retries.
  • Every delivery is stored with its status code, duration, attempts, error and the first 4 KB of your response. The settings page shows the last 25 deliveries per hook.
  • Redeliver on a delivery resends the same body under the same delivery id with X-ByteBench-Redelivery: true.
  • After 20 failed deliveries in a row the hook is switched off and the page shows "Disabled after 20 failures". Ticking Active again resets the counter. A success also resets it.
  • Deliveries left pending by a restart are resent on startup. Hook changes are audited as webhook.created, webhook.updated, webhook.secret_rotated and webhook.deleted.

SSRF guard

  • Only http and https URLs without credentials are accepted.
  • DNS is resolved at send time and the socket connects only to an address that passed the check, so DNS rebinding cannot swap it.
  • Blocked: loopback, private ranges (RFC 1918, unique-local), link-local (including the 169.254.169.254 cloud metadata address), carrier-grade NAT, multicast and reserved ranges, IPv4-mapped, NAT64 and 6to4 forms of those, and localhost. No proxy is used.
  • To deliver to private hosts (an internal chat or CI server), set Webhooks:AllowPrivateNetworks to true. It defaults to false; the Development configuration turns it on. Leave it off in production unless you need it.
# environment form for Docker
Webhooks__AllowPrivateNetworks=true
