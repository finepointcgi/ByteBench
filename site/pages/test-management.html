Test management

Write test cases, group them into plans, run them against a tag, release or CI build, record results with evidence, file bugs from failures, and bring in automated results from JUnit, TRX, xUnit or CTRF reports.

Where things are

Tests live under each project at /p/{KEY}/tests (the Tests link in the project's sidebar):

PageWhat it is for
/p/{KEY}/testsTest cases: search, filter by suite, priority, type, and see each case's newest result
/p/{KEY}/tests/cases/{number}One case: steps, expected result, version history, results across runs. /tests/cases/new writes a new one
/p/{KEY}/tests/plansTest plans: named sets of cases, with a Start run button
/p/{KEY}/tests/runsRuns with progress and pass rate; start a run or upload a report
/p/{KEY}/tests/runs/{number}Run page: work through the cases with the keyboard, add comments and evidence, create bugs
/p/{KEY}/tests/compareCompare two runs (regressions and fixes) and a matrix of cases against the latest runs

Release pages show a Tests panel with the latest runs for the release's tag or commit, and pull requests show one for the head commit (see Release hub).

Who can do what

ActionRole
View cases, plans, runs, results, compare and matrixViewer and above (anyone who can see the project)
Create and edit test cases, start runs, record results, add evidence, create bugs, upload reportsDeveloper and above (RunTests)
Create, edit and delete plans; archive or delete cases; delete runsMaintainer and above (ManageTests)

Creating a bug also needs permission to create issues (Developer). Archived repositories do not matter here: tests belong to the project.

Test cases

A case has a title, preconditions, steps, an expected result, a priority (low, medium, high, critical), a type (manual or automated), tags and components (comma separated, lowercase), a folder or suite path such as Checkout/Payments, linked issues of the project (WEB-12, 15), free-text requirements, and for automated cases an automated name. Cases are numbered per project: TC-1, TC-2, and so on.

Version history. Changing the title, preconditions, steps, expected result, priority, tags or suite creates a new version and keeps the old text; the case page lists every earlier version. Results remember which version they were recorded against, and the run page tells you when the case changed since. Archiving hides a case from lists and new runs but keeps its results; deleting removes the results and their evidence files too.

Test plans

A plan is a named list of cases (for example "Smoke" or "Release acceptance"). Start run on a plan opens the run form with the plan selected. A run without a plan covers all active manual cases.

Runs

A run targets a version. Pick a tag (the tag must exist in one of the project's repositories: the run records the tag's commit and the release for it, if there is one), a build or version label, or both; the label is what the matrix shows. Runs started from CI carry the pipeline, branch and commit instead.

Every case in a manual run starts as not run. Results are passed, failed, blocked or skipped, each with who recorded it, when, an optional comment, and optional evidence. The run shows progress (cases with a result) and the pass rate: passed divided by passed, failed and blocked. Skipped and not-run cases count in neither direction. Finish run closes it (results are then read-only until it is reopened) and raises the test_run.completed webhook.

Executing a run from the keyboard

On the run page click the case list (or press Tab to it) and use:

KeyDoes
j or ↓ / k or ↑Next / previous case
pRecord passed and jump to the next case without a result
fRecord failed
bRecord blocked
sRecord skipped
uReset to not run

Text in the comment box is saved together with the result you record, and is not captured by the shortcuts while you type in it. After a failed or blocked result, Create bug from this failure files a bug issue prefilled with the case's preconditions, steps and expected result, your comment, the failure text, and the run, build, tag, commit and pipeline; the result links to the bug, and pressing the button again never creates a second one. The bug's priority follows the case's.

Evidence

Attach screenshots, logs or other files to a result (up to 25 MB each, 20 per result). Files are stored like issue attachments under a random name, and are always downloaded as attachments (application/octet-stream, nosniff, a sandboxing content security policy), never displayed inline, so an uploaded HTML file cannot run in ByteBench's origin.

Compare and matrix

Compare takes a baseline run and a candidate run and classifies each case: regressed (passed before, failed or blocked now), fixed, still failing, newly run and no longer run. Regressions are listed first. The matrix lines up the cases against the latest eight runs, each column labelled by its build, tag or run number, with an option to show only cases that failed somewhere. The same data is in the API (/tests/compare, /tests/matrix).

Automated results (CI and API)

Automated results come from test reports in these formats, detected automatically or named explicitly:

FormatNameTypical source
JUnit XMLjunitMaven, Gradle, pytest, Jest and most test tools
TRXtrxdotnet test --logger trx
xUnit v2 XMLxunitThe xUnit v2 console runner's -xml output (<assemblies>)
CTRF JSONctrfCommon Test Report Format reporters

How tests map to cases

  1. A TC-n token in the test's name maps it to case TC-n.
  2. Otherwise the test's full name (classname.name, or the TRX class and method) is matched against cases' automated name; the plain name is also tried when exactly one case uses it.
  3. A test that matches nothing creates a new automated case (title = the test name, folder from its class) unless auto-creation is switched off, in which case it is counted as unmapped. At most 5000 cases are created per report.

If a report names the same case twice, the worst outcome wins. Duration and the failure message (cut to 4000 characters) are stored with the result.

From CI jobs

List the report in the job's artifacts.reports, next to the security report types:

jobs:
  test:
    image: mcr.microsoft.com/dotnet/sdk:10.0
    steps:
      - run: dotnet test --logger trx --results-directory TestResults
    artifacts:
      reports:
        trx: "TestResults/*.trx"

Report types are junit, trx, xunit and ctrf. Test report entries may use a pattern (*, **, ?) and then match up to 50 files; security reports (nightowl, sarif) must still name one file. The files are also kept as artifacts. They are read whether the job passed or failed. Symbolic links and files outside the workspace are never read. All reports of one pipeline add up in one run ("CI pipeline #n") that records the pipeline, branch and commit; the run is closed, and the job log says what was read ([bytebench] Test report … 12 test(s), 11 passed, 1 failed → run #7). The configuration key Tests:AutoCreateCases (default true) controls whether CI creates missing cases.

From the UI or the API

The Upload a report button on the Runs page takes a file (optionally a build label and tag). The API takes the raw report as the request body, or a JSON envelope, and needs a token with write_api and Developer access:

curl -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/xml" \
     --data-binary @junit.xml \
     "https://bytebench.example.com/api/v1/projects/WEB/tests/reports?build=2026.11.3&tag=v2026.11.3&name=Nightly"

Query parameters: format (default: detect), build, tag, commit, ref, repository, pipelineId, run (add to an existing run), name, autoCreate (default true). Or send {"content": "…", "format": "junit", "build": "…"} as JSON. The answer is 201 with the run number and counts (total, passed, failed, skipped, createdCases, unmapped, truncated).

Untrusted report safety

  • XML with a DOCTYPE is refused outright, so external entities (reading files or URLs from the server) and entity-expansion bombs cannot work; nothing is ever fetched. The refusal is a normal 422 with a clear message and leaves no half-made run.
  • Reports larger than 16 MB are refused (413 on the API), at most 50,000 tests per report are read (truncated is then true), names are cut to 400 characters and messages to 4000. Invalid XML, JSON or a wrong document type are 422.

REST API

Everything above is available at /api/v1/projects/{key}/tests/… (see the OpenAPI document at /api/v1/openapi.json):

RoutePurpose
GET/POST /cases, GET/PATCH/DELETE /cases/{number}List (filters q, suite, priority, type, tag, archived), create, read, edit, delete cases
POST /cases/{number}/archive, /unarchive, GET /cases/{number}/revisions, /resultsArchive, version history, results across runs
GET/POST /plans, GET/PUT/DELETE /plans/{id}Plans (body: name, description, caseNumbers)
GET/POST /runs, GET/DELETE /runs/{number}Runs (list filters tag, commit, releaseId); body for create: name, planId, build, tag, commitSha, pipelineId, caseNumbers
POST /runs/{number}/close, /reopenFinish or reopen a run
PUT /runs/{number}/results/{caseNumber}Record a result: {"status": "failed", "comment": "…"} (passed, failed, blocked, skipped, not_run)
POST /runs/{number}/results/{caseNumber}/bugCreate (or return) the bug for a failed result
POST /runs/{number}/results/{caseNumber}/evidence?fileName=, GET/DELETE /evidence/{id}Evidence: the request body is the file
POST /reportsUpload an automated report
GET /compare?a=&b=, GET /matrix?runs=&count=&problems=Compare two runs; results matrix

Reads need a token with read_api (or write_api); writes need write_api. A project you cannot see is a 404; a missing role is a 403. The REST API is the only API for tests: the GQL search covers issues only.

Webhooks and audit

The webhook event test_run.completed is sent when a run is closed or an automated report is recorded. Its payload has run with number, name, build, tag, commitSha, ref, source, the counts (passed, failed, blocked, skipped, notRun), passRate and webUrl. Audit events: test_case.created, .archived, .restored, .deleted; test_plan.created, .updated, .deleted; test_run.created, .closed, .reopened, .ingested, .deleted; test_result.bug_created. Recording a single result is not audited. Test runs do not send in-app notifications.
