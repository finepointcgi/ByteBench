FAQ and troubleshooting

Realistic problems with their causes and fixes, followed by an honest list of what has only been tested with fakes.

Most start-up problems show up in two places: the log (docker compose logs -f bytebench) and, for site admins, the /admin/system page, which lists the hosting review and pending migrations.

Sign-in and cookies

I can sign in but I am bounced back to the login page (Docker or production)

Cause: outside Development, sign-in cookies are Secure-only, so a browser will not keep them on plain http://. ByteBench logs "Plain-HTTP request ... sign-in only works over HTTPS" once.

Fix: put ByteBench behind an HTTPS proxy and set ReverseProxy__Enabled=true (see Reverse proxy). For a quick local trial only, set Security__SecureCookies=false.

Everyone is signed out after every restart or deployment

Cause: the Data Protection key ring is not on a persistent volume, so a new one is made each time. Encrypted webhook and CI secrets are lost too.

Fix: point DataProtection__KeysPath at a persistent, backed-up folder (/data/keys in the image) and make sure the container user (uid 1654) can write it. In Production ByteBench refuses to start if the folder is not writable.

Account locked

Five failed sign-ins lock an account for five minutes. In addition, sign-in POSTs are rate limited per IP (10 per minute by default); see rate limits. A site admin can manage accounts at /admin/users.

There is no admin account in my new Docker install

Production has no demo data. Register at /account/register, then restart once with Bootstrap__AdminUsers=your-username. With registration closed, keep it open for this first sign-up or have another admin create the account. Lost passwords are handled by Forgot password? on the sign-in page (needs email) or by an admin on /admin/users (reset email or temporary password).

Browser and CSP

The page is broken and the browser console mentions Content-Security-Policy

Cause: HTML pages carry a CSP with default-src 'self'. Scripts must come from the site; Blazor's import map is allowed with a per-request nonce, and the app's few inline handlers by hash. Styles allow 'unsafe-inline'. Web workers must come from the site (worker-src 'self'), never blob: or data:. Things that trigger a block: a reverse proxy that injects its own script or an extension-like banner; a custom page or snippet with an inline <script> or onclick=""; an external CDN script.

Fix: to find out what is blocked without breaking users, set Security__ContentSecurityPolicyReportOnly=true and read the console. Move custom code into a .js file under wwwroot/js, or add the exact inline handler string to Security:CspInlineHandlers. As a last resort Security__ContentSecurityPolicy=false turns the header off, which the hosting review flags as a warning.

The page loads but nothing reacts, or "Reconnecting..." keeps showing

Cause: the interface is Blazor Interactive Server and needs a WebSocket on /_blazor. A proxy that does not pass Upgrade and Connection headers, or that times out idle connections, breaks it.

Fix: with nginx add proxy_http_version 1.1, the Upgrade/Connection headers and a long proxy_read_timeout (see nginx). Caddy does this by default.

400 "Invalid Hostname" or blank page behind a proxy

Cause: AllowedHosts does not include the host name the proxy sends. Or the proxy changed the Host header.

Fix: set AllowedHosts to your public host name and make the proxy pass the original Host.

Reverse proxy and forwarded headers

The audit log and rate limits show the proxy's address, links use http://

Cause: forwarded headers are only trusted from known proxies. With ReverseProxy:Enabled off, or with a proxy address that is not in KnownProxies/KnownNetworks (only loopback is trusted by default), ByteBench sees the proxy as the client and the request as HTTP. Then HSTS is not sent, cookies and generated links are wrong and every user shares one rate limit bucket.

Fix:

ReverseProxy__Enabled=true
ReverseProxy__KnownNetworks__0=172.16.0.0/12     # the network your proxy runs on
PublicBaseUrl=https://bytebench.example.com

The start-up review and /admin/system warn when PublicBaseUrl is https but the proxy setting is off.

Git push fails with 413 or hangs behind nginx

The proxy limits request bodies and buffers them. For /git/ set client_max_body_size 0; proxy_request_buffering off; proxy_buffering off;. The same applies to package and image uploads.

Database and migrations

Pending migrations

Migrations are applied automatically at start-up, in both SQLite and Postgres. If /admin/system shows pending migrations, or the app fails to start with a migration error, check the log first: it usually names the failing step (permissions, a locked SQLite file, or a PostgreSQL role that may not alter tables).

  • Make sure only one ByteBench instance uses the database.
  • If an upgrade failed half-way: stop, restore the pre-upgrade backup with restore --force and start the previous version.
  • A backup made by a newer ByteBench is refused by an older build; upgrade first.
  • Developers: after a model change add one migration per provider (--context AppDbContext and --context PostgresAppDbContext). A test fails when either snapshot is behind the model.

"ConnectionStrings:Default is required" with Postgres

With Database__Provider=Postgres the connection string must be set explicitly and must not be the SQLite default. Use ConnectionStrings__Default="Host=...;Database=...;Username=...;Password=...".

Can I move my SQLite data to PostgreSQL?

Yes: dotnet ByteBench.dll migrate-db --from <sqlite file> --to <Npgsql connection string> --verify. The steps (stop, back up, copy, switch Database__Provider, start) are in Moving from SQLite to PostgreSQL. Backups still restore only into the same provider.

migrate-db refuses or fails

  • "Start this ByteBench version once against the SQLite file first": the source is behind this version's latest migration. Start the new ByteBench on the SQLite database (it applies its migrations on start), stop it, then run migrate-db again. "A newer ByteBench" means the file was last used by a newer version: run migrate-db from that version.
  • "The target database already contains ByteBench data": use an empty database, or add --force to empty ByteBench's tables in it first (other tables are left alone).
  • "row(s) reference a missing row": the SQLite file has orphaned rows (usually from an old crash or manual edit). PostgreSQL enforces the foreign key, so fix or delete them in a copy of the file and run again.
  • "contains a NUL character": PostgreSQL text cannot hold \u0000. The message names the table, column and row; clean that value in the SQLite file.
  • "Cannot prepare the target database": the connection string, the network or the role is wrong (host, port, password, CREATE DATABASE for a database that does not exist yet). The password is never printed.
  • Verification MISMATCH: the table and counts are printed and the exit code is 1. The copy was committed, but do not switch to it: run again with --force --verify and, if it repeats, keep the SQLite file and report the table.
  • Encrypted secrets say "unreadable: rotate it" after the move: the new start is not using the old Data Protection key ring. Point DataProtection:KeysPath at the original folder.
  • A run that fails part-way leaves no rows behind (the copy is one transaction); the empty schema stays and can be reused.

Git over SSH

"The SSH server could not listen on port 2222"

Cause: something else (often another ByteBench run or a local sshd) holds the port, or the process may not bind it. ByteBench logs the error and carries on without SSH; HTTP still works.

Fix: stop the other process or choose a port with Ssh__Port=2223, or turn SSH off with Ssh__Enabled=false. In Docker, map the host port you want ("2223:2222") and set Ssh__PublicPort so clone URLs show it.

Clone fails: permission denied (publickey)

Add your public key under /account/ssh-keys (ed25519, ECDSA or RSA 2048+; FIDO sk- keys are not supported). A key can be registered only once on the whole site, expired keys stop working, and so do keys of deactivated accounts. Test with ssh -p 2222 git@localhost; you should be greeted by name.

If the host key changes (a new /data/keys volume) every client warns. Back the host key up with the key ring.

OpenSSH prints a "post-quantum key exchange" warning

Harmless: the server offers ECDH and DH key exchange only. Silence it per host with WarnWeakCrypto no-pq-kex in ~/.ssh/config.

CI and Docker

Pipelines end in Error: "Docker is not available on the server"

Cause: the docker CLI that ByteBench runs cannot reach a daemon. In the official image there is no daemon and no CLI, and Ci__Enabled is false. When CI is on, /health/ready reports Degraded and the log says "Docker is not available".

Fix: run docker version as the same user as ByteBench. For the container, choose one of the three options in CI in the container (mounted socket plus WITH_DOCKER_CLI, run on the host, or a remote DOCKER_HOST). Also check Ci:DockerExecutable and that Ci:WorkDirectory exists at the same path on the host.

Pipelines stay Queued, or jobs are killed

Only Ci:MaxConcurrentJobs (default 2) jobs run at once across all pipelines, and a job is killed after Ci:JobTimeoutMinutes (20). Out-of-memory kills come from Ci:Memory (2g). Raise them if the host has capacity. Pipelines that were running when the server stopped are marked Error; queued ones run again.

A pipeline is in Error with a YAML message

The file .bytebench-ci.yml is validated strictly: unknown keys, a step without run, unknown or circular needs and invalid image names are errors with a line and column. Limits: 20 jobs, 50 steps per job, 64 KB per file. See CI pipelines.

Email

Email is not sending

Work through the list:

  1. Email:Enabled is false by default. While off, nothing is queued, and turning it on later does not send a backlog.
  2. Email:Sender: in Development the default is Pickup, which only writes .eml files to mail-drop/. Set Email__Sender=Smtp for real delivery.
  3. Check Email__Smtp__Host, port, UseStartTls and credentials. Port 587 uses STARTTLS; with UseStartTls=false port 465 is implicit TLS and other ports are clear text.
  4. Failed sends are retried three times (after 2 s, 10 s and 30 s), then logged and dropped. Look for the error in the log; addresses are masked (b***@example.com).
  5. The recipient's notification preferences may have email off for that kind of event, or Email:DigestMinutes may be batching mail.
  6. Links in mail point to the wrong host? Set PublicBaseUrl or Email:BaseUrl.

See Notifications and email.

The password reset or confirmation email does not arrive

The page always says "a link is on its way", by design, so it cannot tell you whether anything was sent. Check in this order:

  1. Everything under Email is not sending: Email:Enabled must be true and the sender must deliver. In Development the Pickup sender writes the message to mail-drop/ instead.
  2. The address must belong to an account with a ByteBench password that is not deactivated, locked by an admin or a system account. SSO and LDAP accounts get no reset email. The audit log shows auth.password_reset_requested when a link was queued.
  3. You may have hit the limits: 3 emails per account and 10 requests per IP in 15 minutes. Wait and try once.
  4. The link in the mail is wrong or opens on the wrong host: set PublicBaseUrl or Email:BaseUrl.
  5. Links are single-use and expire (60 minutes for reset, 48 hours for confirmation by default). Ask for a new one.
  6. Cannot get email working? A site admin can set a temporary password or mark the address confirmed on /admin/users.
  7. Users blocked after switching on Account:RequireEmailConfirmation see "Confirm your email address before signing in": they use /account/resend-confirmation, or an admin marks the address confirmed.

Rate limits (429)

Requests over a limit get 429 with Retry-After (problem+json for the API, plain text elsewhere). Defaults per 60 seconds: sign-in POSTs 10, API 300, Git over HTTP 120, Git over SSH 120, package and image registry 3000 per credential and 6000 per IP, webhook test pings 5. In Development rate limiting is off.

Causes you will actually meet: many users behind one NAT or an unconfigured proxy (everyone shares one IP bucket; fix the forwarded headers first), a CI farm pulling and pushing images, or a script polling the API. Raise a limit with RateLimiting__Api__PermitLimit=600, or set a PermitLimit of 0 to switch one off. Over SSH, git prints "Too many requests. Try again in N seconds."

Git, LFS and repositories

Clone and push answer 503

The server runs git http-backend, so git must be on the server's PATH (the Docker image has it) or set via Git:Executable. The error is logged at start-up.

"Repository not found" for a repository that exists

That is deliberate: if you cannot view the project, git sees 404, the same as for a missing repository. Check your role and the project's visibility. A Viewer who pushes gets 403.

git LFS is missing

Two different things. On your machine, git-lfs must be installed (git lfs install) to push or pull LFS files; without it you get small pointer files instead of the content. On the server, ByteBench implements the LFS Batch API itself and does not need git-lfs installed. Notes: objects over Lfs:MaxObjectBytes (2 GB) get 413; the locks API is not implemented, so git-lfs prints a one-time warning (silence it with git config lfs.<url>.locksverify false); and with an SSH remote you must set lfs.url to the HTTPS LFS URL, because git-lfs-authenticate over SSH is not implemented. Full reference: Git LFS and mirroring.

A push is rejected with "remote rejected"

Branch protection, protected tags, an archived repository or a pull mirror. The message after ( names the reason. Force pushes to protected branches are refused by the pre-receive hook.

AI features do not appear

All AI features hide themselves unless Ai:Enabled is true and a key exists (ANTHROPIC_API_KEY or Ai:ApiKey), or, for the web editor and AI review, Claude Code is installed for the server's account. The site admin page /admin/ai shows what was detected and has a Check again button. See AI overview and setup.

Merge queue, deployments, service desk and chat

A pull request sits in the merge queue and nothing happens

Check, in order: the queue page (/p/{KEY}/repos/{slug}/merge-queue) for the entry's state and message; that MergeQueue:Enabled is not false; that the repository has a CI file with at least one job that runs on the target branch (queue pipelines pick jobs as if they ran on it) while "Require CI" is on; and whether the queue pipeline is waiting on a manual job (the entry says "Waiting for approval"). See the merge queue.

A deployment job never starts

On a protected environment it waits for approvals. Look at "Waiting for approval" on the project Environments page, check how many approvals the rule needs and who may approve, and whether a deploy freeze is active.

An email to the service desk created no issue

Read the audit log (service_desk.mail_ignored and service_desk.mail_rejected record the reason, sender and subject). Usual causes: the project's desk is off, the address has no +KEY tag, an auto-reply or bulk header made it look automated, or IMAP polling is off. See Service desk.

Slack or Teams messages do not arrive, or /bytebench fails

Press Send test message on the integration and read its delivery log. An integration switched off after 20 failures needs Active ticked again. For the slash command the signing secret must be set and your server clock accurate. See Slack and Microsoft Teams.

Known limits and what was only tested with fakes

ByteBench has a large automated test suite, but a test suite is not the same as years of production use. These are the places where the honest answer is "tested against a stand-in, not the real thing":

AreaWhat was testedWhat was not
Slack and Microsoft TeamsMessage formatting, signature checks, slash commands, link previews and delivery against a fake HTTP handlerNo live calls to Slack or Teams. Your first real workspace is the first real test, including Slack app scopes and Teams Workflows URLs
Service desk email (IMAP)Intake, spam rules, replies and the signed inbound webhook, with a fake email senderI found no automated test that talks to a real IMAP server. Try it against a test mailbox before pointing it at a real one
Email (SMTP)Composition, queue and retries; pickup filesDelivery through a real SMTP provider
Anthropic API and Claude CodeAI review, triage and the web editor against fake models; the Claude Code backend against a fake claude scriptThe real API and the real Claude Code CLI are never called by the tests. Output quality, cost and rate limits are unknown until you run it
Night Owl scansParsing and ingesting Night Owl JSON and SARIF fixture reports, triage, pull request checksA real Night Owl scan running inside a ByteBench CI job (including the install step and engine images) was not exercised end to end
Single sign-onA built-in mock OIDC provider with GitHub-style endpointsReal Google, GitHub, Entra or Keycloak tenants
LDAPAn in-memory fake directory that evaluates filters; a Docker test against an OpenLDAP container (skipped without Docker)Real Active Directory
CI on DockerA pipeline test runs real containers when a daemon exists (skipped otherwise); GitHub Actions excludes itRemote Docker hosts, rootless Docker and large parallel loads
PostgreSQLThe suite passes against PostgreSQL 17; backup round trip was checked by handFailover, replicas, load, and any data migration from SQLite (there is none)
ScaleSingle-instance behaviourSeveral replicas (not supported), very large repositories and thousands of concurrent users

Not implemented or partial

  • Git LFS: no locks API and no git-lfs-authenticate over SSH.
  • SSH: FIDO (sk-...) keys are not supported; the server offers no shell, no sftp and no forwarding, only git-upload-pack and git-receive-pack; it is not a post-quantum key exchange.
  • Git over HTTP: protocol v2 works, the legacy "dumb" protocol does not.
  • Single instance only, SQLite or PostgreSQL, no clustering.
