Security scanning

Run Night Owl (or any SARIF tool) in a CI job and ByteBench turns its report into findings you can triage, track over time and use as a pull request check.

What Night Owl is

Night Owl is a separate open-source scanner: github.com/finepointcgi/Night-Owl, with documentation at finepointcgi.github.io/Night-Owl. It covers dependency vulnerabilities (SCA), licenses, static analysis (SAST), secrets, infrastructure-as-code, container images and code quality, by driving engines such as syft, osv-scanner, gitleaks, opengrep, trivy and lizard.

ByteBench does not bundle or run Night Owl itself. It integrates through Night Owl's command line and report formats only: a CI job runs nightowl scan, writes a JSON report (and SARIF), and ByteBench reads those files after the job. Reports from other tools work too if they produce SARIF 2.1.

Quick start

include: [nightowl]
jobs:
  build:
    steps: [ { run: ./build.sh } ]

With include: [nightowl] ByteBench adds a built-in job named nightowl (see include). It installs the Night Owl release using Night Owl's checksum-verifying install.sh and runs:

nightowl scan "${NIGHTOWL_PATH:-.}" [--fail-on $NIGHTOWL_FAIL_ON] --no-update \
  --format json --output nightowl.json --sarif-output nightowl.sarif --summary-output nightowl.md ${NIGHTOWL_ARGS:-}
The stock template alone will not scan. Night Owl runs its engines from local binaries or pinned container images, and ByteBench jobs never get a Docker daemon. On the default alpine image the job stops immediately with "This image has no scan engines" (exit 2) instead of failing deep inside the scan. To scan for real you need a runner image that has the nightowl CLI and its engines on PATH (next section).

The runner image requirement

  1. Build an image once that contains the nightowl CLI and the engines you want (syft, osv-scanner, gitleaks, opengrep, trivy, lizard; see engines/ in the Night Owl repository for how each is pinned). Run nightowl update at build time to bake in rule and advisory data.
  2. Push it to a registry. The project's own container registry works.
  3. Override the template job with your image. The template skips its install step when nightowl is already on PATH, so the override is the template's script with one changed line:
include: [nightowl]          # optional once you define the job yourself
jobs:
  nightowl:                  # same name: replaces the template job
    image: bytebench.example.com/sec/nightowl-runner:1.0
    artifacts:
      when: always
      paths: [nightowl.md]
      reports: { nightowl: nightowl.json, sarif: nightowl.sarif }
    steps:
      - name: Night Owl scan
        run: nightowl scan . --no-update --format json --output nightowl.json --sarif-output nightowl.sarif --summary-output nightowl.md

Without the install step the job needs no network, so it also works with Ci:Network: none. A failing quality gate makes the scan exit 1 and the job fail, but the report is still read because artifacts are collected when: always. Repository Settings → Security shows the template's YAML to copy.

NIGHTOWL_* variables

Set these as CI variables (repository or project) to tune the built-in job. They are plain environment variables read by its script, so they do nothing in a job you wrote yourself unless you use them.

VariableEffect
NIGHTOWL_FAIL_ONcritical, high, medium, low or none: fail the job at that severity. Empty means use .nightowl/policy.yml from the repository.
NIGHTOWL_PATHWhat to scan. Default . (the whole workspace).
NIGHTOWL_ARGSExtra nightowl scan options, e.g. --engines opengrep,gitleaks.
NIGHTOWL_VERSIONRelease to install (passed through to Night Owl's installer environment).
NIGHTOWL_REPOWhere to fetch the installer from. Default finepointcgi/Night-Owl.

Report artifacts

Any job can publish reports, not just nightowl:

jobs:
  sast:
    image: registry.example.com/ci/semgrep:latest
    artifacts:
      when: always
      reports:
        sarif: results.sarif        # nightowl: and sarif: are the supported types
    steps:
      - run: semgrep scan --sarif --output results.sarif
  • Report types: nightowl (Night Owl's JSON) and sarif (SARIF 2.1). Each names one file, with no wildcards. The files are added to the job's artifact paths automatically.
  • After the job runs, passed or failed, the runner reads each file from the workspace (never through a symlink, at most 32 MB), and the job log says what was read or why it wasn't.
  • If a job provides both, the Night Owl JSON is used (it has packages, fixed versions, path context and its own triage); the SARIF from that job is kept only as an artifact.
  • Each scan is tied to the pipeline, job, branch and commit.

How findings are read

Each finding keeps Night Owl's fingerprint (its finding id, or partialFingerprints["nightowl/v1"] in its SARIF), a severity (critical, high, medium, low, info), a category (SCA dependency, license, SAST, secret, IaC, container, DAST, quality), the rule or advisory id, aliases (CVE/GHSA), the package, version and fixed versions, file and line, the message, the engines that reported it and the path context. For SARIF from other tools the first partial fingerprint is used, else one derived from rule, path, snippet or line; severity comes from security-severity (CVSS bands) or the SARIF level. Duplicates with the same fingerprint merge, keeping the highest severity and every engine.

The Security tab

Open Repository → Security: /p/{KEY}/repos/{slug}/security (Viewer or higher). It shows the latest scanned pipeline of the default branch (use the branch picker or ?branch=):

  • Open counts by severity and a trend chart of open findings per scan.
  • Filters: status (open, dismissed, all), minimum severity, category and free text.
  • ?finding={fingerprint} opens a finding: description, package and fix versions, location (linked to the source at the scanned commit), aliases, engines, where it was first and last seen, and its triage history.
  • If NightOwl:DashboardUrl is set, a link to your Night Owl dashboard appears on the Security pages.

Triage

Developers and above (PushCode) can decide what a finding means. Decisions are keyed by fingerprint per repository, so they carry across scans and branches.

StateCounts as open?Notes
New (no decision)YesReopening a finding removes its decision.
ConfirmedYesA real problem someone owns.
False positiveNoA reason is required. Optional expiry.
Accepted riskNoA reason is required. Optional expiry.
FixedNoAvailable through the API and imported files.
  • Expiry: a decision with an expiry date (must be in the future when set) stops applying after it; the finding becomes open again automatically. Use this for "accepted until the next upgrade".
  • Only open findings count in the trend, the pull request comparison, the merge check and alerts. This matches Night Owl's own quality gate.
  • A decision carried by the report itself (from the repository's .nightowl/triage.json at scan time) applies too; ByteBench's own decision wins over it.

triage.json import and export

Night Owl keeps shared decisions in .nightowl/triage.json. ByteBench reads and writes the same format:

[
  { "findingId": "3f2a9c...", "state": "accepted-risk", "reason": "Not reachable in our build",
    "by": "alice", "at": "2026-11-01T10:00:00+00:00", "expires": "2027-01-01T00:00:00+00:00",
    "title": "lodash prototype pollution" }
]
  • Export triage (Security tab) downloads ByteBench's decisions in this shape. Commit the file to the repository so nightowl scan in CI, and developers running it locally, see the same decisions.
  • Import triage (Maintainer or higher) reads the file from the default branch, or a pasted one. Each decision replaces ByteBench's decision for that fingerprint; "new" removes it. States are false-positive, accepted-risk, confirmed, fixed or new; every decision needs a findingId of at most 64 characters, and a bad file is rejected whole.

Pull requests and the merge check

A pull request has a Security tab comparing the head commit's latest scan with the target branch's latest scan: new open findings the PR adds and fixed ones it removes, plus the unchanged count. If the head hasn't been scanned yet it says the scan is pending.

In Repository → Settings → Security (/p/{KEY}/repos/{slug}/settings/security, Maintainer or higher) turn on the Security merge check and choose a severity (default high):

ResultWhen
FailedThe PR adds open findings at or above the threshold ("2 new findings at or above high").
PassedNo new findings at or above it (it also reports how many new ones are below, and how many are fixed).
PendingA pipeline for the head is still running.
NeutralThe head has no security report (add include: [nightowl]).

The check only blocks merging if branch protection has "require checks to pass" on the target branch, like every other merge check.

Alerts and the webhook

When a scan of the default branch has open findings at or above the repository's alert severity (Settings → Security, default high) that the previous scan didn't have, ByteBench:

  • notifies the project's Maintainers and Owners, and whoever triggered the pipeline (notification kind "security findings", in the Pipelines preference group, see Notifications);
  • sends the security.new_findings webhook to hooks subscribed to it.
{
  "event": "security.new_findings",
  "repository": { "id": 3, "slug": "web-app", "name": "Web App", "defaultBranch": "main" },
  "pipeline": { "id": 118, "ref": "main", "commitSha": "9f2c1e0...", "url": "https://bytebench.example.com/p/WEB/repos/web-app/pipelines/118" },
  "threshold": "high",
  "findings": [ { "fingerprint": "3f2a9c...", "severity": "critical", "category": "sca", "ruleId": "GHSA-xxxx",
                  "title": "lodash prototype pollution",
                  "package": { "name": "lodash", "version": "4.17.20", "fixedVersions": "4.17.21" },
                  "file": "package-lock.json", "line": null, "url": "https://bytebench.example.com/p/WEB/repos/web-app/security?finding=3f2a9c..." } ],
  "total": 1,
  "url": "https://bytebench.example.com/p/WEB/repos/web-app/security"
}

At most 100 findings are listed; total is the full count. The usual envelope fields (delivery id, timestamp, project, sender) are added; see REST API and webhooks.

Outdated dependencies and the dependency bot

Night Owl reports tell you which dependencies are vulnerable; the dependency bot (Settings, Dependencies) opens pull requests that bump them. When the default branch's latest scan has an open dependency finding for a package at its current version, the bot's "Outdated dependencies" table and the pull request description add a security note listing the advisory ids and whether the proposed version is one of the finding's fixed versions. Findings that triage has dismissed (false positive, accepted risk, fixed) are not mentioned, and with no scan the note is simply absent. Because the bot only edits manifests and never regenerates lockfiles, the next scan on the pull request runs against the updated manifest and the merge check above applies as usual.

Complete example: scan on every push, gate pull requests

include: [nightowl]
on:
  branches: [main]
  pull_requests: true
jobs:
  nightowl:
    image: bytebench.example.com/sec/nightowl-runner:1.0
    artifacts:
      when: always
      paths: [nightowl.md]
      reports: { nightowl: nightowl.json, sarif: nightowl.sarif }
    steps:
      - name: Night Owl scan
        run: nightowl scan . --no-update --fail-on high --format json --output nightowl.json --sarif-output nightowl.sarif --summary-output nightowl.md

Then in Settings → Security enable the merge check at high, and add a nightly schedule on main so new advisories against old dependencies still produce alerts when nobody pushes. Related: CI pipelines, Branch protection.
