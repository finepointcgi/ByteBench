Feature flags

Ship code switched off, turn it on per environment, target it at specific users or a percentage of them, and change it without redeploying.

Concepts

TermMeaning
FlagA named switch owned by a project (not a repository), with a stable key such as new-checkout, a type and an off value.
EnvironmentA place flags have their own state: production, staging, and so on. The same flag can be on in staging and off in production.
StateA flag's setting in one environment: on or off, the default value served when on, and an ordered list of targeting rules.
Rule"If these conditions match (and the user falls in this percentage), serve this value."
SegmentA named list of user ids that rules can target.
SDK keyA read-only credential, per environment, that your application uses to ask ByteBench what value a flag has for a given user.
ContextWho you are evaluating for: a userId plus string attributes such as plan=pro.

Find them at Feature flags in a project's sidebar, /p/{KEY}/flags; a single flag is at /p/{KEY}/flags/{flagKey}. Everyone who can view the project can read flags.

How a value is chosen

  1. If the flag is off in the environment: serve the flag's off value (reason off).
  2. Otherwise check the environment's rules in order; the first matching rule serves its own value (reason rule).
  3. If no rule matches: serve the environment's default value (reason default).
  4. An archived flag always serves its off value (reason archived).

Creating a flag

  1. On the Flags page (Maintainer or higher) choose to create a flag: a key (lowercase letters, digits, ., _, -, up to 64, starting with a letter or digit; it can't change later because code refers to it), a name (up to 120), an optional description (up to 2000), a type, and the value to serve when on.
  2. The flag starts off in every environment. Toggle it in an environment when you're ready (Developer or higher).
  3. Optionally link it to issues of the project, so people can see which work the flag belongs to.

Every value (off value, default value, rule values) is checked against the flag's type and must be at most 4000 characters.

Environments and the CI sync

Flag environments are listed from a mix of two sources: those a Maintainer adds on the Flags page, and the names of your CI environments. Whenever you open the Flags page (or call the API), any environment: name used by the project's pipelines that doesn't exist yet is added automatically, with every flag off in it. So if your pipeline deploys to production and staging, those environments already exist for flags, using the same names.

  • A new environment starts every flag off and copies the default value the flag was created with.
  • Deleting an environment removes its flag states and SDK keys (Maintainer or higher). It does not remove the CI environment.
  • The sync only adds; it never deletes or renames. Names are limited to 64 characters.

Targeting rules

A rule has any number of conditions (clauses), an optional percentage and a value. It matches when all conditions match (a rule with no conditions matches everyone) and, if a percentage is set, the user falls inside it. Up to 50 rules per flag per environment, 20 conditions per rule, 500 values per condition.

Operators

OperatorMatches when
equalsThe attribute equals the (first) value. Case-insensitive.
notEqualsThe attribute is missing or differs from the value.
inThe attribute equals any listed value.
notInThe attribute is missing or equals none of the values.
containsThe attribute contains any listed text.
startsWithThe attribute starts with any listed text.
endsWithThe attribute ends with any listed text.
inSegmentThe context's userId is in any of the listed segments (values are segment keys; no attribute).
notInSegmentThe user id is in none of them.

All comparisons are case-insensitive and attributes are always strings: there are no numeric greater-than comparisons or regular expressions. Positive operators (equals, in, contains, ...) don't match when the attribute is missing; negative ones (notEquals, notIn) do. The attribute name userId (also key and user) means the context's user id; anything else is looked up in the attributes.

Percentage rollouts and stability

Set percentage (0 to 100, two decimals honoured) on a rule to serve it to only part of the users who match its conditions. Each user is put in a fixed "bucket" from 0 to 9999 by hashing flagKey:ruleId:bucketValue with SHA-256, and is in if the bucket is below percentage x 100. That gives these guarantees:

  • Stable: the same user always gets the same answer for the same rule.
  • Only adds: raising 10% to 25% keeps the original 10% in and adds more users, so nobody flips back and forth during a rollout.
  • Independent per rule and flag: users in the first 10% of one flag aren't automatically in the first 10% of another.
  • Keep the rule id. Changing a rule's id or the bucket-by attribute reshuffles who is included. The id is generated for you; edit it only deliberately.
  • The default bucket attribute is userId. Use bucketBy to roll out per another attribute, for example an account id so everyone in the same company gets the same answer.
  • A context with no value for the bucket attribute (an anonymous request) never matches a percentage rule.

Hash definition, so you can evaluate locally: SHA-256 of the UTF-8 text flagKey:ruleId:bucketValue, first 8 bytes read as an unsigned little-endian integer, modulo 10000; the user is in when that is less than round(percentage x 100).

Example

For new-checkout in production: serve true to the beta segment, 20% of everyone on the pro plan, and the default (false) to the rest:

curl -X PUT https://bytebench.example.com/api/v1/projects/WEB/flags/new-checkout/environments/2 \
  -H "Authorization: Bearer $BYTEBENCH_TOKEN" -H "Content-Type: application/json" \
  -d '{
    "enabled": true,
    "defaultValue": false,
    "rules": [
      { "id": "beta", "description": "Beta testers",
        "clauses": [ { "op": "inSegment", "values": ["beta-testers"] } ], "value": true },
      { "id": "pro-20", "description": "20% of pro",
        "clauses": [ { "attribute": "plan", "op": "equals", "values": ["pro"] } ],
        "percentage": 20, "value": true }
    ]
  }'

Segments

A segment is a named list of user ids (strings, up to 200 characters each, up to 10,000 members): your beta testers, internal staff, a customer. Create one in the Segments section of the Flags page: a key, a name and the ids (one per line or comma separated). Reference it from a rule with inSegment or notInSegment. Editing needs Developer; deleting needs Maintainer and is refused while a rule uses it. Segments match only the context's userId, not other attributes.

SDK keys

Create keys on the Flags page under Environments and SDK keys (Maintainer or higher): pick the environment, a name and a kind. The secret (gbsdk_c_... or gbsdk_s_...) is shown once; only a hash is stored. Keys can be rotated (the old secret stops working at once) and revoked. At most 20 active keys per environment. The list shows when each was last used.

KindCan doUse it in
Client (gbsdk_c_)Evaluate flags and get their values. Can't see rules. May be sent as ?sdkKey= (needed for browser EventSource, which can't set headers).Browsers, mobile apps. It reveals only the values flags currently serve, but treat it as semi-public: don't put secrets in flag values.
Server (gbsdk_s_)Everything a client key does, plus download definitions (rules and segments) for local evaluation, and the matching ruleId in results. Refused if sent in the URL.Your backend only. Keep it secret.
The client API accepts only SDK keys, never personal access tokens or browser sessions, and answers with Access-Control-Allow-Origin: * and no credentials. Evaluating happens on the ByteBench server, so rules of a client key are never sent to the browser.

Evaluation endpoints

All under /api/v1/flags. Send the key as Authorization: Bearer gbsdk_... or the X-ByteBench-SDK-Key header. The context comes from query parameters (user=ID or userId=ID and attr.NAME=value) or a JSON body { "userId": "...", "attributes": { "plan": "pro" } }. A context may have up to 50 attributes, values up to 500 characters.

EndpointPurposeKey
GET /evaluate?flag=KEY&user=ID&attr.plan=pro
POST /evaluate (body adds "flag")		One flag. 404 if the environment has no such flag.client or server

With curl

# one flag for user 42 on the pro plan
curl -s "https://bytebench.example.com/api/v1/flags/evaluate?flag=new-checkout&user=42&attr.plan=pro" \
  -H "Authorization: Bearer $BYTEBENCH_SDK_KEY"
# {"key":"new-checkout","type":"boolean","value":true,"reason":"rule","ruleId":null,"version":17}

# everything, with a JSON context
curl -s -X POST https://bytebench.example.com/api/v1/flags/evaluate-all \
  -H "Authorization: Bearer $BYTEBENCH_SDK_KEY" -H "Content-Type: application/json" \
  -d '{"userId":"42","attributes":{"plan":"pro","country":"DE"}}'
# {"version":17,"environment":"production","flags":{"new-checkout":{"key":"new-checkout","type":"boolean","value":true,"reason":"rule"}, ...}}

ruleId is included (and non-null) only for server keys. reason is off, rule, default or archived.

ETags and polling

Every evaluate and definitions response carries a strong ETag and Cache-Control: private, no-cache. Send the ETag back as If-None-Match; while nothing that affects the answer has changed you get 304 Not Modified with no body. That makes polling cheap:

curl -i "https://bytebench.example.com/api/v1/flags/evaluate-all?user=42" \
  -H "Authorization: Bearer $BYTEBENCH_SDK_KEY" -H 'If-None-Match: "3f9a0c..."'

The version in the body is the environment's change counter; it goes up whenever a flag, rule, segment or value that decides evaluation here changes.

Live updates (stream)

GET /stream keeps the connection open and sends an event: flags message first, then another each time the evaluated result for that context changes, with a 20-second keep-alive comment. The connection ends if the key is revoked or rotated. Clients should reconnect on error (the server suggests retry: 3000). A single server holds at most 1000 open streams (extra ones get 503).

Definitions (local evaluation)

A server key can fetch GET /definitions: each flag's type, enabled, offValue, defaultValue and rules, plus all segments (key to member ids) and a hashing note. Use it to evaluate in-process without a network call per check, re-fetching with If-None-Match. Follow the evaluation order and hashing above exactly to get identical answers.

C# example

using System.Net.Http.Headers;
using System.Text;
using System.Text.Json;

public sealed class FlagClient(HttpClient http)
{
    // new HttpClient { BaseAddress = new("https://bytebench.example.com/") }
    // with DefaultRequestHeaders.Authorization = new("Bearer", sdkKey)

    public async Task<bool> IsOnAsync(string flag, string userId, string plan)
    {
        var url = $"api/v1/flags/evaluate?flag={Uri.EscapeDataString(flag)}&user={Uri.EscapeDataString(userId)}&attr.plan={Uri.EscapeDataString(plan)}";
        using var res = await http.GetAsync(url);
        if (!res.IsSuccessStatusCode) return false;   // fail closed: treat errors as "off"
        using var doc = JsonDocument.Parse(await res.Content.ReadAsStringAsync());
        return doc.RootElement.GetProperty("value").GetBoolean();
    }
}

// usage
if (await flags.IsOnAsync("new-checkout", user.Id, user.Plan)) { /* new path */ }

Cache results briefly in your application (or use If-None-Match) rather than calling on every request, and always choose a safe fallback for when the call fails.

JavaScript example

// Browser, with a CLIENT key
const base = "https://bytebench.example.com/api/v1/flags";
const sdkKey = "gbsdk_c_...";            // client key only: never ship a server key to a browser
const ctx = new URLSearchParams({ user: "42", "attr.plan": "pro" });

// one-off
const res = await fetch(`${base}/evaluate-all?${ctx}`, { headers: { Authorization: `Bearer ${sdkKey}` } });
const { flags } = await res.json();
if (flags["new-checkout"]?.value) showNewCheckout();

// live updates: EventSource can't set headers, so a client key goes in the query
const es = new EventSource(`${base}/stream?${ctx}&sdkKey=${sdkKey}`);
es.addEventListener("flags", (e) => {
  const { flags } = JSON.parse(e.data);
  render(flags["new-checkout"]?.value === true);
});
// Node, with a SERVER key and cheap polling via ETag
let etag = null, flags = {};
async function refresh() {
  const res = await fetch("https://bytebench.example.com/api/v1/flags/evaluate-all?user=42", {
    headers: { Authorization: `Bearer ${process.env.BYTEBENCH_SDK_KEY}`, ...(etag ? { "If-None-Match": etag } : {}) },
  });
  if (res.status === 304) return flags;
  etag = res.headers.get("ETag");
  flags = (await res.json()).flags;
  return flags;
}

Stale flags

Old flags are clutter and risk. ByteBench tracks when each flag last changed and when an SDK last evaluated it (recorded at most about once an hour per flag and environment). A flag that has neither changed nor been evaluated for the chosen number of days (default 30, adjustable with "Stale after (days)" on the page) is marked stale. Clean up by removing the flag from code, then archive it (kept, but always serves its off value and can't be edited until restored) or delete it. Via API: GET /api/v1/projects/{key}/flags/_stale?days=45.

History and audit

Every change is written to the flag's history (who, when, old and new value, which environment): created, toggled, default value, off value, rules, details, issues, archived, unarchived. See it on the flag's page or with GET /api/v1/projects/{key}/flags/{flagKey}/history. The same changes are in the project audit log (flag.created, flag.toggled, flag.rules_changed, flag.default_changed, flag.off_value_changed, flag.updated, flag.archived, flag.unarchived, flag.deleted, plus flag.environment_created, flag.environment_deleted, flag.sdk_key_created, flag.segment_created, flag.segment_updated, flag.segment_deleted and key rotation and revocation events). Deleting a flag removes its history, but the audit log keeps the record.

Webhook: flag.changed

Subscribe a webhook to flag.changed to learn when a flag is created, toggled, edited, archived or deleted (for example to post to chat or invalidate a cache).

{
  "event": "flag.changed",
  "flag": { "id": 5, "key": "new-checkout", "name": "New checkout", "type": "boolean", "archived": false },
  "environment": { "id": 2, "name": "production" },
  "change": { "kind": "toggled", "oldValue": "off", "newValue": "on" },
  "url": "https://bytebench.example.com/p/WEB/flags/new-checkout"
}

environment is null for changes that aren't per environment (details, off value, archive). kind is one of created, toggled, default_value, off_value, rules, details, issues, archived, unarchived. Values are clipped to 2000 characters.
