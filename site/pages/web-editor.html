Web editor and AI assistant

A VS Code-style editor in your browser, built on Monaco, with per-branch workspaces, a diff and commit flow, and an optional AI assistant that proposes edits you accept or reject.

Opening the editor

The editor lives at /p/{KEY}/repos/{slug}/edit/{branch}/{path}. The branch is one URL segment, so feature/x is written feature%2Fx. You normally get there with the Open in editor button:

  • on a repository's Source page (opens the current branch and, if you are viewing a file, that file), or
  • on a pull request (opens its source branch; for a fork PR, the branch in the fork).

Anyone who can view the project can open it. Editing and committing need the Developer role (PushCode). Viewers, archived repositories and pull mirrors get read-only mode: you can browse, search and chat with the assistant, but not edit, accept proposals or commit.

Layout

  • Activity bar on the left: Explorer, Find in files, Source control.
  • Explorer: the file tree, loaded one folder at a time from the branch with your working changes laid over it (A, M and R markers; deleted files disappear). Each row's menu has New file, Rename or move and Delete.
  • Tabs across the top for open files, and the Monaco editor with language detection from the file name and extension.
  • Status bar: branch, read-only state, number of changes, the AI backend, language, and line and column.
  • Assistant docked on the right.
  • Large and binary files (over 1 MB, or binary) open as a read-only message and cannot be edited, renamed or sent to the assistant.

Find in files runs git grep at the workspace's base commit for unchanged files, plus your working copies of changed files (same engine as code search).

Workspaces per branch

Your edits are saved automatically (about 0.7 seconds after you stop typing, or with Ctrl/Cmd+S) into a workspace that is private to you and specific to one branch of one repository. A workspace stores added, modified, deleted and renamed files against a base commit, in the database. It survives reloads and restarts, and nobody else sees it. Saving a file back to exactly its base content drops that change. Nothing reaches the repository until you commit.

Diff and commit

  1. Open Source control. It lists your changes.
  2. Click a change to see Monaco's side-by-side diff against the base. Discard a change to undo it (a rename is undone and the original comes back).
  3. Type a commit message. Then either:
    • Commit to {branch} writes one commit authored by you, or
    • Commit to new branch & open PR creates a new branch from the base, commits there and opens a pull request into the current branch. This is the way in when the branch is protected.

Committing follows the same rules as git push: it needs PushCode, is refused on archived repositories and pull mirrors, and honours branch protection (a branch with "block direct pushes" refuses the commit and the editor offers the new-branch flow; creating the new branch is checked too). Only refs/heads/... is written, so protected tags are never touched. After a commit, push listeners run exactly as after a git push: CI pipelines, webhooks, smart commits, automation, stale-approval dismissal, AI review and mirroring. Commits are audited as editor.commit.

When the branch moved under you

If someone pushed after your base commit, files only they changed do not matter: you can still commit, on top of their work. If they changed files you also changed, use Update workspace (rebase). GitBench merges each file three-way. Files that conflict are listed with a diff of the branch's version against yours; choose Keep mine or Take theirs for each.

The AI assistant

The chat panel talks to Claude about the open branch. It knows the open file and your selection (toggle Open file & selection), and you can attach files by typing @path in the message or with Attach a file. It streams its reply and shows each tool it uses.

  • Tools (API backend): list_files, read_file, search_code (git grep at the workspace state) and propose_edit (full new content, a find-and-replace hunk, or delete). They see only your workspace: this repository and branch plus your uncommitted changes. Paths are validated (no .., absolute paths or .git).
  • If no backend is configured the panel says "AI isn't set up" and the AI menus are hidden. The editor itself works normally.

Inline actions

The AI actions menu above the editor (or the command palette) runs a ready-made prompt on your selection, or the whole file if nothing is selected:

ActionWhat it does
ExplainExplains what the code does, in the chat
Refactor...Asks how you want it changed, then proposes the edit
Add commentsProposes explanatory comments
Write testsProposes tests (typically in a new file)
FixProposes a fix for a bug or problem in the selection

They run through the same assistant, so changes come back as proposals.

Proposals: accept or reject

Edits are never applied silently. Each proposed change appears in the chat as a card with Diff, Accept and Reject (plus Accept all and Reject all). Accepting puts the change into your workspace as an ordinary working change; it is still not committed, so you can review it in Source control. Accepting is refused if the file changed since the proposal was made. Accepting needs PushCode.

Ghost-text completions

Monaco inline completions are off by default. Turn them on for the session with the Ghost text button in the status bar or the command palette. Requests are debounced (sent when you pause typing, with up to 6 KB of text before and 2 KB after the cursor) and rate limited. They work only with the API backend; with Claude Code the toggle is hidden because the CLI is too slow for them. Each completion is a small paid request, which is why they are off by default.

Backends: Api, ClaudeCode or Auto

Ai:Editor:Backend chooses the engine that answers the assistant:

ValueMeaning
ApiGitBench calls the Anthropic API itself with a tool-use loop, using the model in Ai:Model and the key from ANTHROPIC_API_KEY or Ai:ApiKey
ClaudeCodeGitBench runs the claude command-line tool installed on the server, headless, in a sandboxed temporary folder
Auto (default)Claude Code if it is installed on the server, else the API if a key is configured, else AI is off

Setting up keys and the overall AI features is covered in AI overview and setup.

How Claude Code mode is sandboxed

  1. Your workspace (the base commit plus your changes: text files up to 1 MB, at most Ai:ClaudeCode:MaxFiles files and MaxBytes in total) is written to a fresh temporary directory with mode 700. The repository's own Claude Code configuration (.claude/, .mcp.json) is not copied, so a repository cannot add hooks, permissions or MCP servers.
  2. claude runs there headless with the prompt on stdin (never on a command line or through a shell). Only the file tools Read, Grep, Glob, Edit and Write are allowed, confined to that directory; Bash, web fetch and search, notebooks and sub-agents are disabled. Permission mode is "don't ask" with prompts off, so anything not allowed is simply refused. It is also started with no MCP servers, no session persistence, no slash commands, and a turn limit. GitBench reads claude --help at startup and passes only the flags that version supports.
  3. The environment is clean: none of the server's variables (API keys, connection strings, cloud credentials) are passed on. Only what Claude Code needs to find itself and its login: HOME, USER, PATH, locale and temp variables, CLAUDE_CONFIG_DIR and CLAUDE_CODE_OAUTH_TOKEN if set.
  4. Text and tool calls stream into the chat panel. A run longer than TimeoutSeconds is stopped by killing the whole process tree.
  5. When it finishes, the directory is compared with what was written. Every changed, added or deleted file becomes a pending proposal, exactly like the API backend. Nothing is applied automatically, and the directory is deleted.
  6. At most MaxConcurrent runs at once (others wait up to 30 seconds), plus the per-user rate limit.

Setup: install Claude Code for the operating-system account GitBench runs as and sign it in once as that account (run claude interactively, or claude setup-token and set CLAUDE_CODE_OAUTH_TOKEN). The editor then uses that account's login or subscription for every user's requests, so usage, limits and billing are the server account's, not each person's.

Per-project switch

Under Project settings, Web editor (/p/{KEY}/settings), the switch AI in the web editor (assistant, inline actions and completions) turns the AI parts on or off for that project. It is on by default whenever a backend is available. The editor itself is unaffected.

The /admin/ai status page

Site admins can open /admin/ai. It is read-only and shows whether the Anthropic API is configured (and which model), whether Claude Code is installed on the server (with its detected version and path), which backend is active, and the editor limits. Check again re-detects Claude Code after you install or log in to it. To change anything, edit the Ai:* configuration and restart. See Administration.

Limits, cost and security

  • Cost. Every chat message and inline action is billed as tokens: the cached system prompt, your message, the open file or selection, attachments and every file the assistant reads. One request can use up to 15 tool calls. Usage is logged per user and project (editor.chat, editor.action.explain|refactor|comments|tests|fix, editor.complete, with .claude-code variants). Turn the assistant off per project, or for the whole site by not configuring a backend.
  • Who can do what. Reading the workspace and chatting need ViewProject; editing, accepting proposals and committing need PushCode on a writable repository. Workspaces are private to their owner.
  • What the AI can see. Only the requesting user's workspace for this repository and branch. It cannot reach other repositories, the server's files or the network through GitBench, and cannot commit, push or call anything outside its tools.
  • Untrusted content. File contents, search results, selections and attachments are wrapped in delimited blocks with a random boundary per request, and the system prompt tells the model they are data, never instructions. Whatever it proposes still has to be accepted by you, as a diff.
  • Monaco and the page security policy. Monaco 0.52.2 ships inside GitBench and never loads from a CDN. Its web workers run from the site's own origin (worker-src 'self'); no unsafe-eval is needed. A trimmed build is used: TypeScript and JavaScript get syntax highlighting but not the full TypeScript language service.
The editor works only on branches (it commits to refs/heads/...). To edit a tag's content, create a branch from it first.
