Concepts

The handful of ideas that explain how ByteBench is organised: groups hold projects, projects hold repositories and issues, and roles flow downwards.

The big picture

Everything you do in ByteBench happens inside a project. Projects can be gathered into groups (and subgroups, up to four levels deep) to mirror your organisation. Inside a project you find its repositories, issues, pull requests, boards, pipelines and packages.

Keys and slugs identify things in URLs: /p/WEB is a project, /p/WEB/repos/web-app a repository in it, /g/acme/platform a subgroup, and the Git address is /git/WEB/web-app.git.

Projects

A project is the unit of work and of access. It has a key (2 to 10 capital letters or digits, starting with a letter, such as WEB), a name, a visibility and a list of members, each with one role. The key is unique across the whole site and appears in issue numbers (WEB-12), Git URLs and API paths. The person who creates a project becomes its Owner, and the last Owner cannot be removed or demoted.

Keys and slugs

  • Project key: global, upper case, used for issues (WEB-12), /p/{KEY}, /git/{KEY}/... and the API.
  • Repository slug: unique inside a project. When you rename a repository, the old slug keeps working as a redirect.
  • Group path: a path segment per level, such as acme/platform. Old paths of a renamed or moved group keep working as redirects until another group takes the path.

Groups and subgroups

A group is a namespace that owns projects and subgroups, like in GitLab. Groups nest up to four levels (/g/acme/platform). A project belongs to at most one group, or to none (top-level). Groups give you shared membership, aggregated issue and pull request lists across all their projects, and group-wide labels and milestones that every project below inherits.

The demo seed data contains an Internal group Acme with a subgroup Platform that owns the projects WEB and OPS. Create your own at /groups/new.

Repositories

A repository is a Git repository inside a project; a project can have several. ByteBench stores each one as a bare repository on disk and serves it over Git Smart HTTP and the built-in SSH server. Repositories carry branches, tags, releases, pull requests, pipelines, branch protection rules, mirrors and their own settings (/p/{KEY}/repos/{slug}/settings).

Issues

Issues track work: a type (task, bug, feature, story, epic, sub-task), a status from the project's workflow, priority, assignee, labels, milestone, story points and due date. They can be linked, nested under epics, put on boards and into sprints, found with the GQL query language and changed by automation rules. Details in Issues and workflows.

Pull requests

A pull request proposes merging one branch into another (possibly from a fork). It has reviews, threaded comments, suggestions, required reviewers and code owners, status checks (CI, AI review, security) and a merge strategy. Branch protection rules decide what must be true before it can be merged. See Pull requests and Branch protection and merge queue.

Roles

There are four project roles, each including everything the one before it can do:

RoleIn short
ViewerRead everything in the project
DeveloperPlus: edit and comment on issues, push code, open and review pull requests, publish packages, toggle feature flags
MaintainerPlus: merge pull requests, manage repositories, labels, milestones, sprints, flags and packages, delete branches
OwnerPlus: manage members, project settings and visibility, delete the project

A site admin (a flag on the user account) is treated as Owner of every project and can reach the /admin pages. The full permission table is in Roles and permissions.

Visibility: Internal and Private

  • Private (the default): only members can see the project. Everyone else gets "Not found", so its existence is not revealed.
  • Internal: every signed-in user can see and read it and counts as a Viewer. Anonymous visitors see no project data: every project page requires sign-in. The only public pages are the sign-in pages, the service desk request form and tracking page, and a static site set to Public.

Groups have the same two visibilities, and a subgroup cannot be more visible than its parent. Group visibility never opens a Private project: an Internal group can contain a Private project that non-members cannot see.

How permissions inherit

A user's effective role on a project is the highest of:

  1. their direct role on the project,
  2. their role in the project's group and in every ancestor group,
  3. Viewer, if the project is Internal,
  4. Owner, if they are a site admin.

So adding someone to group acme as a Developer gives them Developer rights on every project in acme and its subgroups. Inherited members show up read-only on a project's Members page with their source (for example "via acme"). Roles from single sign-on or LDAP group mappings use the same mechanism.

Direct roles never lower an inherited one. If you want someone to have less access on one project, do not put them in the parent group.

Everything above except the CI folders is part of a backup archive (CI artifacts only if you enable Backup:IncludeCiArtifacts). See Backup and restore. The Data Protection key ring encrypts secrets stored in the database (webhook and CI secrets) and signs cookies, so treat it as a secret and keep it with your backups.
