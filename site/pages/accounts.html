Accounts, sign-in and SSO

How people register and sign in with a password, two-factor codes, single sign-on (OIDC, GitHub, Entra ID) or LDAP, and how they manage tokens and their profile.

Every GitBench page requires a signed-in user. Anonymous requests are redirected to /account/login. Sign-in uses ASP.NET Core Identity with a cookie.

Registration and sign-in

  • Register at /account/register. New users get a random avatar colour and are signed in right away. There is no setting to close registration or approve new users; to keep strangers out, restrict network access or use SSO or LDAP only (see production setup).
  • Sign in at /account/login with a username or an email address.
  • Lockout: five failed attempts lock an account for five minutes. This also applies to wrong two-factor codes and LDAP passwords. A site admin can unlock or deactivate accounts (see user administration).
  • Sign out with the button in the top bar.
  • Account pages are plain server-rendered pages (not the live Blazor circuit), because sign-in has to write cookies.

The demo seed data creates a few example accounts (alice, bob, carol, dan) that share the password defined by SeedData.DemoPassword. Do not use seed data in production.

Passwords

  • At least 8 characters. Symbols are not required.
  • Change your password under Profile (/account/profile, click your avatar). You need the current password.
  • Accounts created by SSO or LDAP have no GitBench password, and the profile says so. They use personal access tokens for Git over HTTP.
  • GitBench has no "forgot password" email flow and site admins cannot set another user's password from the admin page. Someone who lost their password needs a different sign-in route (SSO or LDAP if configured) or an operator who can repair the account in the database; plan for this before going live.

Sessions

A sign-in cookie lasts 14 days and slides forward while you use the site. The server checks every minute that the session is still valid (the account's security stamp), so changing a password, resetting two-factor, deactivating an account or an admin signing the user out ends other sessions within about a minute. "Remember this device" for two-factor is separate and lasts 14 days.

Profile and avatars

On /account/profile you change your display name, email, avatar colour and password, manage access tokens, and see Connected accounts (SSO providers and LDAP). Avatars are your initials on a colour you pick from a palette; there are no image uploads. Public profiles (/u/...) and Explore are described under Explore, search and profiles. SSH keys for Git over SSH are at /account/ssh-keys.

Two-factor sign-in (TOTP)

Turn it on at /account/two-factor (Profile, Two-factor sign-in). It uses standard time-based one-time codes (6 digits, 30 seconds), so any authenticator app works.

  1. Open the page, scan the QR code (or type the key shown) in your authenticator app.
  2. Enter a current code to turn two-factor on.
  3. GitBench shows 10 recovery codes once. Store them safely. Each works one time.
  • Signing in: after your password, /account/login-2fa asks for a code, with Remember this device (14 days), or you can enter a recovery code instead. Wrong codes count toward lockout.
  • Manage: see how many recovery codes remain, generate new ones (old ones stop working), or turn two-factor off (asks for your password; the key and recovery codes are discarded).
  • Git and the API: personal access tokens keep working. Git Basic authentication with the account password is refused for two-factor accounts (use a token).
  • Lost device: use a recovery code, or ask a site admin to Reset 2FA for you.
  • Audit events: user.2fa_enabled, user.2fa_disabled, user.2fa_recovery_codes_regenerated, auth.2fa_failed.

Personal access tokens

Tokens let scripts, CI and Git clients authenticate without your password. Create them under Profile, Access tokens.

  1. Give the token a name (for example "Laptop git").
  2. Tick the scopes you need (below) and choose an expiry: 7, 30 (default), 90, 365 days or never.
  3. Press Create token and copy it immediately. It starts with gbp_ and is shown only once. GitBench stores only a SHA-256 hash.
ScopeAllows
read_repositoryClone and fetch over HTTP
write_repositoryPush over HTTP
read_apiGET requests to the REST API
write_apiAll REST API requests

Use a token as the password with any username for Git over HTTP, or as Authorization: Bearer gbp_... for the API. The list shows each token's scopes, creation, expiry and last use, with a Revoke button. A token can never do more than its owner's roles allow. Tokens of a deactivated or locked user stop working.

Single sign-on (OIDC and OAuth)

GitBench can sign people in through OpenID Connect providers (Google, Microsoft Entra ID, Keycloak, Okta and others) and GitHub, next to local accounts. Nothing changes until you configure a provider. The sign-in page then shows a Sign in with ... button per provider.

How sign-in works

  • It uses the authorization code flow with PKCE. The provider redirects back to /signin-sso/{name}, so register https://gitbench.example.com/signin-sso/{name} as the redirect URI. /admin/authentication shows the exact URL for each provider.
  • GitBench then finds or creates the account:
    1. an account already linked to this provider and user id; else
    2. with LinkByVerifiedEmail (default on), the account with the same email, but only if the provider says the email is verified and the GitBench account's email is confirmed too (or it has no password). Otherwise the user must sign in with their password and connect the provider from the profile; else
    3. with AutoCreateUsers (default on), a new account with that verified email, a username from preferred_username (or the email) and no password.
  • An unverified email never links or creates an account. With AllowedEmailDomains, only verified emails in those domains get in.
  • Locked and deactivated accounts are refused.
  • Two-factor: with TwoFactor: GitBench (default), users who enabled GitBench two-factor enter their code after the provider. With TrustIdp, the code is skipped when the ID token shows multi-factor authentication (amr claim).
  • Admins and groups: group claim values in AdminGroups make the user a site admin (revoked again when they leave the group, never for the last admin). GroupMappings turn group values into GitBench group memberships with a role (highest wins). Memberships created by the provider follow the claim on each sign-in; memberships added by hand are never touched.
  • Connected accounts: Connect links another provider to the signed-in account (the link is valid 15 minutes). Disconnect is refused if the account would be left with no password and no other login.

Provider settings (Authentication:Oidc:Providers)

Authentication:Oidc:Providers is a list. Keep client secrets out of appsettings.json: use dotnet user-secrets set "Authentication:Oidc:Providers:0:ClientSecret" "..." or the environment variable Authentication__Oidc__Providers__0__ClientSecret. Invalid providers are skipped with a warning on /admin/authentication and do not stop the app.

LDAP and Active Directory

With Authentication:Ldap:Enabled the normal sign-in form also checks your directory. GitBench uses a fully managed LDAP library, so no native libraries are needed in the container.

  • Who goes to LDAP: a login with the ldap: prefix, a login that no local account has, and accounts that came from the directory. Everyone else uses their GitBench password. A directory user never takes over a local account with the same username or email; that sign-in is refused.
  • How it signs in: GitBench binds as the service account (BindDn), searches UserSearchBase with UserFilter ({0} is the login, escaped so filter injection is not possible), then binds as the entry it found with the given password. Empty passwords are refused. It creates the account (with no GitBench password) or updates name and email, and the sign-in goes through Identity, so lockout and GitBench two-factor apply.
  • Groups come from memberOf, or from a search of GroupSearchBase with GroupFilter when Attributes:MemberOf is empty. AdminGroupDn and GroupMappings work like their SSO counterparts.
  • Git over HTTP: directory users use personal access tokens. With AllowGitPassword: true their LDAP password also works, except for accounts with two-factor.
  • Directory sync: with Sync:IntervalMinutes above 0, every directory account is re-read on that schedule (names, emails, admin, groups). With Sync:DeactivateMissingUsers, accounts the directory no longer returns are deactivated (locked, signed out, tokens revoked). Site admins are never deactivated automatically, and an unreachable directory deactivates no one.

Active Directory example:

"Authentication": { "Ldap": {
  "Enabled": true, "DisplayName": "Corp AD", "Server": "dc1.corp.example", "Security": "Ssl",
  "BindDn": "CN=svc-gitbench,OU=Service Accounts,DC=corp,DC=example",
  "UserSearchBase": "OU=Staff,DC=corp,DC=example",
  "UserFilter": "(&(objectClass=user)(objectCategory=person)(sAMAccountName={0})(!(userAccountControl:1.2.840.113556.1.4.803:=2)))",
  "AdminGroupDn": "CN=GitBench Admins,OU=Groups,DC=corp,DC=example",
  "GroupMappings": [ { "GroupDn": "CN=Developers,OU=Groups,DC=corp,DC=example", "Group": "acme", "Role": "Developer" } ],
  "Sync": { "IntervalMinutes": 60, "DeactivateMissingUsers": true }
} }

The userAccountControl clause leaves out disabled AD accounts, so the sync deactivates them in GitBench too. For OpenLDAP use for example "UserFilter": "(&(objectClass=inetOrgPerson)(uid={0}))" with "Attributes": { "UserName": "uid" }. Set the bind password with Authentication__Ldap__BindPassword.

/admin/authentication

Site admins open Authentication in the admin sidebar. For each provider it shows the type, authority, client id and scopes, whether a secret is set (never the secret), the callback URL to register, the account and mapping rules, the two-factor policy and any configuration errors. For LDAP it shows server, security, service account (password only as "set"), filters, mappings and the last sync result, with Test connection (connect, bind and run the user filter) and Sync now.

Audit events

Sign-in related events recorded in the audit log: auth.sign_in, auth.registered, auth.sso_sign_in, auth.sso_link, auth.sso_unlink, auth.sso_failed (with a reason such as unverified, domain, exists, no_account, locked), auth.external_sync, auth.ldap_sync, auth.directory_user_deactivated, plus the two-factor events above.
