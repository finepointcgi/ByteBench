Signed commits

Show which commits really come from who they say, and optionally require it on protected branches. ByteBench never trusts the pusher: every signature is checked against keys registered on ByteBench accounts.

What "Verified" means

A commit is Verified only when all of these hold:

  1. its signature is good (checked with ssh-keygen -Y verify or gpg --verify),
  2. the key is registered on a ByteBench account: an SSH key on the account (the same keys used for git over SSH; deploy keys never count) or a GPG key,
  3. the key is not revoked and not expired, and its owner's account is active,
  4. the committer email of the commit is the owner's confirmed account email.

Otherwise a signed commit is Unverified and the badge tooltip says why (Unverified (the committer email ... isn't a confirmed email of ...), signed with a key that isn't registered, the signing key was revoked, expired, the signature doesn't match the commit). If the server has no gpg or ssh-keygen, signed commits show Unverifiable and everything else keeps working. Unsigned commits show no badge. The badge appears in commit lists, the commit page and the pull request's commit list; GET .../commits/{sha}/signature returns the same.

Verification runs in a throw-away directory with a keyring or allowed-signers file built from the database. The machine's own keyrings and ~/.ssh are never read. Results are cached per commit and recomputed when keys are added, removed or revoked, when the key expires, and after Signing:CacheHours (default 12).

Registering keys

Open Account, SSH keys (/account/ssh-keys).

  • SSH keys you already added sign commits too: git config gpg.format ssh, git config user.signingkey ~/.ssh/id_ed25519.pub, git config commit.gpgsign true (git 2.34 or newer). Deleting the key revokes it; an expiry date on the key limits how long it verifies.
  • GPG keys: paste the output of gpg --armor --export you@example.com. It must be one public key (private keys are refused), not expired or revoked, and have a user ID with your account email. The list shows the fingerprint, the emails, the algorithm and the expiry; Revoke makes the key stop verifying (irreversible), Delete removes it. Needs gpg on the server (Signing:GpgPath). Audit events: gpg_key.added, .revoked, .removed.

Require signed commits

A branch protection rule can turn on Require signed commits.

  • Push: the new commits of every push to a matching branch must be Verified, or the whole push is refused with the first offending commit and the reason. A rule with Allow admins to bypass exempts Owners.
  • Pull request merge: every commit the PR brings must be Verified (a Signed commits check in the merge box), whatever the merge strategy.

ByteBench's own merge commits

ByteBench has no server signing key. Merge, squash and rebase results created by ByteBench's merge service are not signed; instead the merge commit of a merged pull request is shown as Verified (tooltip: created by ByteBench's own merge). Web merges are not pushes, so protected branches that require signed commits still accept them. Other commits of a rebase carry no badge.
