Pull requests

A pull request proposes merging one branch into another, collects review (approvals, inline threads, suggested changes), runs checks, and merges with a merge commit, a squash or a rebase.

The big picture

Every pull request (PR) belongs to one repository and has a source branch and a target branch. It is numbered per repository (web-app#12). Its page (/p/{KEY}/repos/{slug}/pull-requests/{n}) has three tabs:

  • Overview: description, timeline of comments and activity, and the sidebar with the merge box, reviewers, code owners and linked issues.
  • Commits: the commits on the source that are not on the target.
  • Files changed: the diff, with inline comment threads and code owners per file.

Lists: /p/{KEY}/pull-requests shows every PR across the project (Open, Merged, Declined) and /p/{KEY}/repos/{slug}/pull-requests one repository. Filters: Review requested (open PRs waiting for your verdict, ?filter=review-requested), the repository, and draft state (?draft=ready or ?draft=only).

Site admins count as Owners everywhere. See Roles, groups and permissions.

Creating a pull request

  1. Push a branch (or create one in the web editor, see Web editor).
  2. Click Create pull request on the Source page, on the Branches page, or in the web editor. You can also go to /p/{KEY}/pull-requests/new?repo=&source=&target=.
  3. Pick the repository, source and target (the target defaults to the repository's default branch). The page previews the commits and the diff and runs a conflict check.
  4. Give it a title (required, up to 200 characters) and a description in Markdown. Add reviewers if you like.
  5. Click Create pull request, or Create draft to open it as a draft.

Rules: the source must have commits that the target lacks, source and target must differ, there can be only one open PR from a given source into a given target, and archived repositories refuse new PRs. When a PR is created, assigned reviewers, default reviewers from branch protection and code owners are notified (unless it is a draft), and the PR is queued for an AI review if that is turned on for the repository.

Reviewers and approvals

  • Assign reviewers on the New PR page (project members who can review) or with Edit reviewers in the PR sidebar (the author or a Maintainer). Each reviewer shows as Pending, Approved or Changes requested. Added reviewers get a "requested your review" notification and start watching the PR.
  • Approve, Request changes, Unapprove or Withdraw from the sidebar. You cannot review your own PR.
  • A review records the commit it was given on. If the target's rule has Dismiss approvals when new commits are pushed, only approvals on the PR's current head count and a push removes older ones.
  • Changes requested by anyone blocks merging into a protected branch until it is withdrawn.
  • Required approvals (0 to 10 distinct people other than the author) are set per branch in branch protection.

Draft pull requests

Click Create draft on the New PR page (or send "draft": true to the API). A draft shows a grey Draft badge, can never be merged or queued (an admin cannot bypass this), and its assigned reviewers are recorded but not notified. When it is ready, the author or a Maintainer clicks Ready for review; Convert to draft goes back. A draft in the merge queue is removed. Webhook: pull_request.updated with action ready_for_review or converted_to_draft.

Inline comments and threads

On the Files changed tab, click a line to comment on it. An inline comment starts a thread; Reply adds to it. Select several new-side lines for a multi-line comment (the API's startLine).

  • Resolve or Unresolve a thread (PR author, thread author or Maintainer). Resolved threads collapse. The PR header counts unresolved threads.
  • A thread is marked Outdated when a later push changed its line. Each inline comment remembers the head commit and the text of the line it was made on.
  • The rule Require all threads resolved in branch protection blocks merging while any inline thread is unresolved.

Suggested changes

In an inline comment on a new-side line, a fenced block opened with suggestion proposes replacement text for the commented line or lines. An empty block deletes them. Suggest a change in the comment box inserts a block prefilled with the line.

```suggestion
const timeoutSeconds = 30;
```

It renders as a small diff with Apply suggestion. Applying writes a commit to the source branch authored by the person who applied it, with the message "Apply suggestion from @user" and a Co-authored-by trailer for the suggester, and resolves the thread. Apply all suggestions commits every pending one in a single commit. Both are refused (nothing written) if the suggested lines changed since the comment or two suggestions overlap. The button appears only for people who may push to the source branch; the repository must not be archived.

Code owners (CODEOWNERS)

A CODEOWNERS file on the target branch says who must look at which files. ByteBench uses the first one it finds: .bytebench/CODEOWNERS, then CODEOWNERS, then docs/CODEOWNERS. The syntax is GitHub's: one rule per line, pattern owner owner..., # for comments, and the last matching rule wins. Patterns follow .gitignore rules (*.md, /build/, docs/*, src/**/test.cs). Negation (!) and [ ] classes are not supported and show as a warning.

# .bytebench/CODEOWNERS
*                @alice
/docs/           @bob carol@example.com
*.cs             @acme/backend
/src/billing/    @dana @acme/finance
Owner written asMeans
@usernameThat user
email@example.comThe user with that email
@group/path (or a bare @acme that is not a username)The group's direct members with Developer or higher
  • Owners of the changed files are added as reviewers when the PR is created (if they can review). The Files changed tab and the sidebar show the owners.
  • Owners who cannot see the project, and names that match no user or group, are ignored with a warning on the PR.
  • Branch protection option Require code owner approval blocks merging until each changed file that has owners is approved by one of them. Files owned only by the PR's author need no approval.

The merge box and merge checks

The Merge section in the PR sidebar lists every check with its state, and the button is disabled while anything blocks. Checks come from:

  • Draft: a draft can never merge.
  • Conflicts: ByteBench computes the merge in memory; conflicting files are listed and nothing is written.
  • Approvals, Change requests, Threads and Code owners, from the target branch's protection rule.
  • External checks such as the CI pipeline, which block when pending or failed if the rule has Require checks to pass. A neutral result never blocks. Pipelines are described in CI pipelines.
  • Signed commits: with Require signed commits on the target branch, every commit the PR brings must be Verified (see Signed commits).
  • AI review: when enabled for the repository, unresolved blocker findings block merging (see AI review and triage).

An admin who is allowed to bypass sees Merge (bypass protection); a bypassed merge is noted in the timeline and audit log (pull_request.merged_bypassing_protection). If the target branch uses a merge queue, the button becomes Add to merge queue.

Merge when ready (auto-merge)

While a PR can't be merged yet (a draft, blocked by protection, or conflicting), a Maintainer sees Merge when ready under the merge button. It uses the strategy and Delete source branch choice currently selected in the merge box. ByteBench then merges the PR the moment every requirement is satisfied: required approvals, passing checks, branch protection, no conflicts, not a draft. It goes through the same merge gate and the same merge code as a manual merge, as the person who armed it (they are recorded as the merger), and an admin's bypass of protection never counts. If the target branch uses a merge queue, the PR is added to the queue instead.

  • When it is checked: right away, after reviews and comments, when a pipeline finishes, after any push to the repository, when branch protection changes, and every AutoMerge:SweepSeconds (default 30) as a safety sweep. AutoMerge:Enabled=false turns the background worker off.
  • It cancels itself, with a timeline entry, an audit event and a notification to the person who armed it, when someone other than that person pushes new commits, when they lose merge permission or their account is deactivated, when the PR is closed or retargeted, when nothing is left to merge, or when a check that blocks merging fails. A PR merged by hand just ends it. Conflicts, missing approvals and pending checks keep it waiting; the banner shows what it is waiting for.
  • Race safe: one attempt per PR at a time (a conditional update claims it; a claim abandoned by a crashed worker is taken over after AutoMerge:LeaseMinutes, default 10), and the merge is refused if the source branch moved after it was evaluated.
  • The PR page shows a banner with Cancel auto-merge (the person who set it, or any Maintainer); the PR list shows an Auto-merge chip. Audit events: pull_request.auto_merge_armed, .auto_merge_cancelled, .auto_merge_merged.

Merge strategies

StrategyResult on the target
Merge commitKeeps every commit and adds a two-parent merge commit. Fast-forward if possible moves the branch without a merge commit when the target has not moved.
SquashOne new commit with an editable message, authored by the PR's author, with Co-authored-by trailers for other commit authors. The default message is the title, number and commit list.
RebaseThe PR's commits are replayed onto the target and the target is fast-forwarded. Merge commits are dropped; a conflict refuses cleanly.

Maintainers choose which strategies are allowed and which is the default under the repository's Settings, Pull requests (/settings/merge); at least one must stay allowed and the default must be one of them. The chosen strategy is recorded on the PR (mergeStrategy), in the activity ("squashed and merged...") and as a Merge-Strategy: trailer on merge and squash commits. Tick Delete source branch after merging to remove the source branch (never the default branch, and not for fork PRs); this needs the delete permission and is blocked if a rule forbids deleting that branch.

Decline and reopen

Decline closes a PR without merging; Reopen brings it back. The PR stores the source and target tips at merge or decline time, so its diff stays viewable after the source branch is deleted.

Linked issues

An issue key such as WEB-3 in a PR title, in its source branch name, or in its commit messages links the PR to that issue. The PR lists its linked issues, and each issue's Development panel shows the branches, PRs and recent commits that mention it. Merging adds "merged pull request web-app#N into main" to each linked issue's activity.

ByteBench does not close or transition an issue automatically when its PR merges (there are no "Closes WEB-3" keywords). To do that, use an automation rule with the trigger Pull request merged.

Forks and cross-fork pull requests

To propose a change to a repository you cannot push to, fork it, push a branch to your fork, and click PR to upstream in the fork's header (/p/{KEY}/repos/{slug}/fork-pull-request). It can target any repository in the same fork network. You need CreatePullRequest in the fork's project and only ViewProject in the target. The PR belongs to the target repository and appears in its lists as KEY/slug:branch.

  • How it works. The fork's branch is fetched into the target at refs/pull/{n}/head. Diffs, threads, checks, CODEOWNERS and merging all read that ref; nothing is written to the target's branches until merge. Later pushes to the fork move the ref, add a timeline entry, dismiss stale approvals where the rule asks, re-queue AI review, send a pull_request.updated webhook with action synchronize, and start the PR's pipeline.
  • The author can comment, edit, draft, decline and reopen with only view access to the target. Reviewing and merging need the usual roles in the target. "Delete source branch" is not offered.
  • Suggestions commit to the fork's branch, so Apply suggestion shows only for people who can push there.
  • If the fork is deleted the PR stays open (source shown as "unknown repository:branch") and can still be reviewed and merged. Deleting the upstream leaves forks working, just unlinked.
CI security. A fork PR's pipeline runs code from outside the project, so it gets no CI variables at all (protected or not), uses the unprotected cache scope, and waits until a Maintainer clicks Approve and run on the pipeline page. The approval covers that one pipeline; the next push waits again. Details: CI pipelines.

Sync fork and compare: /p/{KEY}/repos/{slug}/compare/{base}...{head} shows the commits and diff between two branches with a prefilled Create pull request button.

Activity, notifications and webhooks

The Overview timeline records every event: comments, reviews, reviewer changes, draft toggles, title edits, pushes to fork PRs, merge queue actions, bypassed merges and the merge itself. Watchers (the author, reviewers, commenters) get in-app and email notifications according to their notification preferences. Webhook events: pull_request.opened, pull_request.updated (edits, reviews, reopen, draft changes, fork syncs), pull_request.merged, pull_request.declined, pull_request.commented. Payloads carry isCrossFork and sourceRepository. See REST API and webhooks.
