Automation rules

Rules do routine work for you: when something happens, if the issue matches, run a list of actions, as a bot or as the rule's author.

A rule has three parts: a trigger (when), optional conditions (if) and an ordered list of actions (then). Typical uses are closing a parent when all its sub-tasks are done, moving issues to Done when their pull request merges, assigning new bugs round-robin, or commenting when a pipeline fails.

Where rules live

  • Project rules: Settings, Automation at /p/{KEY}/settings/automation. Maintainers and Owners manage them.
  • Group rules: /g/{path}/-/automation. Group Maintainers and above manage them. They run in every project of the group and its subgroups, and each project's page lists the group rules that apply to it, read-only. Group rules refer to statuses and labels by name so they work across projects.

Creating, editing, enabling, disabling and deleting rules is audited (see Audit). The editor offers templates: "When a PR is merged, move linked issues to Done", "When all sub-tasks are done, close the parent", "Auto-assign new bugs round-robin", and "Comment when a pipeline fails".

Pull request and pipeline triggers behave like the smart-commit links in the Development panel. If no issue is linked, the rule runs once with no issue, so only notification and webhook actions can do anything.

Conditions

Conditions combine with all or any:

  • Issue type, priority (is, is not, at least, at most), status, status category.
  • Labels contain or do not contain.
  • Assignee: is, is not, empty, not empty, is the person who triggered the rule.
  • Title contains.
  • Linked pull request: exists, an open one exists, none.
  • Sub-tasks: all done, not all done.
  • Matches GQL query (or does not match), for example labels = urgent AND cf[severity] in (Major, Critical). The query's syntax and field names are checked when the rule is saved. It runs as the rule runs (as the author, so currentUser() is the author and only issues they can view match; or as the bot with system access), with names resolved only in the rule's project. A query that fails at run time, for example an unknown status, counts as not matching. See GQL.

Smart values

Text fields accept {{...}} placeholders. Unknown names render as nothing. The editor lists all of them; common ones:

{{issue.key}}  {{issue.title}}  {{issue.status}}  {{issue.assignee}}  {{issue.parent.key}}
{{initiator.name}}  {{pr.title}}  {{pr.url}}  {{pipeline.status}}  {{comment.body}}  {{rule.name}}
Comment text example:
Pipeline {{pipeline.status}} for {{issue.key}} ({{issue.title}}). Please check, {{issue.assignee}}.

Webhook action

POSTs JSON with event: "automation" and the rule, project, issue, pull request, pipeline and initiator. It uses the same sender as project webhooks: an SSRF guard, a 10 second timeout and no redirects. It is unsigned and the URL is validated when the rule is saved. For signed deliveries use project webhooks instead.

Run as

By default a rule runs as the ByteBench Automation bot (username bytebench-automation), created on first use. It has no password, is locked out, and cannot be assigned or mentioned. It stays inside the rule's project: it only links issues of that project and only assigns users who can view it. Alternatively, a rule can run as its author, meaning whoever last saved it, with that person's permissions at run time. If the author has since been demoted, the rule fails. Activity, comments, notifications and webhooks show the acting identity like any other change.

Execution, loops and limits

Events are queued in memory and processed one at a time by a background worker, each rule in a fresh scope. A timer in the same worker evaluates scheduled rules every minute; missed runs collapse into one.

  • Loop protection: changes made by a rule's actions do not trigger other rules unless the rule has Allow this rule's changes to trigger other rules ticked. Even then a chain stops after 3 rules and logs "Loop stopped".
  • Rate limit: a rule runs at most 100 times in a rolling hour; the first skipped run is logged as "Throttled".
  • Restarts: the queue is in memory, so queued events are lost if the server stops before processing them.

Run log

Every run records the trigger, issue, result (Success, Failed, No actions, Throttled, Loop stopped), the actions taken, a message and the duration. The Log button on a rule shows its latest 100 runs and updates live (?log={id} on the settings page). Only the latest 500 runs per rule are kept.

Walk-through: close the parent when all sub-tasks are done

  1. Open /p/WEB/settings/automation and choose the template "When all sub-tasks are done, close the parent" (or New rule).
  2. Trigger: Issue transitioned, to your Done status.
  3. Condition: the issue's type is Sub-task.
  4. Action: Transition parent when all children are done, to Done. It checks the siblings itself and does nothing (logged as "Not all children ... are done") until the last one finishes.
  5. Leave Run as on the bot, save, then move the last sub-task to Done and open the rule's Log to see the run.
