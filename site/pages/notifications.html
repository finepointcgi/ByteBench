Notifications and email

GitBench tells you about the things that involve you through a live bell in the top bar, optional emails and, if you use Slack, direct messages, and every kind can be tuned from one preferences page.

In-app notifications

The bell in the top bar shows a live unread count and a dropdown with the latest 10 notifications. Click one to mark it read and open the item, or use Mark all read. The full list is at /notifications, with All and Unread tabs and paging.

  • The person who acted is never notified, and each user gets at most one notification per event. Assignment and mention take priority over the watcher notification.
  • Recipients are always restricted to people who can see the project, so a notification never leaks a private item.
  • Edited descriptions notify only users who are newly mentioned. Edited comments notify nobody.

Live updates

Boards, issue lists, issue and pull request pages, the dashboard activity feed, the notifications page and the bell update on their own through GitBench's in-process event hub. Two browsers on the same board see a card move without reloading. A refresh replaces only the loaded data, so text you are typing in a description, title or comment is not touched.

The event hub lives inside one server process. A deployment with several GitBench servers behind a load balancer would need a shared backplane for live updates; see production setup.

Watching and muting

  • You watch an issue automatically when you report it, are assigned to it or comment on it. You watch a pull request when you author it, review it, are a reviewer or comment on it. The Watch / Watching button on the issue and pull request pages toggles it.
  • Mute (next to Watching) keeps the watch but stops watcher notifications. Direct notifications still arrive: assigned to you, mentioned, review requested, reviews of your own pull request.
  • Unwatching is not the same as muting. GitBench auto-watches you again when you comment, are assigned or review, so an unwatch may not stick, while a mute does. Unwatching also clears the mute.

Mentions and autocomplete

Type @ and a letter in any Markdown editor (issue description, new issue, comments, pull request description and comments, inline diff comments) to get up to 8 people who can view the project. Each row shows the display name, @username and avatar colour. Typing # and a number or text suggests issues, and a project key like WEB- suggests that project's issues. Pick with the arrow keys and Enter or Tab, or the mouse; Esc closes the list.

  • Mentions match existing usernames case-insensitively and are ignored inside code spans and code blocks. Known users render highlighted.
  • Suggestions come only from people who can view the project (site admins, members, and everyone if the project is Internal). The AI review bot is never suggested.
  • Lookups run as you and return nothing for a project you cannot view.

Notification preferences

Open /account/notifications (linked from your profile and the bell dropdown). For each group, choose In-app + email, In-app only or Off. A master switch turns all notification emails off. "Don't notify me about my own actions" is shown and is always on.

If one event qualifies for several kinds (say, you are mentioned in a comment on an issue you watch) and you turned the first off, you get the next one. There are no sprint notifications.

When your Slack account is linked and the server has a Slack bot token, a switch Also send my notifications as Slack direct messages appears here. See Slack direct messages.

Email setup (administrators)

Email is off by default. While Email:Enabled is false nothing is queued and pending notification emails are dropped, so switching it on does not send a backlog.

Never put SMTP credentials in appsettings.json. Use user-secrets in development and environment variables in production:

# production (Docker, systemd)
Email__Enabled=true
Email__Sender=Smtp
Email__Smtp__Host=smtp.example.com
Email__Smtp__Port=587
Email__Smtp__User=gitbench@example.com
Email__Smtp__Password=<from your secret store>
Email__From=GitBench <gitbench@example.com>
Email__BaseUrl=https://gitbench.example.com

# development
dotnet user-secrets set "Email:Enabled" "true"
dotnet user-secrets set "Email:Sender" "Smtp"

How email is sent

  • Emails go on an in-memory queue and a background worker sends them, so a page never waits on SMTP. A failed send is retried 3 times (after 2, 10 and 30 seconds), then logged and dropped. Log lines mask addresses (b***@example.com).
  • A second worker turns pending notifications into emails whenever notifications change and every 30 seconds. It skips anything you already read in the app.
  • With a digest interval above 0, the first email goes out immediately and later ones are grouped.

What the email contains

Each email is built from the same notification the bell shows: who did it, what happened, the title and a link to the item. It also includes an excerpt of the comment or description (at most 1,000 characters). The HTML part renders the excerpt with the same safe Markdown as the site (raw HTML disabled), and the plain-text part quotes the Markdown source. Every other piece of user content is HTML-encoded.

Every email links to your preferences and carries a signed one-click unsubscribe link (valid 90 days, also sent as List-Unsubscribe and List-Unsubscribe-Post headers) that switches off all notification emails for that user.

Replying to emails

Replying to a notification email does not add a comment to the issue or pull request; use the link in the email. Reply handling exists for the service desk, where requesters answer by email and replies above the marker line are added to the ticket.
