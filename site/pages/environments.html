Environments and deployments

Mark a CI job as a deployment and GitBench records what is running where, who put it there, who approved it, and which issues, pull requests and releases it contains.

How it works

Environments are not configured up front. A job with an environment: key in .gitbench-ci.yml records a deployment every time it runs (environment, pipeline, job, commit, branch, user, status). The environment is created the first time a job names it, and its URL is refreshed from the file on each run. Environments belong to a repository; the project-wide page gathers all repositories.

  • Repository page: the repository's Environments tab, /p/{KEY}/repos/{slug}/environments.
  • Project page: /p/{KEY}/environments, every repository's environments, deployments waiting for approval, and deploy freezes.
  • Anyone who can view the project sees them (Viewer).

The environment keyword

jobs:
  deploy-production:
    needs: [test]
    only: [main]
    when: manual
    environment:
      name: production              # required
      url: https://example.com      # optional, absolute http(s) URL, up to 500 characters
      action: start                 # start (default) or stop
    steps:
      - run: ./deploy.sh

  stop-review:
    when: manual
    environment: { name: review/pr-42, action: stop }
    steps:
      - run: ./teardown.sh
FieldRules
nameUp to 64 characters: letters, digits, spaces, _ . / -, starting with a letter or digit. Names are per repository.
urlShown as a link on the Environments page and passed to the job as CI_ENVIRONMENT_URL. Non-http(s) URLs are an error.
actionstart (a normal deployment) or stop. A job with action: stop records a stop deployment; when it passes, the environment is marked stopped. Anything else is an error.

The job sees CI_ENVIRONMENT_NAME and CI_ENVIRONMENT_URL, and its log says "Deploying to environment ...". The environment's current deployment is its last successful start deployment; the latest may be newer and still running or failed.

There is no dynamic-name templating ($CI_COMMIT_REF_SLUG in name is not expanded), so per-branch review environments need a job per fixed name, or a name you write in the file.

Protected environments and approvals

A protected environment gates its deployments. Any job that deploys to it waits in Manual as waiting for approval, regardless of allow_failure, until enough approvers approve. The check happens when the job becomes ready, so a pipeline created before the environment was protected still waits.

Who can approve

  • With no approvers listed on the environment, Maintainers and Owners approve.
  • With approvers listed (individual users and/or groups), only those people can approve, and they must still be able to push (Developer or higher). A group means every direct member of that group.
  • Required approvals is 1 to 10 (default 1). Approvals must come from distinct people. Someone who already approved cannot approve again.
  • The person who triggered the pipeline is not excluded from approving, so require 2 approvals if you want a second pair of eyes.

Set it up

  1. Open the repository's Environments tab. Environments appear after a job has run; to protect one before its first deployment, use Add environment (it is added already protected, if you tick that).
  2. Toggle Protected (Maintainer or Owner).
  3. Open Approval rules: set the required count and pick approver users and groups. The card then reads, for example, "2 approvals from Dana Lee, group platform/sre".

Approving or rejecting

Waiting deployments appear on the project Environments page ("Waiting for approval") and on the pipeline page, each with an Approve button (and Reject), optional comment, and the approvals so far ("1 of 2"). When the last required approval arrives the job starts, attributed to the last approver. One rejection cancels the job and fails the pipeline; the pipeline's author is told, with your comment. Approvers get a "deployment approval requested" notification when a deployment starts waiting (see Notifications).

Redeploy and rollback

Every deployment in an environment's history has a rollback (redeploy) button. It re-runs the original deployment's job in its original pipeline, so it deploys the same commit with the same job definition. Only a deployment that passed can be redeployed.

  • The redeploy is recorded as a new deployment flagged as a rollback when it goes back in history ("rollback" in the UI, isRollback in the webhook).
  • On a protected environment the requester must be an approver, the request counts as their approval, and more approvals are collected if the rule needs them. A deploy freeze blocks it.
  • The job's artifacts and logs are replaced by the new run; the job gets the artifacts that its needs still have, which may have expired. Keep artifacts you may need to roll back to.
  • Audit event: deployment.redeployed.

Each deployment row also offers compare (the commits between the previous successful deployment and this one; for a rollback, the commits it removed), and shows the nearest tag, such as v1.4.0 or v1.4.0+3.

Stopping an environment

Stop on an environment runs its stop job (environment: { name: ..., action: stop }) from the pipeline that deployed it. If there is no stop job, a Maintainer can mark the environment stopped. Stopping an environment does not delete its history.

Deploy freezes

A freeze window blocks deployments to protected environments for a period, such as a holiday code freeze. While a window is active, approving, running, redeploying and rolling back such jobs are all refused ("Deployments to protected environments are frozen"). Unprotected environments are not affected.

  • Manage windows at the bottom of the project Environments page ("Deploy freezes"), Maintainer or higher.
  • Date range: a start and/or end (UTC). Either side may be open. Starts inclusive, ends exclusive.
  • Recurring: two cron expressions, one for when the freeze starts and one for when it ends (5-field, UTC, same syntax as schedules), for example start 0 18 * * fri and end 0 6 * * mon for every weekend.
  • Add an optional description (up to 200 characters). Audit events: deploy_freeze.created, deploy_freeze.deleted.

Traceability: what is deployed where

GitBench works out which environments contain a piece of work. A commit counts as deployed when the environment's current successful deployment is that commit or a descendant of it. The result, with the first deployment that shipped it and a "N of M commits" count when only some are in, appears as a Deployed to panel:

  • Issues: in the Development panel of an issue. It looks at commits that mention the issue key (such as WEB-12) and merge commits of merged pull requests whose title or source branch mentions it, across the project's repositories.
  • Pull requests: on a merged PR, where its merge commit is deployed.
  • Releases: on a release's page, where its tag is deployed.

The same data feeds the DORA metrics (set which environment counts as production in the delivery reports settings).

Webhook: deployment.status

Subscribe a webhook to deployment.status. It fires each time a deployment changes status. status is one of waiting_for_approval, running, success, failed, canceled.

  "event": "deployment.status",
  "deployment": {
    "id": 31, "status": "waiting_for_approval", "action": "start",
    "ref": "main", "commitSha": "9f2c1e0...", "isRollback": false, "redeployOfId": null,
    "pipelineId": 118, "jobId": 402, "jobName": "deploy-production",

The delivery also has the usual envelope fields (project, sender); see the webhooks section of REST API and webhooks.

Audit events

environment.created, environment.protected, environment.unprotected, environment.approval_rules_changed, environment.stop_requested, environment.stopped, environment.deleted, deployment.approved, deployment.rejected, deployment.redeployed, deploy_freeze.created, deploy_freeze.deleted. Deleting an environment removes its deployment history but not the pipelines.

Complete example

jobs:
  build:
    steps: [ { run: ./build.sh } ]
    artifacts: { paths: [dist/], expire_in: 14d }
  deploy-staging:
    needs: [build]
    only: [main]
    environment: { name: staging, url: "https://staging.example.com" }
    steps: [ { run: ./deploy.sh staging } ]
  deploy-production:
    needs: [deploy-staging]
    only: [main]
    environment: { name: production, url: "https://example.com" }   # protect "production" in the UI
    steps: [ { run: ./deploy.sh production } ]

Protect production, require 2 approvals from group release-managers, and the deploy-production job will wait for two of them each time. Keep deploy credentials in protected CI variables: environment protection controls who may run the job, while protected variables control which branches may read the secrets.
