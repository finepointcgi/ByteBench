Production setup

Run ByteBench on a real server: Docker image and compose file, a TLS reverse proxy, PostgreSQL or SQLite, data protection keys, backups, upgrades, health checks and a checklist.

The shape of a deployment

ByteBench is one ASP.NET Core process with a database (SQLite by default, or PostgreSQL) and a handful of folders: repositories, attachments, packages, LFS objects, published sites and the Data Protection key ring. Run it as a single instance; the in-process queues for CI, webhooks and AI review are not built for several replicas.

A typical layout: a TLS reverse proxy (Caddy or nginx) in front of the container, the container's volumes on reliable disks, backups written to a different disk, and optionally a PostgreSQL container or server.

Docker image and compose

docker compose up -d --build        # build the image and start on 127.0.0.1:8080
docker compose logs -f bytebench     # JSON logs

The Dockerfile is multi-stage: an SDK build, then an aspnet:10.0 runtime that adds git, openssh-client, postgresql-client, curl and sqlite3. It runs as the non-root app user (uid 1654). Ports: 8080 for HTTP (behind your TLS proxy) and 2222 for Git over SSH.

All state lives under /data, one volume per kind:

VolumePath in the containerHolds
bytebench-db/data/dbSQLite database (unused with PostgreSQL)
bytebench-repos/data/reposBare Git repositories
bytebench-attachments/data/attachmentsAttachments and release assets
bytebench-packages/data/packagesPackage and image blobs
bytebench-lfs/data/lfsGit LFS objects
bytebench-pages/data/pagesPublished static sites
bytebench-keys/data/keysData Protection key ring and SSH host key
bytebench-backups/data/backupsBackup archives. Put this on another disk

Image defaults. The image sets ASPNETCORE_ENVIRONMENT=Production, Seed__DemoData=false (no demo users), Ci__Enabled=false, Security__HttpsRedirection=false (TLS ends at the proxy), Ssh__Enabled=true on port 2222 and the /data/... paths for every folder. Override anything with environment variables; see the Configuration reference.

First admin. Register your account at /account/register, then restart once with Bootstrap__AdminUsers=your-username (several names separated by commas). It only ever promotes users, so you may leave it set.

The compose file publishes HTTP as 127.0.0.1:8080:8080, reachable only from the host itself, so your proxy (or an SSH tunnel) is the way in. It publishes SSH as 2222:2222.

CI in the container

CI jobs need a Docker daemon, so CI is off in the image. Three ways to turn it on:

  1. Mount the host Docker socket: build with --build-arg WITH_DOCKER_CLI=true, mount /var/run/docker.sock, set Ci__Enabled=true, and set Ci__WorkDirectory to a folder mounted at the same path on the host and in the container (the daemon mounts workspaces by host path). The socket's group must be usable by uid 1654 (group_add).
  2. Run ByteBench on the host (dotnet ByteBench.dll under systemd) with Docker installed.
  3. Use a separate Docker host via DOCKER_HOST=tcp://ci-host:2376 with TLS (DOCKER_TLS_VERIFY=1, DOCKER_CERT_PATH). This is the safest: builds cannot touch the ByteBench host.
The Docker socket gives root on the host. Anyone who can push can run any image, so every Developer effectively becomes root on that machine. Do this only on a dedicated host where you trust everyone who can push, and keep Ci__Network=none unless jobs need the network.

Reverse proxy and forwarded headers

Terminate TLS at a proxy and forward to port 8080. Two things must be right or sign-in, links and logs will misbehave:

  1. Trust the proxy's forwarded headers. Set ReverseProxy__Enabled=true and list the proxy in ReverseProxy__KnownProxies__0 (an IP) or ReverseProxy__KnownNetworks__0 (a CIDR range, 172.16.0.0/12 for compose networks). ByteBench then honours X-Forwarded-For and X-Forwarded-Proto, so cookies, HSTS and generated links see https and the audit log and rate limits see the real client IP. Requests from untrusted addresses keep their own IP, so clients cannot spoof it.
  2. Pass the original Host header and WebSockets (Blazor uses /_blazor).

Also set PublicBaseUrl to the public https:// URL and AllowedHosts to your host name.

Caddy

Caddy gets and renews Let's Encrypt certificates and forwards Host, X-Forwarded-* and WebSockets by default. The compose file has a commented-out service; uncomment it, set your domain and remove the ports: mapping from bytebench:

caddy:
  image: caddy:2
  restart: unless-stopped
  ports: ["80:80", "443:443"]
  command: caddy reverse-proxy --from bytebench.example.com --to bytebench:8080
  volumes:
    - caddy-data:/data
  depends_on: [bytebench]

Or with a Caddyfile on a host:

bytebench.example.com {
    reverse_proxy 127.0.0.1:8080
}

nginx

A sketch of the parts that matter (adjust certificates and paths; this is an example, not shipped with ByteBench):

map $http_upgrade $connection_upgrade { default upgrade; '' close; }

server {
    listen 443 ssl;
    server_name bytebench.example.com;
    # ssl_certificate / ssl_certificate_key ...

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_read_timeout 1h;
    }

    # large and slow Git pushes and uploads
    location /git/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        client_max_body_size 0;
        proxy_request_buffering off;
        proxy_buffering off;
    }
}

Package and container registry uploads (/packages/ and /v2/) also need a large body limit. The proxy does not carry Git over SSH: publish port 2222 directly, or use a TCP (layer 4) proxy.

SSH port and clone URLs

To offer git@host:KEY/slug.git URLs, map the host's port 22 to the container ("22:2222", after moving the host's own sshd elsewhere) and set Ssh__PublicPort=22. Set Ssh__PublicHost if the SSH host name differs from the web one. Set Ssh__Enabled=false for HTTPS-only.

HTTPS, cookies and HSTS

  • Outside Development, sign-in cookies are Secure-only. Over plain HTTP sign-in does not work; ByteBench logs a warning when it sees that. For a short trial set Security__SecureCookies=false.
  • HSTS is sent on HTTPS responses outside Development: Security:HstsMaxAgeDays (365) and Security:HstsIncludeSubDomains (false). It only appears once ByteBench knows the request was HTTPS, which needs the forwarded headers above.
  • Security:HttpsRedirection redirects HTTP to HTTPS. The image turns it off because the proxy does that.
  • Every response also gets X-Content-Type-Options: nosniff, X-Frame-Options: DENY, a referrer policy, a permissions policy and Cross-Origin-Opener-Policy: same-origin. HTML pages get a Content-Security-Policy; see CSP blocking something.

Postgres or SQLite

SQLite is the default and is fine for one server. PostgreSQL 14 or newer is the better choice when you want a managed database, standard database tooling or more concurrent writers.

Database__Provider=Postgres
ConnectionStrings__Default="Host=postgres;Database=bytebench;Username=bytebench;Password=..."
  • With compose: docker compose --profile postgres up -d starts the optional postgres:17-alpine service. Uncomment the three Database__Provider lines and depends_on in docker-compose.yml, and set BYTEBENCH_DB_PASSWORD in your environment.
  • Migrations run at start and create the database if the role may CREATE DATABASE.
  • There is no data migration from an existing SQLite database. Start a new installation on PostgreSQL, or stay on SQLite.
  • Backups on PostgreSQL use pg_dump and pg_restore (in the image) and restore only into the same provider.
  • Npgsql pools connections (default 100): size it against max_connections.
  • Failover, replicas and load were not tested; ByteBench is still one instance.

Data Protection keys

The key ring encrypts secrets stored in the database (webhook and CI secrets, chat webhook URLs), signs cookies and protects tokens. If it is lost, everyone is signed out and the stored secrets cannot be read.

  • DataProtection:KeysPath must be a persistent, backed-up folder (a volume in Docker). In Production, if it is unset ByteBench warns; if it is not writable it refuses to start.
  • Set DataProtection:CertificatePath (and CertificatePassword) to a .pfx to encrypt the keys at rest. On Linux they are otherwise plain XML in a mode-700 folder.
  • After rotating the certificate, list the old ones in DataProtection:DecryptionCertificatePaths.
  • The SSH host key lives next to the key ring. A new host key makes every SSH client warn about a changed host.

Backup and restore

One archive, bytebench-backup-<UTC time>.tar.gz plus a .sha256 file, holds everything needed to rebuild: the database (a consistent SQLite online backup, or a pg_dump), repositories, attachments, packages, LFS, pages, the keys (Backup:IncludeKeys, default on) and optionally CI artifacts. A manifest.json records format, version, provider, newest migration and the size and SHA-256 of every file. Archives store folder names, not absolute paths, so they restore onto any layout.

Command line

# safe while ByteBench is running
dotnet ByteBench.dll backup /srv/backups --keep 14

# stop ByteBench first
dotnet ByteBench.dll restore /srv/backups/bytebench-backup-20261119-023000.tar.gz [--force]

# Docker
docker compose exec bytebench dotnet ByteBench.dll backup
docker compose stop bytebench
docker compose run --rm bytebench restore /data/backups/bytebench-backup-....tar.gz
docker compose start bytebench

Exit code 0 means success, 1 a backup or restore problem, 2 bad arguments. Run dotnet ByteBench.dll backup --help for details.

Restore checks everything first. It unpacks into a staging folder and verifies: entries are plain files under known sections (no .., absolute paths or links); the manifest is present and from the same database provider; the backup is not from a newer ByteBench than this build; every file matches its size and SHA-256; and the installation is empty (no users or projects, empty storage folders). A non-empty installation is refused unless you pass --force, which replaces the database and the contents of each folder in the archive.

Scheduled backups and the admin page

Set Backup__Enabled=true (the compose file does) and archives are written on a schedule inside the server: at Backup:StartTimeUtc (02:30) plus every Backup:IntervalHours (24), keeping the newest Backup:KeepLast (7) and, if set, dropping those older than Backup:KeepDays. The newest archive is never deleted, and only bytebench-backup-*.tar.gz files are touched. Site admins can use /admin/backups to back up now, download and delete archives; /admin/system shows the last result.

A backup contains password hashes, webhook and CI secrets and the key ring. Store it encrypted with access control, on a different disk or machine. Test a restore into a scratch directory now and then; an untested backup is a hope, not a backup.

scripts/backup.sh is an older shell-only SQLite alternative.

Upgrades and migrations

  1. Back up first: docker compose exec bytebench dotnet ByteBench.dll backup, or rely on the schedule.
  2. Deploy the new version: git pull && docker compose up -d --build, or replace the published files and restart.
  3. Migrations run automatically at start-up. Watch the log for Applying migration and /admin/system for pending migrations. If start-up fails, stop, restore the backup with restore --force and run the previous version. A backup made by a newer version is refused by an older one.

Two migration histories exist (SQLite and PostgreSQL); the correct one is chosen from Database:Provider.

Upgrading an install that was called GitBench

The product was renamed from GitBench to ByteBench. An existing install keeps working after the upgrade, and nothing needs to be migrated by hand:

SQLite filegitbench.dbbytebench.dbWith no ConnectionStrings:Default set, and only the old file present, the old file is used. Rename it (with its -wal and -shm files, while the app is stopped) whenever you like.
CI file.gitbench-ci.yml.bytebench-ci.ymlThe old name is still read when the new one is absent.
CI variablesGITBENCH_*BYTEBENCH_*Jobs get both names.
Repository files.gitbench/ (issue templates, pull request template, CODEOWNERS).bytebench/The old folder is still read.
Webhook headersX-GitBench-*X-ByteBench-*Changed. Update receivers that check X-GitBench-Signature or X-GitBench-Event.
Flag SDK headerX-GitBench-SDK-KeyX-ByteBench-SDK-KeyChanged. The Authorization: Bearer form is unaffected.
Bot accountsgitbench-ai, gitbench-automation, gitbench-service-deskbytebench-*Renamed in place by a migration; their history is kept.
Backupsgitbench-backup-*.tar.gzbytebench-backup-*.tar.gzOld archives are still listed and can be restored.
Encryption namesGitBench…unchangedThe data-protection application name (DataProtection:ApplicationName, default GitBench) and the internal purpose strings keep their old spelling on purpose: changing them would make stored CI secrets, webhook secrets and tokens unreadable.

Access token prefixes (gbp_, gbj_, gbr_, gbsdk_) and the gb_pages cookie are unchanged, so existing tokens keep working.

Health checks

Both endpoints are anonymous, return JSON without error details and are not rate limited:

  • GET /health/live returns 200 while the process runs.
  • GET /health/ready checks that the database answers and the repository and attachment folders are writable (otherwise Unhealthy, HTTP 503), and, with CI on, that Docker is reachable (otherwise Degraded, still 200).

The image's HEALTHCHECK and the compose file both call /health/ready every 30 seconds with curl.

The /admin/system page

Site admins get an operator's overview at /admin/system:

  • Server: version, runtime, OS, uptime, memory.
  • Database: provider, target (never the password), server version, size, applied and pending migrations.
  • Health: the checks behind /health/ready.
  • Storage: files and bytes per folder (measured on demand, cached for a minute).
  • Queues: webhook deliveries waiting, CI pipelines queued and running, merge queue entries, pending email and chat notifications, and failures in the last 24 hours.
  • Backups: schedule, folder, count and size, last success and last error.
  • Hosting checks: the same review that runs at start-up and goes to the log.

Logs

Production logs are JSON lines on stdout. ByteBench does not rotate them: the compose file sets the Docker json-file driver with max-size: 20m and max-file: 5; journald and Kubernetes have their own limits. Keep Logging:LogLevel:Default at Information. Data that grows inside the database has retention settings: Audit:RetentionDays (365) and Retention:WebhookDeliveryDays (30).

Production checklist

The start-up review warns about most of these and lists them on /admin/system.

  1. TLS at a reverse proxy; PublicBaseUrl is the public https:// URL.
  2. ReverseProxy__Enabled=true and the proxy listed in KnownProxies or KnownNetworks.
  3. AllowedHosts set to your host name.
  4. DataProtection:KeysPath on a persistent volume that is backed up; consider a certificate to encrypt it.
  5. Seed:DemoData is false (the image default). The demo users share a published password.
  6. First admin created with Bootstrap__AdminUsers.
  7. Backup__Enabled=true, archives on another disk, a restore tested.
  8. Rate limits left on (RateLimiting:Enabled).
  9. Logs rotated; log level Information.
  10. Exactly one ByteBench instance.
  11. If CI is on: understand that pushers can run code on the Docker host; prefer a separate Docker host.
  12. If you use email, set the Email__* keys and test with a real notification.
  13. Open ports: 443 (and 80 for certificates) for the proxy; 2222 or 22 if you offer Git over SSH.
