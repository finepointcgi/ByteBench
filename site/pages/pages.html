Static sites (Pages)

Publish a folder of HTML, CSS and JavaScript from a CI job as your repository's website, with versions you can roll back and temporary review sites for branches.

Quick start

Add a job named pages to .bytebench-ci.yml that leaves its files in public/, and push to the default branch:

jobs:
  pages:
    image: python:3.13-alpine
    steps:
      - run: mkdir -p public && echo '<h1>Hello</h1>' > public/index.html

When the job passes, the site is live. Open it from the Site button in the repository header, or from Repository → Settings → Pages (/p/{KEY}/repos/{slug}/settings/pages). By default only people who can view the project can open it.

The pages job keyword

Any of these forms turns a job into a publishing job. It publishes after its steps succeed, so build the site in the steps.

FormMeaning
A job named pagesImplicitly publishes public/.
pages: truePublishes public/ from any job name.
pages: distPublishes the folder dist/.
publish: distAlias for pages: { path: dist }. Using both pages and publish is an error.
pages: { path: dist, review: true, expire_in: 3d }Full form. path defaults to public; review allows review sites; expire_in (e.g. 12h, 3d, 2w) sets how long a review site lives.
pages: falseSwitches off the implicit publishing of a job named pages.

The folder must be a plain relative path (no * or ?, no ..) and must not be, or sit inside, a symbolic link. Unknown keys inside the mapping are errors (use path, review or expire_in).

A Pages job does not need artifacts: ByteBench reads the folder straight from the job's workspace. It runs after the job's steps, cache and artifacts are handled. If publishing fails (folder missing, empty, over a limit, unsafe contents) the job fails with an explanation in its log. If the job simply isn't allowed to publish (see below), it passes and the log says why nothing was published.

Which pipelines publish

  • Default branch (and not a pull request pipeline): replaces the main site.
  • Any other branch or a pull request pipeline: only with review: true on the job, and only if review sites are allowed on the server (Pages:ReviewSites) and for the repository. Otherwise nothing is published and the log says so.
  • Fork pull request pipelines never publish.
  • If the repository's Pages are disabled in settings, or Pages:Enabled is false on the server, jobs pass without publishing.

Review sites

With review: true, a feature branch's pipeline publishes to its own address and the site expires automatically (default 7 days, from the repository's Pages settings, or the job's expire_in; the setting accepts 1 to 365 days). Each branch gets a name made of lowercase letters, digits and -; names that change or get too long get a short hash so two branches never collide. Review sites keep only their last 2 versions.

jobs:
  pages:
    steps: [ { run: ./build-site.sh } ]
    pages: { path: public, review: true, expire_in: 3d }

Where the site lives

ModeMain siteReview site
Path mode (always available unless disabled)https://bytebench.example.com/pages/WEB/web-app/https://bytebench.example.com/pages/WEB/web-app/-/r/feature-login/
Host mode (when Pages:BaseDomain is set)https://web-app.web.pages.example.com/https://feature-login.web-app.web.pages.example.com/

Host mode is {slug}.{key}.{BaseDomain} (project key lowercased). It needs wildcard DNS and a wildcard TLS certificate for *.*.pages.example.com pointing at ByteBench (a reverse proxy usually does this), because each site gets its own origin. Repository slugs containing . or _ are not valid host names and stay path-only. Set Pages:PathModeEnabled=false to serve only dedicated hosts.

Behaviour of the server: index.html for folders, clean URLs (/about serves about.html), 404.html when present, optional single-page-app fallback, ETag/If-None-Match, byte Range requests and HEAD. The top-level folder named - is reserved in path mode.

Who can open a site

SettingMeaning
Members (default)Everyone who can view the project, signed in. Checked on every request, so removing a member ends their access at once.
PublicAnyone on the internet, no sign-in. Only a project Owner can switch to it, and Pages:AllowPublic=false forbids it for the whole server.

Other settings on the Pages settings page (Maintainer or Owner): enable or disable Pages for the repository, what unknown addresses do (show the site's 404.html, or always a plain 404), a single-page-app option (serve index.html for paths without a file extension), whether review sites are allowed and for how many days, and Delete site.

A signed-in person who can see the project but not the site gets a 404; an anonymous visitor to a members-only site is sent to sign in, which reveals that the address exists.

How sign-in works for members-only sites. On a dedicated host, an unauthenticated visitor is bounced to ByteBench's sign-in, which hands back a one-minute signed code; the site's host then sets its own host-only gb_pages cookie that lasts Pages:HostCookieHours (8). In path mode, a visit with the ByteBench cookie is redirected to a URL containing a signed token (/-/t/{token}/..., valid Pages:PathTokenMinutes, 60) because the sandbox below prevents sub-requests from carrying cookies; relative links keep working but don't share that link publicly, it grants access until it expires.

Why sites can't hurt ByteBench (plain terms)

A Pages site is whatever HTML and JavaScript someone pushed. If it ran with ByteBench's privileges it could read other people's cookies or call the API as them. ByteBench prevents that in two ways, depending on mode:

  • Host mode: each site has its own host name, so the browser's normal same-origin rules already keep it apart from ByteBench. ByteBench's sign-in cookie is never sent to site hosts and is ignored there. Put Pages:BaseDomain on a registrable domain (or a Public Suffix List entry) different from ByteBench's so one site can't set cookies for the others or for ByteBench.
  • Path mode: the site shares ByteBench's address, so every response carries Content-Security-Policy: sandbox allow-scripts allow-forms allow-popups ... without allow-same-origin. The page runs in an "opaque origin": scripts work, but they can't read ByteBench cookies or storage or call its API as you. The side effect is that a site's own localStorage, cookies and same-origin requests don't work in path mode. Use host mode for sites that need them.
  • Always: X-Content-Type-Options: nosniff, a restrictive Permissions-Policy, and no Set-Cookie from ByteBench except the host sign-in cookie. Pages responses set their own full header set; ByteBench's own CSP is unchanged.
  • Uploads are checked: the whole archive is refused for .., absolute, drive-letter or backslash names, symlinks and other non-regular entries, duplicates (also by case), and file/folder name clashes. Symlinks in the workspace are skipped and nothing is ever served through a link.

Versions and rollback

Each successful publish is a numbered version. A deployment is packed, unpacked into a staging folder, renamed, and only then made current with one database save, so visitors see the old site or the new one, never a half-written one. A failed deployment leaves the live site untouched.

  • The last Pages:KeepVersions (default 10) main-site versions are kept; review sites keep 2.
  • On the Pages settings page, the Deployments list shows each version with its commit, branch, file count and size. Roll back to this makes an older version live again (Maintainer or Owner). Rolled-back versions are labelled.
  • Audit events: pages.deployed, pages.rolled_back, pages.settings_updated, pages.deleted.
  • Webhook pages.deployed (also for rollbacks): site: { url, visibility, slot } and deployment: { id, version, slot, ref, commitSha, fileCount, sizeBytes, isRollback, pipelineId, jobId, createdAt, expiresAt }. Whoever triggered the pipeline also gets a "Pages deployed" notification.

Example with host mode on (as environment variables: Pages__BaseDomain, and so on):

"Pages": {
  "BaseDomain": "pages.example.com",
  "AllowPublic": false,
  "KeepVersions": 20
}

Also set PublicBaseUrl so links in the UI and webhooks are absolute; the scheme and port of a dedicated host follow it.

Troubleshooting

Log line or symptomCause
"not published: 'feature-x' is not the default branch"Add review: true to the job, or merge to the default branch.
"folder 'public' was not found in the workspace (or is a symbolic link)"Your steps didn't create the folder, or it is a symlink. The job fails.
"not published: ... limit"Over MaxFiles, MaxSiteBytes or MaxFileBytes.
Site's login or storage doesn't work in path modeThe sandbox blocks cookies and localStorage. Enable host mode.
404 for a signed-in colleagueThey can't view the project, or Pages is disabled for the repository.
