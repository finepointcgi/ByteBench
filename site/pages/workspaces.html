Workspaces

A private development environment per user: a Docker container with the repository checked out and VS Code in the browser (OpenVSCode Server), an integrated terminal, previews of the ports your app listens on, an AI assistant that works inside the container, and a commit and push helper. Everything is reached through ByteBench.

Opening a workspace

Click Open in workspace on a repository's Source page (it uses the branch or tag you are viewing), on a pull request (its source branch; for a fork pull request, the branch in the fork) or on an issue (you pick the repository, and the issue key is recorded as the source). A start page lets you change the branch, tag or commit, then Open in workspace starts the container; the workspace page shows progress and the IDE appears when it is ready. Workspaces in the side menu lists yours.

Anyone who can view the project can start one. Whether it may push is decided at the start: Developers and above on a writable repository get a token that can push; Viewers, archived repositories and pull mirrors get a read-only token. The role is checked again on every push.

Set-up: nothing to do

If Docker is reachable (the docker CLI and its daemon), workspaces are on, and ByteBench builds the workspace image from docker/workspace/ in the background shortly after startup (or when the first workspace is requested). Progress and any error are shown on the start page and on Admin → Workspaces, whose health table lists: Docker reachable, image present, the reaper's last pass, how workspaces are reached and the limits in force. If Docker is missing the buttons explain it; nothing else breaks.

The image (bytebench-workspace:2, set with Workspaces:Image) contains git, node, python, make and g++ and OpenVSCode Server 1.109.5, downloaded in the Dockerfile and checked against a pinned SHA-256 (the build fails on a mismatch). Repositories that name a toolchain get an image built from the same Dockerfile on the matching base (.NET, Node 22, Python 3.13, Go, Java 21, Rust), once, on first use. To make the default image the .NET one by hand: docker build --build-arg BASE_IMAGE=mcr.microsoft.com/dotnet/sdk:10.0 -t bytebench-workspace:2 docker/workspace.

On by default, bounded

The administrator switch (Admin → Workspaces) is on unless an administrator turns it off, and each project can turn workspaces and the assistant off in its settings (Maintainers and Owners). Being on by default is limited by: Docker having to be reachable, a per-user cap (MaxPerUser, 2) and a server cap (MaxTotal, 10), CPU, memory, process and disk limits, an idle timeout (30 minutes) and a maximum lifetime (8 hours). Workspaces can only be opened where a safe origin exists, see below.

The repository's environment: .bytebench/workspace.yml

A repository describes its own workspace in a file in the repository. Opening a workspace then gives a ready-to-run environment: the right toolchain, submodules, dependencies installed, one click to run the app and preview it. The start page shows what the file asks for (or what is wrong with it) before you open the workspace.

# .bytebench/workspace.yml
toolchain: node@22          # or: image: ... (admin must allow), dotnet@10, python@3.13, go, java@21, rust
setup:                      # run once after the checkout; output is shown on the workspace page
  - npm ci
tasks:                      # Run / Stop buttons, logs, port links
  run:
    command: npm run dev
    port: 5173
    preview: true           # opens the preview next to the IDE when the port is up (one task at most)
  test: npm test            # short form: name: command
ports: [9229]               # extra ports listed in the Preview menu
env:                        # plain variables (no secrets: use workspace secrets)
  NODE_ENV: development
submodules: true            # default true
services:                   # sidecars on a private network, reachable by name
  db:
    image: postgres:17
    env: { POSTGRES_PASSWORD: dev }
    ports: [5432]           # optional for postgres, redis, mysql, mariadb, mongo, rabbitmq, memcached, ...
  • Toolchains come from a curated list that the server pins: dotnet@10, node@22, python@3.13, go, java@21 (JDK and Maven) and rust. Each gets a workspace image built on demand from docker/workspace on the matching base image and cached (bytebench-workspace:2-node22); the first start of a toolchain takes a few minutes and the page shows the build output. image: names your own base image (it must be Debian or Ubuntu based) and is ignored, with a visible note, unless an administrator turns on Let repositories choose their own base image under Admin → Workspaces (off by default). A repository's own Dockerfile is never built.
  • Setup runs after the IDE is up, one command at a time with bash -c inside the container, exactly as written. Output streams to the Tasks & setup panel; a failing command is shown with its exit code, stops the setup and leaves the workspace usable; Run again repeats it. Setup runs again only when the setup block changes (a hash of the commands and toolchain is stored in the workspace's volume), so stopping and resuming keeps what was installed.
  • Tasks run as processes inside the container as your user, from the repository directory, with the environment file sourced (cache locations, env: and your secrets). Output is capped (the newest 256 KB are kept) and secret values are masked. Stop ends the whole process tree. A task with preview: true opens the preview beside the IDE as soon as its port listens; every task port and ports: entry is in the Preview menu, served through the same proxy as before. Reload in the panel re-reads the file after you edit it in the IDE.
  • Submodules are fetched recursively when submodules is on (the default). A relative URL (../lib.git) or one that names this ByteBench server is fetched with the workspace's token, read-only, for the submodules of repositories you can view; the credential is stored in git's credential store for ByteBench's own host only, so it is never sent anywhere else. A submodule on another host is fetched anonymously; if that fails (private, offline, slow), the page lists the submodule's path and the reason and the workspace still opens. Only http(s) transports are allowed, each submodule has a time limit (Workspaces:SubmoduleTimeoutSeconds).
  • Services start before the checkout on a private per-workspace Docker network (--internal: no way out), with the workspace attached, reachable by their name (postgres://db:5432). The workspace's network policy allows only those addresses and ports in addition to the git endpoint. The start waits until each port accepts connections and fails with a clear message if not. Services are removed when the workspace stops; their data is not kept.
  • devcontainer.json (.devcontainer/devcontainer.json, .devcontainer.json or devcontainer.json) is read when there is no .bytebench/workspace.yml: image, forwardPorts, postCreateCommand (also onCreateCommand, updateContentCommand), containerEnv and remoteEnv. features, build/Dockerfile and compose are not run, runArgs/mounts are ignored; each is listed as a note on the page.
  • Validation is strict: unknown keys, bad image names, ports below 1024 or the IDE's own port, reserved variable names (PATH, HOME, BB_*, GIT_*, LD_*, DOCKER_*, …), too many or too long entries and files over 64 KB are refused with a message per problem. A refused file never stops the workspace from opening: it opens with the default setup and the errors on the page. Nothing from the file is placed in a host command or a Docker argument except validated image names, ports and variable names; commands only ever run inside the container.
  • No file? The start page and Repository settings → Workspaces recognise .NET (*.sln/*.csproj), Node (package.json), Python, Go, Rust and Java (pom.xml/Gradle) repositories and suggest a file; Add .bytebench/workspace.yml opens the web editor with it ready to commit.

Stop, resume and delete: dependencies stay

Each workspace has two named Docker volumes: the project (/workspace) and the dependency caches (~/.bbcache, which NuGet, npm/yarn/corepack, pip, Cargo, Go modules and build cache, Gradle and Maven are pointed at). Stop removes the container, its services and its network but keeps the volumes, so Resume brings back the same checkout (uncommitted work included), node_modules and caches, and setup does not run again. The volumes are deleted when you Delete the workspace, or Workspaces:VolumeRetentionDays (14) after it stopped; volumes that belong to no workspace are removed by the reaper. A start that fails before it ever ran leaves nothing behind. Admin → Workspaces → Disk use lists every volume with its size and owner. (Prebuilds, ready-made environments shared between users, are not implemented.)

Secrets

Account → Workspace settings holds your secrets; Repository settings → Workspaces holds the repository's (Maintainer and above). They are encrypted at rest (ASP.NET Core Data Protection, as CI variables), never shown after saving, never written to logs or the audit log (only the name), and masked as *** in task output and in what the assistant sees. When a workspace starts they are written, with the file's plain env:, to ~/.bb-env (mode 600, owned by your user, not readable by the assistant's user) through standard input, never a command line or docker run -e; tasks and terminals source it, so they are environment variables there. They are not in the repository, a URL or a preview. A user's secret overrides a repository secret of the same name. Repository secrets reach only users who can push: a read-only visitor gets their own secrets but not the repository's. Changes apply to workspaces that start afterwards. Anyone with a shell in the workspace can read its variables, so a secret is as private as the code you run in it.

Your settings and shell

Account → Workspace settings also takes extra VS Code settings.json content (up to 16 KB, comments allowed) and a shell snippet (up to 8 KB, sourced by your terminals). Both are applied when one of your own workspaces starts and are never visible to anyone else.

Using the IDE

The toolbar above the IDE has:

  • Preview: lists ports something in the container is listening on (checked every few seconds); choosing one opens it in a panel next to the IDE, or in a new tab. Servers bound to 127.0.0.1 work too.
  • AI: the assistant panel (see below).
  • Commit & push: shows git status, takes a message and commits everything as you; Commit & push pushes to the workspace's branch or to a branch name you type. A protected branch refuses the push (server-side), so type a new branch name and open a pull request.
  • The git bar: the branch (with how far it is ahead of or behind its remote, or "not pushed"), the number of changed files and, when the workspace was opened for an issue, that issue. Commit opens the commit dialog, Push pushes the current branch with the workspace's own git token, and Open PR pushes and opens a pull request into the default branch (or a branch you type) with a title and description. If the workspace was opened for an issue, the description names it (Fixes KEY-12, or Related to KEY-12 if you untick "close when merged"), which links the pull request to the issue. An open pull request for the same branch is shown instead of a duplicate. Uncommitted changes are refused (a pull request only contains commits).
  • Open in local editor: connect VS Code (Remote - SSH) or JetBrains Gateway on your own computer (below).
  • New tab, Restart (restarts the container: files stay, running processes end; the network policy is applied again before the IDE returns) and Stop (deletes the container and everything in it: push first).
  • Tasks: the tasks and setup panel (Run, Stop, status, live log tail, port links).
  • New tab, Restart (restarts the container: files stay, running processes end; the network policy is applied again before the IDE returns) and Stop (removes the container; the files and dependencies are kept so you can Resume until they expire, see above; push what matters anyway).

A workspace stops by itself after the idle timeout (no proxied request and no IDE traffic), at its maximum lifetime, or when ByteBench restarts. All stops are audited with the reason.

Start a workspace from an issue or a pull request

Start workspace on an issue page opens (or resumes) a workspace on a branch named from the issue: KEY-12-fix-login (the key, then the title as a lower-case slug of at most 40 characters). The branch is reused if it exists; otherwise it is created from the repository's default branch (this needs push permission and follows branch protection). A project with several repositories asks which one (repo in the API). Start workspace on a pull request page opens the source branch (pull requests from forks aren't supported). If you already have a live workspace on that branch you get that one back instead of a second. The workspace is linked to the issue or pull request: its git bar shows the issue, the issue page offers Resume workspace, and the pull request opened from the workspace names the issue.

Connect your own editor (VS Code, JetBrains Gateway)

Off by default: an administrator switches Local editors on under Admin → Workspaces. Open in local editor on the workspace page then explains the steps.

  • How it works. Both editors speak SSH. An OpenSSH server is started inside your workspace on demand, as the unprivileged coder user, listening on 127.0.0.1:2222 of the container only, with key login only (no passwords, no root). Nothing is published on the server. Your editor reaches it through ByteBench over a WebSocket (/api/v1/workspaces/{id}/editor/tunnel, so it passes the same TLS and reverse proxy as the web UI) using the bytebench workspace tunnel command as its SSH ProxyCommand.
  • Steps. Install the bytebench command line and sign in with a personal access token that has the write_api scope. In the panel (or with bytebench workspace connect <id> --key ~/.ssh/id_ed25519.pub) allow your public key, add the printed block to ~/.ssh/config, then in VS Code run "Remote-SSH: Connect to Host…" or in Gateway choose SSH → OpenSSH config.
  • Credentials. Your public key is installed in that workspace only, for at most 8 hours and never past the workspace's own end (expiry-time); the line is rebuilt from the key so no options can be smuggled in. The page never shows a token or a private key. The tunnel only accepts a personal access token (not a browser session), only for the workspace's owner, and at most 8 tunnels per workspace at a time. Audited: workspace.editor_key_added, workspace.admin_editor_switch.
  • Limits. The editors download their remote components inside the workspace, so the server's network mode must allow the internet (public-only, not none). The workspace image needs openssh-server (rebuild it from docker/workspace if yours is older).

The AI assistant

The panel next to the IDE uses ByteBench's AI (the Anthropic API with the editor's tool loop; Claude Code is not used here) with tools that run in the container through docker exec: list_files, read_file, write_file, edit_file, search_code, run_command and run_task (runs one of the repository's tasks, listed in its prompt, and returns its status and masked output).

  • It never commits or pushes. Its commands run as a separate unprivileged user (bbai) that cannot read your git credentials or git configuration, and commands that try git commit, push, fetch, remote, config and similar are refused before they run. You review the changes (the working tree and git diff) and commit them yourself.
  • Limits: paths must be relative and are checked twice (in ByteBench, then in the container after symlinks are resolved: no .., absolute paths, symlinks out of the checkout or anything under .git); commands have a time limit (60 s) enforced inside the container, and output, file reads and writes are capped. File contents, search results and command output are put in delimited untrusted blocks and the model is told they are data, not instructions.
  • Switches: Ai:Enabled and an API key; Admin → Workspaces (assistant switch); the project's setting; a per-user rate limit (Workspaces:Ai:RequestsPerMinute, 6) separate from the web editor's; tool-call and token budgets per request. Usage is logged as workspace.chat.
  • Audit: each request that used tools records workspace.ai_tools with the tool counts and the first word of each command, never file contents or output.

Review mode: accept or reject the AI's edits

By default the assistant does not edit your files directly. write_file, edit_file and the new delete_file propose changes, which appear in the review panel inside the AI panel as a pending change set with a diff per file. You accept or reject each file, pick individual hunks, or accept all; accepted text is written into the workspace (through the same checked, unprivileged tools as before) and rejected changes are discarded. A file that changed in the workspace after the proposal is shown as a conflict and nothing is written over it. While proposals are pending, run_command still sees the unchanged files; the assistant is told so.

  • Setting: Review first (default) or Apply directly per workspace, or as your default for every workspace (the checkbox in the panel, or PUT /api/v1/workspaces/{id}/ai/settings).
  • Audit: workspace.ai_changes_proposed, workspace.ai_change_applied, workspace.ai_change_rejected, workspace.ai_change_conflict, workspace.ai_changeset_resolved, workspace.ai_mode. In apply-directly mode workspace.ai_tools lists the paths written or deleted. Only the owner sees or decides a change set.

Task-driven AI runs on issues

Assign an issue to ByteBench AI (bytebench-ai) or press Let AI work on this on the issue. The run is queued, then the AI user starts its own workspace on a new branch named from the issue (ai/{key}-{number}-{title}), works the issue with the assistant's tool loop (read and edit files, run builds and tests), and ByteBench itself commits, pushes the branch and opens a pull request that Fixes the issue, comments on the issue with the summary and stops the workspace. The issue page shows the status and a link to the run page (/ai-runs/{id}) with the log, counters, the pull request and a Cancel button.

  • Permissions: the AI user must be a member of the project with the Developer role (the issue page offers to add it): it can do no more than that role allows, and its git token is the workspace's (one repository, only while the run lasts). Starting a run needs EditIssues. The model never commits or pushes and never sees a credential: tool output and the log are masked, issue text is handed over as untrusted data.
  • Limits (Workspaces:AiRuns): MaxConcurrent (2) runs at once, MaxQueued (20), MaxRunsPerProjectPerDay (30), MaxDurationMinutes (30), MaxSteps (40 model turns), MaxToolCalls (150), MaxTokens (1.5 M), MaxCostUsd ($5, from the configured token prices). A run that hits a limit stops, says so on the issue and, if it already changed files, opens a draft pull request with the work so far. Failures (workspace, model, push, pull request) and cancellations comment on the issue; a server restart fails runs in flight.
  • Switches: Workspaces:AiRuns:Enabled, a site setting, the workspace switches, and one working backend (below).
  • Backend: Workspaces:AiRuns:Backend is auto (default), api or claude-cli; a site administrator can override it under Admin → AI, which also shows which backend is active and why, or why runs are unavailable when neither exists. auto uses the Anthropic API when a key is configured and otherwise the Claude Code CLI when it is installed on the server (Ai:ClaudeCode:Path) and signed in; api and claude-cli never fall back to the other. The run page names the backend that did the run. The CLI backend lets a run use the server account's Claude subscription instead of an API key.
  • Audit: ai_run.requested, ai_run.refused, ai_run.cancel_requested, ai_run.finished, ai_run.admin_backend, plus the workspace and git events. Usage is logged as workspace.run (API) or workspace.run.claude-cli.

The Claude Code CLI backend: why it runs on the host

The CLI is not run inside the workspace container. Its login (a subscription credential) is long-lived and the container runs the repository's own code (builds, tests, setup commands), which would be able to read it; and the workspace network is restricted, so the CLI could not reach Anthropic from there anyway. Instead claude -p --output-format stream-json runs on the server, in an empty private directory (mode 700, deleted afterwards), with a clean environment (the server account's Claude login only; no ByteBench secrets, connection strings or API keys) and every built-in tool switched off (--tools "", a deny-list, --strict-mcp-config, dontAsk permissions, nothing prompts). Its only tools are the run's own, served by ByteBench to the CLI over MCP on 127.0.0.1 for the life of the run: the same eight tools as the API backend (list_files, read_file, search_code, write_file, edit_file, delete_file, run_command, run_task), executed inside the run's workspace container through the workspace exec path as the unprivileged bbai user. So the run uses the repository's real toolchains, services and tasks; it can only touch its own workspace; and the CLI's credentials are never in the container, never in a tool's output and never reachable by repository code. There is no commit, push or pull request tool: ByteBench does those afterwards, exactly as for API runs.

  • Bridge security: the bridge needs a per-run random bearer token (kept in a 0600 file in the private directory, not in the CLI's environment, command line or prompt), checks the Host header (no DNS rebinding) and rejects browser requests, serialises tool calls, caps them at MaxToolCalls and closes when the run ends. Tool output is masked for tokens, keys and the workspace's secret values before the model sees it, and is wrapped in UNTRUSTED blocks like the API backend's; the issue and its comments are handed over on stdin as UNTRUSTED blocks with a random boundary.
  • Limits are the same ones: MaxDurationMinutes (the process tree is killed), MaxSteps (model messages seen on the stream; also passed as --max-turns), MaxToolCalls (tool calls seen on the stream, and refused by the bridge past the limit), MaxTokens and MaxCostUsd (from the usage events; the CLI's own total_cost_usd replaces the price-based estimate when it reports one; also passed as --max-budget-usd when the CLI lists it). With a subscription the cost is the API-equivalent estimate, not a charge. Cancel and the time limit kill the CLI and everything it started. Stopping on a limit keeps the work as a draft pull request, as before.
  • Review: as for API runs, edits take effect in the run's ephemeral workspace at once (there is no per-edit approval, because nobody is there to give it); the review is the pull request ByteBench opens from the resulting diff. The editor assistant's accept/reject review mode applies to people working in a workspace, not to runs.
  • The server account's Claude settings apply. The CLI runs as the account ByteBench runs as and reads that account's Claude settings and login; use a dedicated account for ByteBench. The CLI stays logged in on the server only: sign in once with claude as that account (or set CLAUDE_CODE_OAUTH_TOKEN for the ByteBench process). Subscription limits are shared by every run; lower MaxConcurrent if you hit them.

How it is secured

Containers

Each workspace container runs as uid 1000, with every capability dropped, no-new-privileges, never privileged, with no host mounts and never the Docker socket, and with memory (swap off), CPU and process limits (and a disk limit where the Docker storage driver supports --storage-opt size=; where it does not, ByteBench logs a warning and starts without). IPv6 is off. Workspaces sit on their own Docker network with inter-container traffic switched off. Orphans are removed at startup and by a periodic reaper.

Network egress

The container starts idle. ByteBench applies the network policy from a separate throw-away helper container that shares its network namespace (the workspace itself never holds NET_ADMIN, so its user cannot undo the rules), and only then checks out the repository and lets the IDE start, so there is no unrestricted window. Workspaces:EgressMode:

  • public-only (default): the internet is open; private, link-local, CGNAT, loopback and multicast ranges are rejected, which includes the Docker network, other workspaces and the ByteBench host. Only ByteBench's git endpoint (one address and port) stays reachable.
  • none: only the git endpoint. open: no restrictions (not recommended).

Limits: the policy is IPv4 and IP-based (a hostname that resolves to a private address is blocked by its address); it does not stop data leaving to the internet in public-only mode; and it is only as strong as the Docker host's kernel and Docker itself, so use a dedicated Docker host for untrusted code.

Allow-list egress and repository rules

Besides the modes above, an administrator can choose allowlist under Admin → Workspaces: the container can then reach only ByteBench's git endpoint and a filtering proxy inside ByteBench. The list holds hosts with optional ports (registry.npmjs.org, git.example.com:2222, *.example.com) and presets (@git, @npm, @nuget, @pypi, @crates, @go, @maven); without a port, 80 and 443 are meant. A repository can add egress: to .bytebench/workspace.yml (egress: none or egress: [registry.npmjs.org]), but it can only narrow what the administrator allows: anything wider is dropped and shown as a warning on the workspace's Network tab, which also lists blocked requests (they are audited too).

Limits: tools must use the proxy environment variables (git, npm, pip, cargo, go, curl and dotnet do; Maven needs a settings.xml); raw TCP such as an SSH git remote cannot connect; HTTPS is tunnelled, so the host name is what is enforced, not the content.

The IDE and previews are only reachable through ByteBench

The only thing a container publishes is the IDE port on 127.0.0.1 of the Docker host (or nothing at all with IdeTransport: Relay, which relays through the container and is chosen automatically when ByteBench itself runs in a container or DOCKER_HOST is set). ByteBench's proxy handles HTTP and WebSocket and checks that the signed-in user owns the workspace.

  • Subdomain mode (recommended): the IDE is ide-{id}.{BaseDomain} and a preview of port 3000 is p3000-{id}.{BaseDomain}, each its own origin, with a random 100-bit id. Point a wildcard DNS name and certificate (*.{BaseDomain}) at ByteBench and set Workspaces:BaseDomain. In Development it defaults to localhost. ByteBench's session cookie is host-only, so it is never sent to these origins, and scripts in a workspace cannot read or act on ByteBench's origin. A signed-in user gets a single-use link (60 seconds) from ByteBench; the workspace origin turns it into its own host-only, HttpOnly session cookie (SameSite=None; Secure; Partitioned where the browser accepts it, because the IDE is shown in an iframe of ByteBench's page). The OpenVSCode connection token is random per workspace and injected by the proxy: the browser never has it. Upstream X-Frame-Options is replaced by a CSP frame-ancestors naming ByteBench.
  • Shared-origin mode (only with Workspaces:AllowSharedOrigin: true and no base domain): /_ws/{id}/ide/ and /_ws/{id}/p3000/ on ByteBench's own origin, authenticated by the normal session; every cookie is stripped before the request goes upstream and previews are served with CSP sandbox (an opaque origin: no cookies, no access to ByteBench), but the IDE cannot be sandboxed, so code running in the workspace can act as the signed-in user in ByteBench. Use it only for code you trust. Without either setting, workspaces cannot be opened and the page says why.

Git access

The container clones from ByteBench's own git endpoint with a token gbw_… made for that workspace: valid for that one repository (and read-only for its submodules on this server), only while the workspace is starting or running, only for its owner, and revoked when it stops, fails or ByteBench restarts (only its SHA-256 is stored). It is not a personal access token and the REST API, MCP and the package registry do not accept it. It is written to ~/.git-credentials (mode 600) through standard input, never a command line or environment variable. Pushing needs a token that was created with write access and the owner's current PushCode, archived and mirror checks and branch protection, all enforced by the git endpoint on every push. No personal tokens or passwords are put in the container.

Prebuilds

A prebuild is a snapshot of a repository with the slow part already done: cloned, submodules fetched and the setup commands run. After a push to a prebuilt branch, ByteBench builds one in the background; a new workspace on that branch then starts from the newest prebuild and only has to fetch what changed since. With no prebuild, or a stale one, it starts exactly as before, and a failing prebuild never blocks a start.

  • Turn it on under Open in workspace → Prebuilds (Maintainer and Owner): enable it, pick the branches (names or patterns such as release/*; empty means the default branch), how many prebuilds to keep per branch (default 3) and for how many days (default 14). A branch is only prebuilt when it has a .bytebench/workspace.yml.
  • What runs: only the repository's own environment file at the pushed commit, with the same validation and image rules as a workspace (toolchain, or image when the administrator allows it). The setup commands run in the checkout and stop at the first failure; submodules are fetched unless submodules: false. services, tasks and secrets are not part of a prebuild.
  • Secrets are not baked in. The build container gets no workspace secrets and no environment beyond BB_*. Its read-only git token (one repository, only while the build runs) is deleted from the container before the setup commands run and again before the snapshot is taken.
  • History: every prebuild with its state (Queued, Building, Ready, Failed, Superseded, Expired), commit, trigger and full log. Rebuild now queues one at the branch's current tip; Clean up applies the keep-last and retention settings at once. A newer push replaces a queued build of the same branch.
  • Stale means ignored: a prebuild is not used when the setup, submodules or image changed since, it is older than the retention, or its image is gone. A workspace you resume from its saved files never uses a prebuild.

Resource limits and idle auto-stop

  • Limits per user (Admin → Workspaces): running workspaces, workspaces in total, CPUs and memory across running ones, and disk across all of them; 0 means no limit. The same page sets what each new workspace gets by default (CPUs, memory, disk). Stopped workspaces whose files are kept count toward the total and the disk. A start that would go over a limit is refused with a message that says which one and what to do (in the UI, and as 422 from the API). Changes apply to the next start. Never set, the limits come from Workspaces:MaxPerUser, Cpus, Memory and DiskLimit.
  • Your usage is on the Workspaces page next to the limits.
  • Idle auto-stop: a workspace with no IDE or preview traffic and no running task for the idle period is stopped (Stop keeps its files and volumes; resume it later). The administrator sets a default and a maximum; you can choose your own period on the Workspaces page, up to that maximum. The workspace page warns a few minutes before and has Keep it running.

Sharing a workspace

Open Share & history on a running workspace and invite a ByteBench user who can already see the repository (by default a project member; an administrator can widen this to anyone who can view the repository, or turn sharing off).

  • Collaborator: full IDE access for pair programming, as a separate user. OpenVSCode has no multi-user mode, so each collaborator gets their own unprivileged user inside the container (own home, own terminals) and their own IDE server running as that user; they open it with their own single-use ticket and ByteBench's proxy sends them to it. You share the project files (through group permissions); there are no live cursors and terminals are not shared. A collaborator cannot read your home folder: your ~/.bb-env (the secrets ByteBench injected), your git credential and your IDE token stay yours alone. Their git has no credentials unless you tick May push when inviting: then they get a credential of their own (their user name, this repository only, this workspace only, ended when you remove them or take the permission away), and a push is checked against their role and branch protection. They can still read and change everything in /workspace and run code in the container, so invite people you trust with that, and remember your own commands can't hide anything from them that you put in the project folder.
  • Viewer: read-only. They never get an IDE session; they browse files and read terminals you share through ByteBench. This is enforced on the server.

The panel lists who is connected. Removing someone, End sharing and stopping the workspace cut access at once, including open IDE connections. Invitees are notified and find the workspace under Shared with you.

Administration

  • Admin → Workspaces: the health table, the workspaces switch, the assistant switch, every workspace (owner, repository, state, activity) with Stop and Stop all. Administrators can stop any workspace but cannot open one.
  • Project settings → Workspaces (Maintainer and Owner): allow workspaces and the assistant for the project.
  • Local editors switch (off by default): see above.
  • Audit log: workspace.push, workspace.pull_request_opened, workspace.started, workspace.stopped (with reason and who), workspace.failed, workspace.restarted, workspace.commit, workspace.ai_tools, workspace.admin_switch, workspace.admin_ai_switch and workspace.project_settings.
  • Workspace audit (/admin/workspaces/audit): search every workspace event by workspace, person, action, text and date; export CSV; set how long events are kept. Each workspace also has its own History tab. Secrets are only ever recorded by name. Also available over the REST API.
  • Audit log: workspace.created, workspace.shared, workspace.share_ended, workspace.ticket_redeemed, workspace.egress_blocked, workspace.started, workspace.stopped (with reason and who), workspace.failed, workspace.restarted, workspace.commit, workspace.ai_tools, workspace.admin_switch, workspace.admin_ai_switch and workspace.project_settings.
  • Admin → Workspaces → Disk use: every workspace volume with size, owner and state, and a switch for repository-chosen base images.
  • Audit log: also workspace.resumed, workspace.deleted, workspace.task_started/task_stopped (task name), workspace_secret.created/updated/deleted (name only), workspace.user_settings and workspace.admin_custom_images. Earlier: workspace.started, workspace.stopped (with reason and who), workspace.failed, workspace.restarted, workspace.commit, workspace.ai_tools, workspace.admin_switch, workspace.admin_ai_switch and workspace.project_settings.

With Docker or docker-compose

ByteBench needs a Docker CLI and a daemon, exactly like CI pipelines. In the container image build with --build-arg WITH_DOCKER_CLI=true and give it the daemon: mount /var/run/docker.sock (anyone who can start a workspace is then bounded only by the container restrictions above, and ByteBench can control the host), or better set DOCKER_HOST to a separate Docker host over TLS. The workspace Dockerfile ships inside the image (/app/docker/workspace), so the image is built on first use. Set Workspaces:BaseDomain to a wildcard domain routed to ByteBench, and make the git endpoint reachable from workspaces: put ByteBench on the workspaces' Docker network and set Workspaces:GitBaseUrl to http://bytebench:8080. The compose file has the lines ready, commented out.

Troubleshooting

  • "Docker isn't available": the docker CLI must run as ByteBench's account and reach a daemon; see Admin → Workspaces.
  • The image never becomes ready: the build output (last lines) is on the admin page; the build needs internet access for the base image, the apt packages and the OpenVSCode download.
  • Clone fails with a connection error: containers must reach Workspaces:GitBaseUrl, so ByteBench must listen on an address the Docker network can reach, not only on 127.0.0.1 of a Linux host.
  • The IDE shows "Open this workspace from ByteBench": the link expired (60 seconds) or cookies for the workspace origin are blocked; use New tab.
