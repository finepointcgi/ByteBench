Workspaces

A private development environment per user: a Docker container with the repository checked out and VS Code in the browser (OpenVSCode Server), an integrated terminal, previews of the ports your app listens on, an AI assistant that works inside the container, and a commit and push helper. Everything is reached through ByteBench.

Opening a workspace

Click Open in workspace on a repository's Source page (it uses the branch or tag you are viewing), on a pull request (its source branch; for a fork pull request, the branch in the fork) or on an issue (you pick the repository, and the issue key is recorded as the source). A start page lets you change the branch, tag or commit, then Open in workspace starts the container; the workspace page shows progress and the IDE appears when it is ready. Workspaces in the side menu lists yours.

Anyone who can view the project can start one. Whether it may push is decided at the start: Developers and above on a writable repository get a token that can push; Viewers, archived repositories and pull mirrors get a read-only token. The role is checked again on every push.

Set-up: nothing to do

If Docker is reachable (the docker CLI and its daemon), workspaces are on, and ByteBench builds the workspace image from docker/workspace/ in the background shortly after startup (or when the first workspace is requested). Progress and any error are shown on the start page and on Admin → Workspaces, whose health table lists: Docker reachable, image present, the reaper's last pass, how workspaces are reached and the limits in force. If Docker is missing the buttons explain it; nothing else breaks.

The image (bytebench-workspace:1, set with Workspaces:Image) contains git, node, python, make and g++ and OpenVSCode Server 1.109.5, downloaded in the Dockerfile and checked against a pinned SHA-256 (the build fails on a mismatch). For the .NET SDK build it on an SDK base: docker build --build-arg BASE_IMAGE=mcr.microsoft.com/dotnet/sdk:10.0 -t bytebench-workspace:1 docker/workspace.

On by default, bounded

The administrator switch (Admin → Workspaces) is on unless an administrator turns it off, and each project can turn workspaces and the assistant off in its settings (Maintainers and Owners). Being on by default is limited by: Docker having to be reachable, a per-user cap (MaxPerUser, 2) and a server cap (MaxTotal, 10), CPU, memory, process and disk limits, an idle timeout (30 minutes) and a maximum lifetime (8 hours). Workspaces can only be opened where a safe origin exists, see below.

Using the IDE

The toolbar above the IDE has:

  • Preview: lists ports something in the container is listening on (checked every few seconds); choosing one opens it in a panel next to the IDE, or in a new tab. Servers bound to 127.0.0.1 work too.
  • AI: the assistant panel (see below).
  • Commit & push: shows git status, takes a message and commits everything as you; Commit & push pushes to the workspace's branch or to a branch name you type. A protected branch refuses the push (server-side), so type a new branch name and open a pull request.
  • New tab, Restart (restarts the container: files stay, running processes end; the network policy is applied again before the IDE returns) and Stop (deletes the container and everything in it: push first).

A workspace stops by itself after the idle timeout (no proxied request and no IDE traffic), at its maximum lifetime, or when ByteBench restarts. All stops are audited with the reason.

The AI assistant

The panel next to the IDE uses ByteBench's AI (the Anthropic API with the editor's tool loop; Claude Code is not used here) with tools that run in the container through docker exec: list_files, read_file, write_file, edit_file, search_code and run_command.

  • It never commits or pushes. Its commands run as a separate unprivileged user (bbai) that cannot read your git credentials or git configuration, and commands that try git commit, push, fetch, remote, config and similar are refused before they run. You review the changes (the working tree and git diff) and commit them yourself.
  • Limits: paths must be relative and are checked twice (in ByteBench, then in the container after symlinks are resolved: no .., absolute paths, symlinks out of the checkout or anything under .git); commands have a time limit (60 s) enforced inside the container, and output, file reads and writes are capped. File contents, search results and command output are put in delimited untrusted blocks and the model is told they are data, not instructions.
  • Switches: Ai:Enabled and an API key; Admin → Workspaces (assistant switch); the project's setting; a per-user rate limit (Workspaces:Ai:RequestsPerMinute, 6) separate from the web editor's; tool-call and token budgets per request. Usage is logged as workspace.chat.
  • Audit: each request that used tools records workspace.ai_tools with the tool counts and the first word of each command, never file contents or output.

How it is secured

Containers

Each workspace container runs as uid 1000, with every capability dropped, no-new-privileges, never privileged, with no host mounts and never the Docker socket, and with memory (swap off), CPU and process limits (and a disk limit where the Docker storage driver supports --storage-opt size=; where it does not, ByteBench logs a warning and starts without). IPv6 is off. Workspaces sit on their own Docker network with inter-container traffic switched off. Orphans are removed at startup and by a periodic reaper.

Network egress

The container starts idle. ByteBench applies the network policy from a separate throw-away helper container that shares its network namespace (the workspace itself never holds NET_ADMIN, so its user cannot undo the rules), and only then checks out the repository and lets the IDE start, so there is no unrestricted window. Workspaces:EgressMode:

  • public-only (default): the internet is open; private, link-local, CGNAT, loopback and multicast ranges are rejected, which includes the Docker network, other workspaces and the ByteBench host. Only ByteBench's git endpoint (one address and port) stays reachable.
  • none: only the git endpoint. open: no restrictions (not recommended).

Limits: the policy is IPv4 and IP-based (a hostname that resolves to a private address is blocked by its address); it does not stop data leaving to the internet in public-only mode; and it is only as strong as the Docker host's kernel and Docker itself, so use a dedicated Docker host for untrusted code.

Allow-list egress and repository rules

Besides the modes above, an administrator can choose allowlist under Admin → Workspaces: the container can then reach only ByteBench's git endpoint and a filtering proxy inside ByteBench. The list holds hosts with optional ports (registry.npmjs.org, git.example.com:2222, *.example.com) and presets (@git, @npm, @nuget, @pypi, @crates, @go, @maven); without a port, 80 and 443 are meant. A repository can add egress: to .bytebench/workspace.yml (egress: none or egress: [registry.npmjs.org]), but it can only narrow what the administrator allows: anything wider is dropped and shown as a warning on the workspace's Network tab, which also lists blocked requests (they are audited too).

Limits: tools must use the proxy environment variables (git, npm, pip, cargo, go, curl and dotnet do; Maven needs a settings.xml); raw TCP such as an SSH git remote cannot connect; HTTPS is tunnelled, so the host name is what is enforced, not the content.

The IDE and previews are only reachable through ByteBench

The only thing a container publishes is the IDE port on 127.0.0.1 of the Docker host (or nothing at all with IdeTransport: Relay, which relays through the container and is chosen automatically when ByteBench itself runs in a container or DOCKER_HOST is set). ByteBench's proxy handles HTTP and WebSocket and checks that the signed-in user owns the workspace.

  • Subdomain mode (recommended): the IDE is ide-{id}.{BaseDomain} and a preview of port 3000 is p3000-{id}.{BaseDomain}, each its own origin, with a random 100-bit id. Point a wildcard DNS name and certificate (*.{BaseDomain}) at ByteBench and set Workspaces:BaseDomain. In Development it defaults to localhost. ByteBench's session cookie is host-only, so it is never sent to these origins, and scripts in a workspace cannot read or act on ByteBench's origin. A signed-in user gets a single-use link (60 seconds) from ByteBench; the workspace origin turns it into its own host-only, HttpOnly session cookie (SameSite=None; Secure; Partitioned where the browser accepts it, because the IDE is shown in an iframe of ByteBench's page). The OpenVSCode connection token is random per workspace and injected by the proxy: the browser never has it. Upstream X-Frame-Options is replaced by a CSP frame-ancestors naming ByteBench.
  • Shared-origin mode (only with Workspaces:AllowSharedOrigin: true and no base domain): /_ws/{id}/ide/ and /_ws/{id}/p3000/ on ByteBench's own origin, authenticated by the normal session; every cookie is stripped before the request goes upstream and previews are served with CSP sandbox (an opaque origin: no cookies, no access to ByteBench), but the IDE cannot be sandboxed, so code running in the workspace can act as the signed-in user in ByteBench. Use it only for code you trust. Without either setting, workspaces cannot be opened and the page says why.

Git access

The container clones from ByteBench's own git endpoint with a token gbw_… made for that workspace: valid for that one repository, only while the workspace is starting or running, only for its owner, and revoked when it stops, fails or ByteBench restarts (only its SHA-256 is stored). It is not a personal access token and the REST API, MCP and the package registry do not accept it. It is written to ~/.git-credentials (mode 600) through standard input, never a command line or environment variable. Pushing needs a token that was created with write access and the owner's current PushCode, archived and mirror checks and branch protection, all enforced by the git endpoint on every push. No personal tokens or passwords are put in the container.

Sharing a workspace

Open Share & history on a running workspace and invite a ByteBench user who can already see the repository (by default a project member; an administrator can widen this to anyone who can view the repository, or turn sharing off).

  • Collaborator: full IDE access for pair programming. OpenVSCode has no multi-user mode, so the collaborator opens their own browser window on the same IDE server, with their own single-use ticket. You share the files on disk and, if you start tmux new -s main, terminals; there are no live cursors. A collaborator acts as the container's user and can push with your git token, so invite people you trust like yourself.
  • Viewer: read-only. They never get an IDE session; they browse files and read terminals you share through ByteBench. This is enforced on the server.

The panel lists who is connected. Removing someone, End sharing and stopping the workspace cut access at once, including open IDE connections. Invitees are notified and find the workspace under Shared with you.

Administration

  • Admin → Workspaces: the health table, the workspaces switch, the assistant switch, every workspace (owner, repository, state, activity) with Stop and Stop all. Administrators can stop any workspace but cannot open one.
  • Project settings → Workspaces (Maintainer and Owner): allow workspaces and the assistant for the project.
  • Workspace audit (/admin/workspaces/audit): search every workspace event by workspace, person, action, text and date; export CSV; set how long events are kept. Each workspace also has its own History tab. Secrets are only ever recorded by name. Also available over the REST API.
  • Audit log: workspace.created, workspace.shared, workspace.share_ended, workspace.ticket_redeemed, workspace.egress_blocked, workspace.started, workspace.stopped (with reason and who), workspace.failed, workspace.restarted, workspace.commit, workspace.ai_tools, workspace.admin_switch, workspace.admin_ai_switch and workspace.project_settings.

With Docker or docker-compose

ByteBench needs a Docker CLI and a daemon, exactly like CI pipelines. In the container image build with --build-arg WITH_DOCKER_CLI=true and give it the daemon: mount /var/run/docker.sock (anyone who can start a workspace is then bounded only by the container restrictions above, and ByteBench can control the host), or better set DOCKER_HOST to a separate Docker host over TLS. The workspace Dockerfile ships inside the image (/app/docker/workspace), so the image is built on first use. Set Workspaces:BaseDomain to a wildcard domain routed to ByteBench, and make the git endpoint reachable from workspaces: put ByteBench on the workspaces' Docker network and set Workspaces:GitBaseUrl to http://bytebench:8080. The compose file has the lines ready, commented out.

Troubleshooting

  • "Docker isn't available": the docker CLI must run as ByteBench's account and reach a daemon; see Admin → Workspaces.
  • The image never becomes ready: the build output (last lines) is on the admin page; the build needs internet access for the base image, the apt packages and the OpenVSCode download.
  • Clone fails with a connection error: containers must reach Workspaces:GitBaseUrl, so ByteBench must listen on an address the Docker network can reach, not only on 127.0.0.1 of a Linux host.
  • The IDE shows "Open this workspace from ByteBench": the link expired (60 seconds) or cookies for the workspace origin are blocked; use New tab.
