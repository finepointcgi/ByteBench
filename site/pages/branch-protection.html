Branch protection and merge queue

Protect important branches and tags so changes arrive only through reviewed pull requests, and optionally merge through a queue that tests every pull request on top of the ones ahead of it.

Branch protection rules

Rules are set per repository under Settings, Branch protection (/p/{KEY}/repos/{slug}/settings/branches). You need the Maintainer role or higher (ManageRepositories). Protected branches show a lock badge on the Branches page.

  1. Open the repository, then Settings, then Branch protection.
  2. Click Add rule and type a branch name pattern. The form lists the existing branches the pattern matches.
  3. Choose the options below and optionally the default reviewers, then Create rule.

Patterns

A pattern is an exact branch name (main) or a glob. * and ? stay inside one path segment (release/* matches release/1.0 but not release/1.0/hotfix); ** crosses /. Patterns cannot contain spaces or .., start or end with /, or start with refs/, and are at most 250 characters. There can be one rule per pattern.

When several rules match a branch, the strictest setting of each option wins: the highest required approvals, and any rule that turns an option on turns it on.

"Changes requested" by anyone always blocks merging into a protected branch, whatever the options. A draft can never merge, with or without protection. Rules and their changes are recorded in the audit log as branch_protection.created, .updated and .deleted.

Where rules are enforced

  • Git push over HTTP and SSH. Before git sees a push, ByteBench reads the ref updates and refuses deletes, creates and direct pushes with a normal report, so git prints ! [remote rejected] main -> main (branch 'main' is protected: changes must go through a pull request) and nothing is written. A force push can only be recognised once the data arrives, so for those branches a small pre-receive hook checks that the new commit descends from the old one (this needs git 2.31 or newer on the server).
  • Branch creation and deletion in the UI and API.
  • Pull request merges, direct and through the queue, which refuse with the list of reasons.
  • The web editor: committing to a branch with "block direct pushes" is refused and the editor offers a new branch plus pull request instead (see Web editor).

With Require signed commits the push is accepted only if a pre-receive hook can verify every new commit against the keys registered on ByteBench accounts (needs git 2.34 or newer on the server for SSH signatures, plus ssh-keygen and/or gpg). A refused push names the first commit and why, for example commit 1a2b3c4 on 'main' is not verified: it isn't signed. If the server has neither tool the push is refused with that explanation. Merges made by ByteBench itself are not pushes and are not signed; see ByteBench's own merge commits.

What about "push rules"?

ByteBench has no separate "push rules" feature (no commit message regexes, file size or author checks at push time). What is checked on every push, by every route, is: branch protection, protected tags, tags used by a release (cannot be deleted), archived repositories, and pull mirrors (read-only). Two further things are refused when any rule exists: signed pushes (git push --signed) because they cannot be checked, and any push to refs/merge-queue/, which belongs to the merge queue.

Admin bypass

Only rules with Allow admins to bypass can be bypassed, and only by site admins and project Owners. They then see Merge (bypass protection) on blocked PRs, can push directly, and (if the rule allows it) can merge directly into a branch that has a merge queue. Drafts cannot be bypassed. Deploy keys never bypass.

Protected CI variables

Branch protection also decides which pipelines see protected CI variables (CI pipelines). A protected variable reaches only pipelines whose branch matches a branch protection rule. Pull request pipelines run on the PR's source branch, so a PR from an unprotected branch never sees them, and a pipeline for a PR from a fork gets no variables at all. Merge queue pipelines run on a special ref but count as the target branch when it is safe: they must belong to an active queue entry, not come from a fork, and the person who queued the PR must still be allowed to merge in the project.

Delete source branch after merge

The merge box has Delete source branch after merging, and the queue has the same checkbox. It needs the Maintainer role, is not offered for the default branch or for fork PRs, and is refused if a rule with Block deletion matches the source branch.

Protected tags

Under Settings, Protected tags (.../settings/tags, Maintainer or Owner) a rule has a name pattern (exact, such as v1.0.0, or a glob such as v* or release/**) and:

OptionDefaultEffect
Allowed to createMaintainers and OwnersOr Developers and above. Deleting or moving a tag that is not blocked needs the same role
Block deletiononNobody, Owners included, can delete a matching tag while the rule exists
Block movingonNobody can move a matching tag to another commit (a forced tag push)

The strictest matching rule wins. Enforcement covers git push over HTTP and SSH (a refused tag prints ! [remote rejected] v1.0 -> v1.0 (tag 'v1.0' is protected: only Maintainers and Owners can create it); deploy keys count as Developers), the Tags page, the release form and the API. Independently of any rule, a tag used by a release cannot be deleted. Audit events: protected_tag.created, .updated, .deleted. See also Releases and tags.

Required status checks and pipelines

Turn on Require checks to pass to make external checks gate merging. The merge box shows each check's state: Passed, Pending, Failed or Neutral. A CI pipeline on the PR's head is the usual check (CI pipelines), and other features register their own, for example the Night Owl scan (Security scanning). Only Pending and Failed block. Without the option, the checks are shown but advisory.

A typical setup for main: required approvals 1 or 2, block direct pushes, block force pushes, block deletion, require checks, dismiss stale approvals, and require threads resolved. Leave "Allow admins to bypass" off unless you need an emergency path.

The merge queue

What it is and why use it

When many pull requests are ready at once, each one can pass its own tests and still break the branch once the others land. A merge queue fixes this: it tests each pull request merged on top of the target and on top of every pull request ahead of it, then fast-forwards the target branch in order. The branch only ever moves to commits that were tested exactly as they will land.

How it works

  1. A person with merge rights clicks Add to merge queue on a PR that passes every other check. The PR joins the end of its target branch's queue (each branch has its own queue).
  2. ByteBench builds a speculative commit for each of the first batch size entries: the target tip plus every entry ahead, merged with the configured method. It is stored under refs/merge-queue/{branch}/{id} and a pipeline runs on it.
  3. When an entry's pipeline passes it is Passed. The furthest passed entry merges together with every entry ahead of it (its commit already contains them): the target is fast-forwarded to that commit, only if the target has not moved meanwhile, and each PR is closed as merged by whoever queued it. Webhooks, CI, smart commits and notifications run as for a normal push, and queue pipelines no longer needed are cancelled.
  4. If the target moved, an entry ahead left, or the order changed, the affected entries are rebuilt automatically (their old pipelines are cancelled).

Entry states: Queued (waiting, or waiting for a place in the train), Testing (pipeline running, or waiting for approval), Passed, and the final states Merged, Failed and Removed. Queues are re-evaluated on every event and at least every MergeQueue:PollSeconds seconds, and survive restarts: everything is derived from the database and the repository.

Turning it on and settings

In a branch protection rule, tick Require a merge queue. Merging into matching branches then happens only through the queue; "Merge" becomes "Add to merge queue" (and a direct API merge is refused with a message pointing to the queue).

When several rules match a branch, the smallest batch size and timeouts win, CI is required if any rule requires it, and the merge method comes from the most specific rule that sets one (exact names before globs). Server settings: MergeQueue:Enabled (default true, runs the background processor) and MergeQueue:PollSeconds (default 15).

Queue pipelines pick their jobs as if they ran on the target branch, so rules and only in your CI file that select main will apply. Make sure at least one job runs there, or the queue reports that no job runs on the branch.

Queueing a pull request

  1. Open the PR. The merge box shows the queue section with the merge method and settings.
  2. Optionally tick Delete source branch after it merges.
  3. Click Add to merge queue. You need the Maintainer role. The PR must be open, not a draft, merge cleanly, and pass every other merge check (approvals, threads, code owners, required checks, with admin bypass counting).
  4. Follow progress on the PR ("#2 of 4 in the merge queue of main") or on the queue page /p/{KEY}/repos/{slug}/merge-queue, which updates live and lists active and recent entries per branch.
  • Remove from queue: the PR's author or any Maintainer. Entries behind it are tested again without it.
  • Move to front: Maintainers only (ManageRepositories). Everything behind the moved PR is rebuilt.

Failure and ejection

An entry is ejected (state Failed or Removed), its pipeline and speculative ref are cleaned up, the PR gets an activity line, the person who queued it gets a notification, and everything behind it is rebuilt without it. Reasons:

  • The queue pipeline failed, errored, was cancelled or skipped.
  • The pipeline did not finish within the pipeline timeout, or was not approved within the approval timeout.
  • The PR conflicts with the target plus the entries ahead of it.
  • New commits were pushed to the PR while queued (add it again when ready), or the source branch was deleted, or the PR was converted to a draft, closed or merged outside the queue.
  • The PR stopped meeting its merge checks (for example an approval was dismissed) just before merging.
  • The queue was turned off for the branch, the repository was archived, or the target branch disappeared.
  • CI is off or the CI file is missing while "Require CI" is on.

A failed entry stays visible on the PR for a week with the reason and a link to the pipeline.

Manual approval gates in queue pipelines

If the queue pipeline reaches a manual job (see manual jobs in CI pipelines), the entry shows Waiting for approval and links to the pipeline. The pipeline timeout does not run while it waits; the approval timeout does. Once someone runs the manual job, the pipeline timeout starts over.

Batching in practice

With batch size 1 PRs are tested and merged one at a time. With a larger batch, PRs are tested in parallel on stacked commits, so throughput rises, and when a later PR passes it carries the earlier ones with it. If an entry in the middle fails, the entries behind it are rebuilt without it and tested again. Each pipeline uses CI runner capacity (Ci:MaxConcurrentJobs), so do not set the batch higher than your runners can serve.

Pipelines started by the queue have the trigger MergeQueue. There is no dedicated webhook for queue events; merged PRs send the normal pull_request.merged and the target's push event. The queue state shows in the admin system page (Administration).
