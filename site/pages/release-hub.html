Release hub

One place for everything that belongs to a tagged version: the notes, source archives and uploaded files, the CI builds and artifacts, packages and images, the security scan, SBOM files, test results, linked issues and pull requests, and whether the tagged commit is signed.

Built on what already exists

Releases, tags, generated release notes, assets, source archives and download counts are described in Code browsing and tools. The hub adds to a release page; nothing there changed and the existing release API keeps its shape. A release page (/p/{KEY}/repos/{slug}/releases/{id}) now shows, under the release card, a Release hub panel; /p/{KEY}/releases (the Releases link in the project sidebar) lists the releases of every repository of the project.

Container imagesShown under packages when the registry has an image tag equal to the release's tag

Drafts, and everything in a draft release, are visible only to people who can push (Developer and above), exactly like the release itself. Everything else needs only read access to the project.

Attaching CI artifacts automatically

On a release page, Maintainers (permission to manage repositories) can switch on Attach automatically and list patterns, one glob per line, matched against the paths inside the artifact zips (dist/*.zip, **/*.nupkg, bom/*.cdx.json). The rule is per repository (also at GET/PUT /api/v1/projects/{key}/repos/{slug}/release-settings).

  • It runs when a release is created or published, and when a pipeline passes later on the release's commit.
  • Only artifacts of passed pipelines whose commit is the tag's commit are used, newest pipeline first.
  • Matching files are copied onto the release as assets (file name only, no folders). A name the release already has is skipped, so running it again adds nothing. The usual limits apply: 50 assets per release and the release asset size limit (Releases:MaxAssetBytes, default 512 MB per file, measured on the bytes actually read, so a small zip that expands hugely is cut off).
  • Developers can press Attach artifacts now (or POST …/releases/{id}/attach-artifacts) at any time; it uses the patterns even if automatic attaching is off.
  • Patterns must be relative (no leading /, .., ~ or backslashes), at most 20 patterns of 200 characters. Artifacts are read entry by entry from the zip and never extracted to disk; entries with .. or absolute names are ignored.
Artifacts expire (expire_in on the job) and are deleted after that. Attach them while they exist: once copied, they are ordinary release assets that do not expire.

REST API

RoutePurpose
GET /api/v1/projects/{key}/releasesReleases of all repositories of the project, with asset counts, download counts and the newest test summary
GET …/repos/{slug}/releases/{id}/hubThe release with commit, signature, pipelines and artifacts, packages, security summary, SBOM files, issues, pull requests, test runs, total downloads and the checksum URL
GET …/repos/{slug}/releases/{id}/checksumsSHA256SUMS text for the assets
POST …/repos/{slug}/releases/{id}/attach-artifactsAttach matching CI artifacts (Developer+)
GET/PUT …/repos/{slug}/release-settingsRead or set the auto-attach rule (Maintainer+): {"autoAttachEnabled": true, "patterns": ["dist/*.zip"]}

The existing routes (/releases, /releases/latest, /releases/{id}, /releases/tags/{tag}, POST /releases, /tags) are unchanged. Asset downloads at /release-assets/{id}/{fileName} still count downloads.

Audit

Attaching files records release.assets_attached (repository, tag, count, file names, source ci-artifacts); publishing still records release.published and raises the release.published webhook.
