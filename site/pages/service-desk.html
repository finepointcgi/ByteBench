Service desk

Let people without a ByteBench account report problems by email or through a public form, and answer them from the issue page.

When the service desk is on for a project, each request becomes an ordinary issue in that project, created by a built-in Service Desk system user (bytebench-service-desk, no password, cannot sign in). The person who asked is a requester: just an email address and a name, never an account. Your team works the request like any issue; only comments you explicitly send as a reply to the requester leave the building.

How a request flows

  1. A requester emails desk+web@support.example.com (or submits the form at /desk/WEB).
  2. ByteBench checks for loops and spam, then creates an issue in project WEB with the subject as title and the message as description. Attachments are saved to the issue.
  3. If auto-reply is on and outbound email is enabled, the requester gets a confirmation with the issue key and a private tracking link.
  4. Your team sees it in the queue at /p/WEB/service-desk, handles it as an issue, and sends public replies.
  5. When the requester answers the email (or uses the tracking page), their message is added as a comment on the same issue and the request returns to "waiting on us".

Setup

  1. Choose an inbox address. Create one real mailbox for the whole ByteBench server, for example desk@support.example.com, and set ServiceDesk:IncomingAddress to it. Every project gets a plus-address of it (see below), so one mailbox serves all projects. Your mail provider must support plus-addressing (Gmail, Microsoft 365 and most others do).
  2. Connect mail to ByteBench in one of two ways: poll the mailbox over IMAP, or have your provider POST each message to the signed webhook.
  3. Turn on outbound email (Email:Enabled, SMTP settings) if you want auto-replies and replies to reach requesters. See Notifications and email. Without it, requests still arrive, but nothing is emailed back; the reply is still saved and shown on the tracking page, and the form says it was not emailed.
  4. Enable the project. A Maintainer opens Settings, Service desk (/p/{KEY}/settings/service-desk) and switches on Accept requests for this project. Until then, mail to the project's address is refused and the form is unavailable.
# appsettings.Production.json (secrets go in environment variables, not here)
"ServiceDesk": {
  "IncomingAddress": "desk@support.example.com",
  "Imap": { "Enabled": true, "Host": "imap.example.com", "Port": 993, "UseSsl": true,
            "User": "desk@support.example.com", "Folder": "INBOX", "PollSeconds": 60 }
}

# environment
ServiceDesk__Imap__Password=...        # never commit
ServiceDesk__WebhookSecret=...         # only if you use the webhook

Addresses and plus-addressing

AddressMeaning
desk@support.example.comThe inbox itself. Mail sent here alone has no project and is refused ("no matching project").
desk+web@support.example.comOpens a request in the project with key WEB. The tag is the project key, lower-cased, 2 to 10 letters or digits starting with a letter.
desk+r-<token>@support.example.comThe reply address of one request. ByteBench sets it as Reply-To on every email it sends, so a reply lands on the same issue. The token is 128 random bits.
A custom address, e.g. support@example.comSet per project in the settings and forward it to the inbox. ByteBench reads the original recipient from headers such as Delivered-To and X-Original-To to find the project. It cannot be the inbox itself and a custom address can belong to only one project.

Replies are matched even without the token: a message from the requester whose In-Reply-To or References names a message already on that request is added to it.

Inbound email

IMAP polling

Off by default. When ServiceDesk:Imap:Enabled is true and a host is set, ByteBench connects every PollSeconds (minimum 10), reads up to 100 unseen messages from the folder and flags each one seen (or deletes it with DeleteProcessed). A message that fails to process stays unseen and is retried on the next poll. Messages larger than MaxMessageBytes are skipped and logged.

Signed webhook

For providers that forward each message as raw MIME (and for tests), send it to:

POST https://bytebench.example.com/service-desk/inbound
X-ByteBench-Timestamp: 1767225600
X-ByteBench-Signature: sha256=<hex>
Content-Type: message/rfc822

<raw RFC 5322 message as the body>

Signature scheme. The signature is the lower-case hex HMAC-SHA256, keyed with ServiceDesk:WebhookSecret (as UTF-8), of the string "{timestamp}.{body}": the timestamp digits, a literal dot, then the exact raw body bytes. Prefix the hex with sha256=. The timestamp is Unix seconds and must be within WebhookToleranceSeconds (default 300) of the server's clock, which blocks replays. The comparison is constant-time.

SECRET='...'                       # same value as ServiceDesk:WebhookSecret
TS=$(date +%s)
SIG=$( { printf '%s.' "$TS"; cat message.eml; } | openssl dgst -sha256 -hmac "$SECRET" -hex | sed 's/^.* //' )
curl -X POST https://bytebench.example.com/service-desk/inbound \
  -H "X-ByteBench-Timestamp: $TS" -H "X-ByteBench-Signature: sha256=$SIG" \
  -H "Content-Type: message/rfc822" --data-binary @message.eml
ResponseMeaning
200 with {outcome, reason, issueId}Handled. outcome is created, commented, ignored or rejected. Even ignored or refused mail returns 200 so the provider does not retry it; read the outcome in the body.
401Bad or missing signature or timestamp
404No WebhookSecret is configured: the endpoint is off
413Body larger than MaxMessageBytes

Public form and tracking page

  • Request form: /desk/{KEY}, open to anyone, no sign-in. It asks for name, email, subject and message, and shows your Form introduction. Turn it off with Public request form in the settings. Submissions are limited per client IP.
  • Tracking page: /desk/t/{token}. The requester gets this link in the auto-reply and in every email. The 256-bit token is the credential, so anyone with the link sees the request; the page is marked noindex and sends no referrer. It shows the status and the public conversation only: never internal comments or activity. The requester can reply there while the desk is enabled.

Public replies vs internal comments

On an issue that came through the desk, the comment box offers Reply to requester alongside normal comments. Needs Developer or above (the Comment permission).

Internal commentReply to requester
Who sees itProject membersMembers, and the requester on the tracking page
EmailedNeverYes, to the requester, signed with your display name

Only three things email a requester: the auto-reply, a reply to requester, and a status notification (the issue moving into a status you picked in the settings). Requester comments appear on the issue with the requester's name and are visibly distinct. Requester email addresses are visible to Developers and above only.

The queue

/p/{KEY}/service-desk (Developer and above) lists requests, with the project's inbound address and a link to the public form. Filters:

FilterShows
Waiting on us(default) nobody has replied yet, or the requester spoke last. A closed issue counts only if the requester wrote after it closed.
UnansweredOpen and never replied to
Open, Closed, AllBy issue state

Longest-waiting first. A request waiting longer than the response target is flagged overdue. This is a simple flag, not a full SLA engine: no business hours, no escalation.

Loop, spam and abuse protection

Every inbound message passes these checks. A rule that fires is recorded in the audit log and the message creates nothing.

CheckResult
Same Message-ID seen beforeIgnored (duplicate), silently
Auto-Submitted other than no, Precedence bulk/junk/list/auto_reply, X-Autoreply headers, List-Id or List-Unsubscribe, delivery reports, empty Return-PathIgnored (auto-reply, mailing list, bounce)
Sender local part mailer-daemon, postmaster, noreply, no-reply, donotreplyIgnored (automated sender)
Sender is the inbox, a plus-address of it, or ByteBench's own From addressIgnored (own address): this is what stops two systems answering each other forever
No matching project, or the desk is disabledRejected
More than MaxMessagesPerSenderPerHour from one senderRejected (rate limited)
X-Spam-Flag: yes or X-Spam-Status: yes, a blocked sender, or more than MaxLinks linksRejected (spam)
Empty reply or empty messageIgnored

ByteBench's outbound mail helps the other side avoid loops too: it sets Auto-Submitted on auto-replies and status emails and X-Auto-Response-Suppress: All on all of them. Quoted text in replies is stripped (the reply marker line, "On ... wrote:", "Original Message", Outlook headers, > quotes and signatures), HTML mail is converted to Markdown with scripts and unsafe links removed, and attachments with executable or script extensions are skipped with a note on the issue. The in-memory rate limits reset when the server restarts.

Audit events

service_desk.enabled, service_desk.disabled, service_desk.settings_updated, service_desk.request_created, service_desk.reply_received, service_desk.reply_sent, service_desk.status_notified, service_desk.mail_ignored, service_desk.mail_rejected and service_desk.form_rejected. Ignored and rejected mail records the reason, sender and subject, which is how you debug "why did my email not create an issue". See Administration.

Limits and gotchas

  • Requesters have no accounts: they cannot see the issue page, only the tracking page.
  • Email to a project works only while its desk is enabled. Disabling closes the form and tracking-page replies too.
  • Auto-replies need working SMTP. In development, mail is written to the pickup directory (Email:PickupDirectory) instead of being sent.
