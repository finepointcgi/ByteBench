CI pipelines

Put a .bytebench-ci.yml in a repository and ByteBench runs its jobs in Docker containers on the server: on every push, on pull requests, on a schedule, or by hand.

Different from GitLab CI. ByteBench's format is small on purpose. There are no stages (order comes from needs), no script/before_script/after_script keys (a job has steps), no services, no retry, no per-job timeout or variables, no extends, no trigger and no include of files (only built-in templates). The sections below say what exists, what is not there, and the usual replacement.

Quick start

Create .bytebench-ci.yml at the root of the repository (the name and location are fixed), commit it and push. A pipeline appears on the repository's Pipelines tab.

jobs:
  build:
    steps:
      - name: Say hello
        run: echo "Hello from $BYTEBENCH_JOB on $BYTEBENCH_REF"

Without an image the job runs in alpine:3.20. Everything you need to know to read and write the file is on this page; the sections build from the file layout to security.

The file format

The file is YAML. Unknown keys are errors so typos are caught: the pipeline is created in the Error state with a message such as invalid YAML at line 4, column 5: Property 'stepz' not found. The whole file may be at most 64 KB, with at most 20 jobs and 50 steps per job.

image: alpine:3.20             # default image for every job (default alpine:3.20)
include: [nightowl]            # built-in job templates (see "include")
on:                            # which pushes/PRs start a pipeline automatically
  branches: [main, "feature/*"]
  pull_requests: true
jobs:
  <job-name>:
    image: ...                 # per-job image
    needs: [other-job]         # dependency graph
    when: on_success | manual
    allow_failure: true | false
    only: [main, "release/*"]  # or rules (not both)
    rules: [ { branches: [main], when: manual } ]
    cache:     { key: ..., paths: [...] }
    artifacts: { paths: [...], expire_in: 7d, when: on_success, reports: { ... } }
    environment: { name: production, url: https://..., action: start|stop }
    pages: true | false | dist | { path: dist, review: true, expire_in: 3d }
    publish: dist              # alias for pages: { path: dist }
    steps:
      - name: Optional label
        run: shell commands

Top-level keys

KeyMeaning
imageDefault Docker image for jobs that don't set one. Default alpine:3.20. Names are validated (letters, digits and ._/:@-, must not start with -).
includeA template name or list of names. The only built-in template is nightowl. See include.
on.branchesBranch patterns that start a pipeline on push. Omitted means every branch. * matches within one path segment, ** across segments (feature/* matches feature/x but not feature/x/y).
on.pull_requestsDefault true: a pull request's source head gets a pipeline even if its branch isn't in on.branches. false disables that.
on.tagsTag patterns that start a pipeline when a tag is pushed or created. Without it, tags only start pipelines when a job has a rule about tags. See Tag pipelines.
variablesPlain environment variables for every job. See variables in the file.
jobsRequired map of job name to job. Names use letters, digits, _, ., -, up to 64 characters, starting with a letter or digit.

What the format does not have

You might look forIn ByteBench
stages: and a job's stageNot supported. Use needs: a job without needs starts immediately, one with needs waits for them. A "stage" is just a set of jobs that need the previous set.
script, before_script, after_scriptUse steps. Put setup in the first step. There is no after-script that runs on failure; later steps are skipped once a step fails.
Secrets in variables:variables: is for plain values (they are in the repository). Secrets go in CI variables in the UI, which win over the file's variables.
services: (sidecar containers)Not supported, and jobs get no Docker daemon, so they can't start containers either. Use an image that bundles what you need, or install it in a step.
retry: { max, when }, parallel: NOnly the plain number retry: 2 (any failure) and parallel: { matrix } exist.
trigger: (child and multi-project pipelines), extends: and hidden .jobs, include: { local/remote/project }, YAML anchors across filesNot supported. Repeat the keys, or use YAML anchors inside the one file.
resource_group:, environment: on_stop, cache: key: files:Not supported. environment: { action: stop } marks a stop job you run yourself, and {{ hashFiles('...') }} in a cache key does what key: files: does.
Test coverage parsing (coverage:) and pipeline status badgesNot supported. Test reports (artifacts.reports) give pass/fail counts; the commit status endpoint gives a commit's state.
when: always, on_failure, delayedNot supported for jobs. (artifacts.when does accept on_failure and always.)

Images and steps

Each job gets a fresh export of the commit's files, mounted at /workspace, which is also the working directory. Each step runs in its own container:

docker run --rm --entrypoint sh <image> -e -c "<run>"
  • The image must therefore contain sh. A multi-line run stops at its first failing command (-e).
  • Steps of one job share the /workspace folder, so files written by step 1 are there for step 2, but nothing else carries over: installed packages, exported variables and cd do not. Install tools and use them in the same step.
  • The first failing step fails the job and the job's remaining steps are Skipped.
  • The log is streamed to the pipeline page about once a second. Each step's log is capped at about 1 MB (Ci:MaxLogChars).
jobs:
  test:
    image: mcr.microsoft.com/dotnet/sdk:10.0
    steps:
      - name: Restore
        run: dotnet restore
      - name: Test
        run: |
          dotnet test --no-restore \
            --logger "trx;LogFileName=results.trx"

Job dependencies (needs)

needs: [a, b] makes a job wait for a and b. Jobs without needs run in parallel (limited by Ci:MaxConcurrentJobs). A job also gets the artifacts of every job it needs, extracted into its workspace before its first step.

  • A job whose needed job failed (without allow_failure) or was skipped is skipped.
  • Needing an undefined job, itself, or a cycle is an error (The 'needs' of these jobs form a cycle: a → b → a).
  • If rules or only leave out a job on the branch being run, any job that needs it makes the pipeline an Error for that branch. Give the dependent job the same rule.

The pipeline page draws this as a graph: jobs in columns by needs depth, a line from each need, each job showing status, duration and environment. Click a job for its log; ▶ runs a manual job and ↻ retries a finished one.

The graph the pipeline page draws for a file where unit-tests, lint and package need build, integration needs unit-tests and package, and deploy needs integration.

Rules, only and when

  • only: [main, "release/*"] creates the job only on matching branches.
  • rules is a list of { branches, tags, if, when } (up to 20). The first rule that matches decides. A rule with branches matches branch pipelines whose branch matches one pattern; with tags it matches tag pipelines whose tag matches; with neither it matches every ref. If it has an if, the condition must hold too. when is on_success, manual or never; never leaves the job out, and an omitted when keeps the job's own. If no rule matches, the job is not created.
  • only: [main] is the branch-only form. A branch filter never matches a tag, and a tags filter never matches a branch.
  • If no job at all is left for a branch, pushes don't create a pipeline and Run pipeline says so.
  • There are no conditions on changed files (changes:) or exists:. For a pull request pipeline the "branch" is the pull request's source branch.

if: conditions

A small subset of GitLab's syntax: $NAME (true when the variable is set and not empty), "text" or 'text', null, ==, !=, =~ and !~ with a /regular expression/ (flag i allowed), &&, ||, ! and parentheses. An unset variable is null. They can read CI_COMMIT_TAG, CI_COMMIT_BRANCH, CI_COMMIT_REF_NAME, CI_PIPELINE_SOURCE and the run's own schedule or manual variables (not CI variables, which are secrets). A condition that doesn't parse is a file error.

jobs:
  release:
    rules:
      - { if: '$CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/' }   # a release tag
    steps: [ { run: ./release.sh "$CI_COMMIT_TAG" } ]
  nightly:
    rules:
      - { if: '$CI_PIPELINE_SOURCE == "schedule" && $CI_COMMIT_BRANCH == "main"' }
    steps: [ { run: ./nightly.sh } ]
jobs:
  preview:
    rules:
      - { branches: [main], when: never }        # not on main
      - { branches: ["feature/**"], when: manual } # click to run on feature branches
      - { when: on_success }                      # everything else: automatic
    steps: [ { run: ./preview.sh } ]

Manual jobs

A job with when: manual (or a rule that says so) waits in Manual once its needs pass, until someone with PushCode (Developer or higher) clicks ▶ on the pipeline page. Jobs that need it wait too.

  • With allow_failure: true (the default for manual jobs) a waiting manual job does not block: the pipeline finishes as Passed and the job can still be run later.
  • With allow_failure: false the pipeline stays Manual (blocked). The merge check reports it as pending, and no pipeline.completed webhook or failure notification is sent until it really finishes.
  • Jobs that deploy to a protected environment wait for approval regardless of allow_failure.

REST API

Pipelines can be driven from scripts: list and filter them, read a pipeline with its jobs and steps, read a step's log (tail or page it), run a pipeline for a branch or tag (with variables), cancel or re-run it, read a commit's combined pipeline status, retry or play a job, and list or download a job's artifacts. Under /api/v1/projects/{key}/repos/{slug}/pipelines, with the same roles as the buttons in the UI (read: Viewer and read_api; actions: Developer and write_api). CI variables can be listed (names and flags only, never values), created, updated and deleted by a Maintainer under .../ci/variables. Fork pull request pipelines still wait for approval and never receive variables. See the endpoint catalogue.

curl -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" -d '{"branch":"main"}' \
  https://bytebench.example.com/api/v1/projects/WEB/repos/site/pipelines
curl -H "Authorization: Bearer $TOKEN" "https://bytebench.example.com/api/v1/projects/WEB/repos/site/pipelines/12/steps/34/log?tail=2000"

variables in the file

variables: at the top of the file and inside a job sets plain environment variables (the job's win). Names use letters, digits and _ and can't be CI or start with BYTEBENCH_ or GITBENCH_; values are single lines up to 2000 characters, at most 50 per level. They are not secret (they are in the repository and in the pipeline file's history). Precedence, lowest first: the file's variables, CI variables, then the run's own variables (a schedule's, or those given with Run pipeline or the API). The predefined variables above always win.

variables: { CHANNEL: stable }
jobs:
  build:
    variables: { CONFIGURATION: Release }
    steps: [ { run: 'dotnet build -c "$CONFIGURATION" -p:Channel="$CHANNEL"' } ]

CI variables (secrets)

Secret values are managed in the UI or the REST API, not in the YAML: project variables under Project settings → CI variables (/p/{KEY}/settings#ci-variables) and repository variables under Repository → Settings → CI variables (/p/{KEY}/repos/{slug}/settings/ci-variables). Managing them needs Maintainer or higher (ManageRepositories).

  • Names: letters, digits and underscores, not starting with a digit, up to 100 characters; CI and BYTEBENCH_* are reserved. Values: a single line, up to 10,000 characters.
  • Values are encrypted at rest (ASP.NET Core Data Protection) and are never shown again after saving. If the server's Data Protection keys change, a value can't be decrypted: the log says which variable was skipped and you save it again.
  • A repository variable overrides a project variable of the same name.
  • They reach the container through a mode-600 env file outside the workspace, never on the docker command line.
  • Masking: every secret value of four characters or more is replaced by *** in step logs, including values split across output chunks. Shorter values are not masked. Masking is a safety net, not a guarantee: a step that prints a secret in a transformed form (base64, reversed) is not caught.
  • The log lists the names of the variables the job received, never the values.

Protected variables

Mark a variable Protected and it only reaches pipelines on a protected branch. For a pull request pipeline the source branch must be protected, so a feature branch never sees deploy keys. A merge queue pipeline counts as running on its target branch only if the PR isn't from a fork and the person who queued it can merge pull requests. The log notes how many protected variables were withheld.

Fork pull requests get no variables at all, protected or not, because the code comes from outside the project.

Pipeline (schedule and manual-run) variables

Run pipeline has a Variables box (NAME=value, one per line), and the API takes "variables": { "NAME": "value" }. They follow the same rules as the file's variables and the same treatment as a schedule's below.

A schedule carries variables too. All of these are not secret (Maintainers can read them), override CI variables of the same name, and go through the same env file. A fork pull request pipeline never carries them.

Artifacts

jobs:
  build:
    steps: [ { run: dotnet publish -o out } ]
    artifacts:
      paths: [out/, "*.log"]   # folders (trailing /), files or globs, relative to /workspace
      expire_in: 7d            # 30m, 12h, 7d, 2w, 3mo, 1y, never. Default 30d
      when: on_success         # on_success (default), on_failure, always
      reports:                 # optional, see Security scanning
        sarif: results.sarif
  • After the job's steps, if when matches the result, the files are zipped and stored under Ci:ArtifactsRoot. Over Ci:MaxArtifactBytes (100 MB) nothing is stored and the job fails.
  • Paths can't contain .. or be absolute (up to 50 paths). Symbolic links are never followed or stored; the log names each one skipped.
  • Jobs that needs this job get the files extracted into their workspace before their first step. Extraction refuses names with .., absolute paths and anything that would be written through a symlink.
  • The pipeline page lists artifacts with Download (the zip), Browse (file list, each file downloads) and Keep (pin past expiry; PushCode). Downloads need ViewProject and are always served as application/octet-stream attachments with a sandboxing CSP.
  • An hourly cleanup deletes expired, un-kept artifacts.
  • reports accepts only the types nightowl and sarif, each naming one file (no globs). ByteBench reads them into Security scanning. There is no JUnit/test report type.

Cache

jobs:
  build:
    image: node:22
    cache:
      key: "npm-{{ hashFiles('package-lock.json') }}"   # default key is "default"
      paths: [node_modules/]
    steps: [ { run: npm ci && npm run build } ]
  • Keys may contain letters, digits, ., _, - and {{ hashFiles('glob', ...) }}, which becomes a hash of the matching files' names and contents in the fresh checkout.
  • The cache with that key is extracted before the first step. After the job passes the paths are zipped and replace that key's cache. A failed job does not save a cache. There are no fallback keys: if the exact key misses, the job starts cold.
  • Limits: Ci:MaxCacheBytes (500 MB) per cache and Ci:CacheBytesPerRepository (2 GB) per repository; the least recently used are evicted.
  • Two scopes. Pipelines on a protected branch read and write only the protected cache; everything else (other branches, pull requests) uses the unprotected one. This stops someone pushing a branch that poisons node_modules for the next main pipeline, which may hold deploy secrets. The log says which scope was used.

include (the Night Owl template)

include: [nightowl] (or include: nightowl) adds a built-in job named nightowl. A job of the same name in your file replaces it. No other templates exist; any other name is an error listing the available ones. Details, variables and the runner-image requirement are on Security scanning.

include: [nightowl]
jobs:
  build:
    steps: [ { run: ./build.sh } ]

Tag pipelines

A pipeline can run when a tag is pushed, or created in ByteBench (the Tags page, or a release that makes its tag). Its ref is refs/tags/{tag}, shown as tag v1.4.0 in the pipeline lists, and steps see CI_COMMIT_TAG and CI_COMMIT_REF_NAME set to the tag (and no CI_COMMIT_BRANCH). The commit is the one the tag points at, annotated or not.

  • Opt in. Files written before tag pipelines existed never run on a tag. A tag starts a pipeline if the file has on.tags with a pattern that matches it (["v*"], or ["*"] for every tag), or, when there is no on.tags, if some job has a rule with tags: or an if: that mentions $CI_COMMIT_TAG.
  • Which jobs. The same rules as for branches: a job with no rules runs on tags too, only and branches rules never match a tag, and tags: / if: select tag jobs. A tag whose rules leave no job starts nothing.
  • Once per tag and commit. Pushing the same tag again does not repeat it; moving a tag to another commit does. Deleting a tag starts nothing. Re-run on a tag pipeline runs the same tag and commit again.
  • By hand. Run pipeline lists tags after the branches; the API takes {"tag":"v1.4.0"}. Needs PushCode, like branches.
  • Secrets. A tag pipeline gets protected variables only when the tag matches a protected tag rule (those limit who can create the tag); other tags see only unprotected variables, and the log says so. The same split applies to the cache scope.
  • Not published. A tag pipeline never publishes a Pages site. Its artifacts are attached to a release whose tag points at the commit, and the release hub lists the tag's pipeline first.
  • Not covered. Tags that arrive through a mirror pull or an import start nothing; use Run pipeline.

Matrix jobs

parallel: { matrix: [ { VAR: [a, b], OTHER: [x] }, ... ] } runs a job once per combination of each entry's lists (several entries add up). Each instance is named {job}-{value}-{value} (characters other than letters, digits, _, . and - become _; up to 64 characters), gets its combination as environment variables on top of the job's variables, and a job that needs the matrix job needs every instance. Variable names follow the variable rules; the total, with all other jobs, can't pass 20 jobs, and two instances can't get the same name. Image names can't use variables.

Statuses, retries and timeouts

  • A pipeline is Queued, Running, Passed, Failed, Canceled, Error or Manual (blocked on a manual job). Jobs and steps can also be Skipped. Error means the file was invalid or Docker was unavailable.
  • Retry on a finished job runs it again inside the same pipeline, replacing its logs and artifacts (PushCode). A job with retry: N also runs again by itself, up to N more times, when it fails (not when the pipeline is canceled): its steps, logs and artifacts are replaced, the new attempt's log starts with a note naming the failed step and its exit code and the last lines of the failed attempt, and a job that deploys records a deployment per attempt. Running out of retries fails the job as before.
  • Timeout: every job is killed after Ci:JobTimeoutMinutes (default 20). A job's own timeout: can make that shorter but never longer, so an admin's limit stays the ceiling. The clock covers the steps, not the checkout or the artifact upload.
  • Cancel stops a running pipeline (PushCode).
  • When a pipeline fails or errors, whoever triggered it gets a notification. The pipeline.completed webhook fires when it finishes.
  • After a server restart, pipelines that were running are marked Error; queued ones run again; leftover containers and workspaces from this instance are removed.

Schedules (cron)

Pipelines → Schedules (/p/{KEY}/repos/{slug}/pipelines/schedules, Maintainer+) lists, creates, edits, deletes and runs schedules.

  • A schedule has a description, a branch, variables and a 5-field cron expression in UTC: minute hour day-of-month month day-of-week. Fields take *, numbers, ranges, steps (*/15), lists and names (mon-fri, jan). @hourly, @daily (@midnight), @weekly, @monthly, @yearly (@annually) also work. If both day-of-month and day-of-week are restricted, either matching is enough (classic cron).
  • CiScheduleRunner checks every 30 seconds and starts each due schedule on the branch's tip with CI_PIPELINE_SOURCE=schedule. Disable all schedules with Ci:SchedulesEnabled=false.
  • The pipeline runs as the schedule's owner (the last person who saved it). If the owner can no longer push, the schedule records an error and a Maintainer saves it to take it over.
  • Runs missed while the server was down happen once, then the schedule moves on. Run now runs it immediately as you.
  • Audit events: pipeline_schedule.created, .updated, .deleted.
# nightly at 02:30 UTC on weekdays
30 2 * * mon-fri

Fork pull requests

A pull request from a fork runs code from outside the project, so its pipeline is created Queued but waiting for approval. A Maintainer (or higher, anyone who can merge pull requests) clicks Approve and run on the pipeline page. Approval covers that one pipeline; the next push to the fork waits again. Even once approved the pipeline gets no CI variables, never publishes Pages sites, and carries no schedule variables.

Docker requirement and security model

The server needs the docker CLI with a reachable daemon. If it can't connect, pipelines end in Error with "Docker is not available on the server". When ByteBench itself runs in a container (see Production setup), the daemon must be able to mount Ci:WorkDirectory.

Pipelines run arbitrary code from the repository on the server host, inside Docker. Anyone who can push (Developer or higher) can run any command in any image. Treat PushCode as "can run code on the CI host". Docker isolation is not a hard security boundary.
  • The docker CLI is always started with an argument list, never a shell string; image names are validated so they can't be read as flags.
  • Containers never get the Docker socket, the host's environment variables or any ByteBench secret. They get the BYTEBENCH_* variables, the allowed CI variables and the job token.
  • Containers run with --security-opt no-new-privileges, memory, CPU and PID limits, a timeout and --rm, as the image's user (often root inside the container) unless you set Ci:User; Ci:DropCapabilities adds --cap-drop ALL.
  • Only the exported workspace is mounted. Symlinks in the repository are created after every regular file so nothing is written through them. Submodules aren't fetched.
  • Containers have network access by default (bridge). On a shared or exposed server use Ci:Network: none, rootless Docker or a separate CI host, and let only trusted people push.

ByteBench has no separate runner agents: the server itself runs jobs. There are no runner tags or per-runner registration.

Pipelines are shown at /p/{KEY}/repos/{slug}/pipelines and .../pipelines/{id}. The latest pipeline on a pull request's head is a merge check: Passed, Pending (queued, running, manual-blocked, or none yet) or Failed. It reports nothing if the head has no .bytebench-ci.yml, or if no pipeline would start for the pull request (every job's rules leave it out, or on: excludes it), so the check never waits for a pipeline that will not come. Tag pipelines on the same commit are not counted.

Example pipelines

1. .NET build, test and publish with a cache

image: mcr.microsoft.com/dotnet/sdk:10.0
on:
  branches: [main, "release/*"]
  pull_requests: true
jobs:
  build:
    cache:
      key: "nuget-{{ hashFiles('**/*.csproj') }}"
      paths: [.nuget/]
    steps:
      - name: Restore and build
        run: |
          export NUGET_PACKAGES="$PWD/.nuget"
          dotnet restore
          dotnet build -c Release --no-restore
    artifacts:
      paths: [src/App/bin/Release/]
      expire_in: 3d
  test:
    needs: [build]
    steps:
      - name: Test
        run: dotnet test -c Release
  publish:
    needs: [test]
    only: [main]
    artifacts:
      paths: [out/]
      expire_in: 30d
    steps:
      - run: dotnet publish src/App -c Release -o out

Note that test receives build's artifacts, so it can reuse the compiled output, while the NuGet cache keeps restores fast across pipelines.

2. Node app with a manual production deploy

jobs:
  install-and-test:
    image: node:22
    cache:
      key: "npm-{{ hashFiles('package-lock.json') }}"
      paths: [node_modules/]
    steps:
      - run: npm ci
      - run: npm test
      - run: npm run build
    artifacts:
      paths: [dist/]
  lint:
    image: node:22
    allow_failure: true            # report but don't block
    steps: [ { run: npx eslint . } ]
  deploy-staging:
    needs: [install-and-test]
    only: [main]
    environment: { name: staging, url: "https://staging.example.com" }
    steps:
      - run: ./scripts/deploy.sh staging dist/
  deploy-production:
    needs: [deploy-staging]
    only: [main]
    when: manual
    allow_failure: false           # the pipeline stays "Manual" until someone runs it
    environment: { name: production, url: "https://example.com" }
    steps:
      - run: ./scripts/deploy.sh production dist/

Put a deploy key in a protected CI variable (for example DEPLOY_KEY) so only main pipelines can read it, and mark production as a protected environment to require approval (see Environments).

3. Build and push a container image to the project registry

jobs:
  package:
    image: gcr.io/kaniko-project/executor:debug   # example: any image that can build images without a Docker daemon
    only: [main]
    steps:
      - name: Build and push
        run: |
          mkdir -p /kaniko/.docker
          AUTH=$(printf '%s:%s' "$BYTEBENCH_REGISTRY_USER" "$BYTEBENCH_REGISTRY_PASSWORD" | base64 | tr -d '\n')
          printf '{"auths":{"%s":{"auth":"%s"}}}' "$BYTEBENCH_REGISTRY" "$AUTH" > /kaniko/.docker/config.json
          /kaniko/executor --context /workspace --dockerfile /workspace/Dockerfile \
            --destination "$BYTEBENCH_REGISTRY_IMAGE/web:$BYTEBENCH_COMMIT_SHA"

Jobs get no Docker daemon, so docker build is not available inside a step; a daemonless builder such as Kaniko is one option. The job token only works for the project's own registry and only while the job runs. This example needs Ci:Network to allow reaching the registry, and Kaniko's behaviour with your registry's TLS settings is yours to verify. See Package and container registry.

4. Nightly security scan plus a docs site

include: [nightowl]
on:
  branches: [main]
jobs:
  nightowl:                                   # same name: replaces the template
    image: registry.example.com/ci/nightowl-runner:1.0
    artifacts:
      when: always
      paths: [nightowl.md]
      reports: { nightowl: nightowl.json, sarif: nightowl.sarif }
    steps:
      - name: Night Owl scan
        run: nightowl scan . --no-update --format json --output nightowl.json --sarif-output nightowl.sarif --summary-output nightowl.md
  pages:                                      # a job named "pages" publishes ./public on main
    image: python:3.13-alpine
    steps:
      - run: python3 tools/build_docs.py      # writes ./public

Then add a schedule (0 3 * * *) on main so the scan also runs when nobody pushes. See Security scanning and Static sites.

5. Fan-out with a matrix

A job with parallel: matrix becomes one job per combination (see matrix); a job that needs it waits for all of them:

jobs:
  test:
    parallel: { matrix: [ { CONFIG: [Debug, Release] } ] }
    steps: [ { run: 'dotnet test -c "$CONFIG"' } ]
  all-green:
    needs: [test]
    steps: [ { run: echo "every variant passed" } ]

Image names are fixed text (they can't contain variables), so a matrix varies a variable for the steps, not the image. To vary the image, write one job per image:

jobs:
  test-net8:
    image: mcr.microsoft.com/dotnet/sdk:8.0
    steps: [ { run: dotnet test } ]
  test-net10:
    image: mcr.microsoft.com/dotnet/sdk:10.0
    steps: [ { run: dotnet test } ]

6. Build and publish when a version tag is pushed

on:
  tags: ["v*"]
jobs:
  build:
    artifacts: { paths: [dist/], expire_in: never }
    steps: [ { run: ./build.sh "$CI_COMMIT_TAG" } ]
  publish:
    needs: [build]
    rules: [ { if: '$CI_COMMIT_TAG' } ]     # tags only, not branch pushes
    environment: { name: production }
    steps: [ { run: ./publish.sh dist/ } ]

Pushing v1.4.0 runs both jobs; pushing a branch runs build only (the file's on: has no branches, so branches run as usual). If a release in the release hub uses that tag, the passed pipeline's artifacts are attached to it (when the repository's auto-attach setting is on).

Troubleshooting

SymptomCause
Pipeline is Error immediatelyThe YAML is invalid (read the message on the pipeline page) or Docker isn't reachable.
No pipeline after a pushNo .bytebench-ci.yml at that commit, the branch isn't in on.branches and has no open PR, every job's rules excluded the branch, the commit already ran on that branch, or Ci:Enabled is off.
Pipeline sits QueuedAll Ci:MaxConcurrentJobs slots are busy, or it is a fork PR waiting for approval.
A secret is empty in a jobThe variable is protected and the branch isn't, or it's a fork PR pipeline, or its value couldn't be decrypted (check the notes at the top of the first step's log).
command not found in a later stepEach step is a new container: install tools in the step that uses them.
