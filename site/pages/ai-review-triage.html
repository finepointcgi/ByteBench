AI review and triage

Let Claude review pull requests and suggest labels, priority, assignee and duplicates for new issues, with every limit configurable and every change reviewable.

Both features are off by default and need AI set up first; see AI overview and setup. Pull request review runs on the same backend as the web editor (Claude Code on the server or the Anthropic API, see Ai:Editor:Backend). Issue triage uses the Anthropic API key only.

AI pull request review

An AI review reads the pull request title, description, commit messages and diff and posts inline comments from a bot account named ByteBench AI (bytebench-ai). The bot has no password and cannot sign in. Its comments carry an AI badge. It never approves a pull request and never merges.

Turn it on for a repository

  1. Open the repository, then Settings, AI review (/p/{KEY}/repos/{slug}/settings/ai-review). You need the Maintainer role.
  2. Switch on Enable AI review for this repository. If the server has no backend, the page shows why (for example "no Claude API key is configured").
  3. Pick When to review and press save. Changes are written to the audit log as repository.ai_review_settings_changed.

Review with AI

On a pull request, the sidebar block AI review shows the status (queued, running, completed with a finding count, or failed with the error) and updates live. A user with the Developer role or higher (the review-pull-request permission) sees the Review with AI button while the pull request is open. Reviews run one at a time in a background worker.

A given head commit is reviewed once. Pressing the button again on an unchanged branch says that commit was already reviewed. Push a new commit, or wait for a failed run, to review again.

Automatic triggers

  • Created (modes "opened" and "opened and after each push"): queued when the pull request is created.
  • Push (mode "opened and after each push"): queued after a push to the source branch of an open pull request. The wait is debounced (30 seconds by default, Ai:Review:PushDebounceSeconds), so a burst of pushes produces one review.

Findings and severities

The model returns structured findings, each with a file, line, severity, title and body, plus an overall verdict. ByteBench validates every finding against the diff before posting.

SeverityMeaningBlocks?
bugLikely incorrect behaviourYes, can set "changes requested" and counts for the merge check
securityInjection, missing authorization, secrets in code, and the likeYes, as above
suggestionMaintainability or performance improvementNo
nitStyle and small points, lowest priorityNo
  • Valid findings become inline comment threads. A finding a few lines off is moved to the nearest changed line and marked as moved. Findings that cannot be placed are listed in the summary comment.
  • If there is at least one blocking finding, the bot records Changes requested. Otherwise it only comments, and a clean re-review withdraws its earlier request for changes.
  • A later review does not repeat a finding it already posted (each has a stable fingerprint based on file and title).
  • Binary files, lockfiles (package-lock.json, yarn.lock, go.sum and others), minified or generated files and build output are skipped. Diffs larger than about 120,000 characters are reviewed in per-file batches, up to 6. Everything skipped or not reviewed is listed in the summary, so nothing is cut silently.

Dismiss a finding

If a finding does not apply, dismiss it. That resolves its thread as "not applicable", records an activity entry, and stops it blocking a merge. The pull request's author, a Maintainer or the comment's author can do this (the same people who can resolve a thread). Un-resolving the thread brings the finding back. Dismissals are audited as ai_review.finding_dismissed.

Merge check

With "block merging while AI blocker findings are unresolved" switched on, the merge box shows an AI review line. A blocker is an unresolved AI finding of severity bug or security. The line passes with "No unresolved AI blocker findings" and fails with "N unresolved AI blocker findings: resolve or dismiss them". It applies whether or not the target branch is protected. It is separate from branch protection rules, and the sidebar also counts unresolved blockers.

Other audit events: ai_review.queued, ai_review.failed and a completed event per run. Token usage is stored per call in the AiUsages table with the feature name pr-review. The fixed system prompt is served from the prompt cache, and most pull requests need one call.

Prompt-injection protections

  • The pull request title, description, commit messages, file paths and the diff are written by whoever opened the pull request. They are put inside blocks marked UNTRUSTED with a random boundary per request, so content cannot close its own block. The prompt tells the model never to follow instructions found there.
  • Only the repository's focus prompt, placed outside the untrusted blocks, is treated as guidance.
  • Findings are checked against the real diff, so the model cannot comment on files or lines that are not part of the change.
  • With the Claude Code backend, the review runs with no tools that can run commands, in a throwaway directory without the repository's own Claude configuration. See how it is sandboxed.
  • The bot account cannot sign in, and it has no project role. Its permissions apply only to posting the review.

AI issue triage

Triage reads a new issue and proposes labels, a component, priority, type, an assignee and likely duplicates, along with a one-line summary. Suggestions use only what exists in the project: its labels (including labels inherited from groups), its components, and Developer-or-higher members. Nothing is applied until a person accepts it, except labels when auto-apply is on.

Turn it on

  1. Open the project, then Settings and find the AI issue triage card. You need the Maintainer role (the manage-labels-and-milestones permission).
  2. Switch on Suggest labels, component, priority, type, assignee and duplicates for issues.
  3. Optionally switch on Apply suggested labels to new issues automatically.

Both switches are off by default. Changes are audited as project.settings_changed. If AI is not configured, the card says so and nothing is suggested.

The suggestions panel

On an issue, the AI suggestions panel shows the latest run. When triage is on, ByteBench queues a run automatically for each newly created issue (only if the issue is under about two minutes old and has no run yet). Anyone with the Developer role can press Suggest (or Suggest again) to request one. Runs happen on a background queue, and the panel updates live.

Each suggestion has a kind (label, component, priority, type, assignee or duplicate), a value, a reason, and its state: pending, accepted, dismissed or applied automatically.

  • Accept applies it through the normal issue services as you, so permissions, activity entries, notifications, workflow rules, webhooks and automation all run just as if you made the change by hand. Accepting a duplicate adds a "duplicates" link to the other issue. An assignee is re-checked at accept time and must still be a Developer or higher.
  • Dismiss marks the suggestion as dismissed. Both need the Developer role.

Audit events: ai.triage.requested, ai.triage.accepted, ai.triage.dismissed, ai.triage.auto_applied, ai.triage.rate_limited.

Auto-apply labels

When enabled, suggested labels from the automatic run on a new issue are added at once, shown as "applied automatically", and recorded in the issue's activity as an AI suggestion. A label that no longer exists is skipped. All other kinds still wait for a person.

Duplicate hints

Two mechanisms look for duplicates:

  • Triage duplicates: the model picks likely duplicates from up to 10 candidates chosen by keyword overlap from the project's 1,500 most recently updated issues. It gives a reason for each.
  • Similar-issue hints on the new-issue form while typing: pure keyword overlap with no model call and nothing stored. A title needs at least two meaningful words and a score of at least 0.35 (Ai:Triage:MinHintScore). They are labelled "Similar wording".

The issue text is untrusted and goes into delimited data blocks. The answer must match a JSON schema, and every label, component, assignee and duplicate in it is validated against the project's real data before it is stored.

AI review API

Under /api/v1/projects/{key}/repos/{slug} (see the endpoint catalogue). The permissions and guards are those of the UI: settings need Maintainer, asking for a review needs Developer and hits the same per-repository hourly limit.

Method and pathPurpose
GET, PUT /ai-review/settingsMaintainer. The repository's settings; PUT keeps omitted fields. The GET also reports whether an AI backend is available.
GET /pull-requests/{number}/ai-reviewsReviews of the pull request with status, counts, summary and inline findings.
POST /pull-requests/{number}/ai-reviewsQueue a review. 202, or 409 (already reviewed or pending), 429 (hourly limit), 422 (off, not set up, pull request closed).
POST /pull-requests/{number}/ai-findings/{commentId}/dismiss, /undismissDismiss a finding's thread as not applicable, or bring it back.
