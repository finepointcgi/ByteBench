Repositories and Git hosting

Every project can host any number of Git repositories. You clone and push over HTTP with a password or personal access token, or over ByteBench's built-in SSH server with an SSH key or a deploy key.

How repositories work

A repository lives inside a project (which has a key such as WEB). It is a normal bare Git repository on the server's disk, plus a database row for its name, description, default branch and settings. ByteBench reads and writes it with LibGit2Sharp and runs the real git executable for the network protocols, so any Git client works.

A repository is addressed as KEY/slug, for example WEB/web-app. The slug is the URL-friendly name. These are the main pages:

RouteWhat is there
/p/{KEY}/reposThe repository list and Create repository
/p/{KEY}/repos/{slug}Source browser, clone box, rendered README (see Code browsing and tools)
/p/{KEY}/repos/{slug}/branchesBranches with ahead/behind counts, create, delete, Create pull request

/p/{KEY}/repos/{slug}/forksThe forks of this repository

The repository tabs are Source, Commits, Branches, Tags, Releases, Pull requests, Pipelines, Environments, Security and Search, plus Settings for Maintainers and Owners.

Creating a repository

  1. Open the project, then Repositories in the sidebar (/p/{KEY}/repos).
  2. Click Create repository. You need the Maintainer role or higher (the ManageRepositories permission).
  3. Enter a Name (required, up to 100 characters). The Slug is filled in from the name; you can change it. It must start with a letter or digit and use only lowercase letters, digits, ., _ or -, at most 100 characters, and must not end in .git. The slugs wiki and *.wiki are reserved for the project wiki.
  4. Optionally add a description, then click Create repository.

The new repository starts with one commit on main containing a README.md built from the name and description. The default branch of a new repository is always main; change it later in Settings. The slug must be unique inside the project. Creation is recorded in the audit log as repository.created.

Bringing existing code in

The quickest way is the import wizard. There are also three alternatives, which still work and suit other situations:

  • Push it. Add the new repository as a remote and push. Because a new repository already has a README commit, either push to a different branch name, or force-push if you want your history to replace main (branch protection must allow it): 
    git remote add bytebench https://bytebench.example.com/git/WEB/web-app.git
git push bytebench --all
git push bytebench --tags
  • Mirror it. A pull mirror keeps the repository in sync with an upstream URL on a schedule. While a pull mirror is enabled the repository is read-only for pushes.
  • Fork it. To copy a repository that already lives in ByteBench, use Fork.

Issues and pull requests from other systems are not imported by repository tools. For issues use the CSV import described in Fields, filters and search.

The import wizard

Import repository, next to Create repository on the Repositories page (/p/{KEY}/repos/import), copies a repository from another server in three steps. It needs the same permission as creating a repository (Maintainer or Owner).

  1. Source. Enter an https://, http:// or ssh:// URL and, if the source is private, a username and a password or token. ByteBench lists the remote's refs to check the address and credentials, and detects the default branch. The URL follows the same SSRF rules as mirrors: private, loopback, link-local and metadata addresses are refused unless Mirroring:AllowPrivateNetworks (or, when unset, Webhooks:AllowPrivateNetworks) allows them. file:// and other schemes are always refused.
  2. Details. Choose the name, slug, description and default branch (preselected from the source). A repository's visibility is its project's, so it is shown, not chosen. Tick Keep as a pull mirror to have ByteBench keep fetching the source afterwards.
  3. Import. A background job clones every branch and tag. The progress page shows queued, cloning (with the size so far), done or failed (with git's error), and has a Cancel button.
  • Credentials are used for this one clone, kept only in server memory and passed to git through a temporary 0600 credential file; they are never stored, logged or audited. Only if you choose keep as a pull mirror are they saved, encrypted, through the mirror feature (see credentials and safety).
  • What is imported: all branches and tags. Not imported: pull requests, issues, LFS objects, and refs outside refs/heads and refs/tags (so no refs/pull/* or other reserved namespaces).
  • Limits: the clone is stopped if its data on disk passes Import:MaxRepoBytes or git runs longer than Import:TimeoutMinutes. The data is cloned into a private temporary folder under the repository root and only moved into place when complete, so a failed or cancelled import leaves nothing behind.
  • After the import the repository is created through the normal service: the same slug rules, repository.created audit event (marked as imported), plus repository.import_requested and repository.imported. Push listeners (webhooks, CI pipeline detection, smart commits and so on) run once, as a single push of the default branch, not once per imported branch or tag.
  • Restarts: an import interrupted by a server restart is marked failed on the next start and its temporary data is removed; start it again. The slug import is reserved for the wizard.

Cloning over HTTP

Every repository is served over the Git Smart HTTP protocol at /git/{KEY}/{slug}.git:

git clone https://bytebench.example.com/git/WEB/web-app.git
cd web-app
git push origin main

The repository page has HTTPS and SSH tabs in its clone box with the exact URLs for your server.

  • Credentials. Clone, fetch and push all require a ByteBench account. When git prompts, enter your username (or email) and either your password or a personal access token. Use a credential helper (osxkeychain, manager, store) instead of putting a secret in the URL. Failed logins count towards account lockout.
  • Two-factor accounts. If you turned on two-factor sign-in, Git over HTTP refuses your password with a message to use a personal access token instead. See Accounts, sign-in and SSO.
  • Permissions. Clone and fetch need the Viewer role (ViewProject). Push needs Developer or higher (PushCode). If you cannot see the project, git answers 404 Repository not found, the same as for a repository that does not exist. A Viewer who tries to push gets 403.
  • Server requirement. The server needs the git executable on its PATH (or set Git:Executable). Without it the Git endpoints answer 503 and an error is logged at startup.
  • Protocol v2 works (git -c protocol.version=2 ...). The legacy "dumb" HTTP protocol is not supported.
  • Smart commits. After each push, commits whose message mentions an issue key (for example WEB-5: virtualize the list) are added to that issue's activity and shown in its Development panel. Each commit is linked once per issue.
  • Old slugs of renamed repositories keep working (see Rename).

Personal access tokens

A token replaces your password for Git and for the REST API. Create one under Profile, Access tokens (/account/profile): give it a name, choose scopes and pick an expiry of 7, 30, 90 or 365 days, or never.

ScopeAllows
read_repositoryClone and fetch over HTTP (and download LFS objects)
write_repositoryPush, and also clone and fetch
read_api, write_apiREST API read and write access (see REST API and webhooks)
  • The token looks like gbp_ followed by 43 characters and is shown once. ByteBench stores only a SHA-256 hash and a short display prefix.
  • Use it as the password: git clone https://bob@bytebench.example.com/git/WEB/web-app.git, then paste the token when prompted.
  • A token with only read_repository gets 403 on push. Your project role still applies on top of the token's scopes.
  • Revoked or expired tokens are rejected like a wrong password. The token list shows when each was last used.
Treat a token like a password. Never commit it, and do not paste it into issues or chat. If one leaks, revoke it on the same page.

Cloning over SSH

ByteBench has its own SSH server for Git. It is off by default; it is on in appsettings.Development.json (port 2222) and in the Docker image.

git clone ssh://git@bytebench.example.com:2222/WEB/web-app.git
git clone git@bytebench.example.com:WEB/web-app.git     # scp-like form, only works when the public port is 22

Any SSH user name works; use git. The identity comes from your key, not the name.

Your SSH keys

  1. Open Profile, SSH keys (/account/ssh-keys).
  2. Paste the contents of your .pub file, give it a title (default: the key's comment) and optionally an expiry.
  3. Test: ssh -p 2222 git@bytebench.example.com should print Hi alice! You've successfully authenticated, but ByteBench does not provide shell access.
  • Supported: ssh-ed25519 (recommended), ecdsa-sha2-nistp256/384/521 and ssh-rsa of 2048 bits or more. FIDO (sk-...) keys are not supported yet.
  • The list shows each key's SHA256: fingerprint (as ssh-keygen -lf key.pub prints it), when it was added and when it was last used.
  • A key acts as you, with your project permissions. Two-factor sign-in does not apply to SSH keys.
  • Keys of deactivated or locked accounts stop working at once, as do expired keys.
  • A key (by fingerprint) can be registered only once across all users and deploy keys.
  • To pick a specific key: GIT_SSH_COMMAND="ssh -i ~/.ssh/other_key -o IdentitiesOnly=yes" git clone ...
  • Audit events: ssh_key.added, ssh_key.removed.

Deploy keys

A deploy key is an SSH key for a server or CI system that needs one repository and nothing else. Add it under the repository's Settings, Deploy keys (/p/{KEY}/repos/{slug}/settings/deploy-keys; Maintainer or Owner).

  • It works for that repository only, and is read-only unless you tick Allow write access.
  • A write deploy key pushes like a Developer: branch protection applies and there is no admin bypass.
  • Its pushes run webhooks, pipelines and smart commits as the person who added it. It stops working if that person's account is deactivated.
  • Deploy keys only work when the SSH server is on (the page warns you if it is off).
  • Audit events: deploy_key.added, deploy_key.removed.

Git LFS

ByteBench implements the Git LFS Batch API (the basic transfer adapter) at the URL git-lfs derives from the clone URL, /git/{KEY}/{slug}.git/info/lfs/. Nothing needs turning on:

git lfs install
git lfs track "*.psd"
git add .gitattributes
git commit -m "Track PSD files with LFS"
git push
  • Auth is the same as Git over HTTP (password or gbp_ token). The batch response hands out short-lived (one hour) transfer tokens limited to one user, repository and operation, so your password is never echoed back.
  • Permissions. Download needs ViewProject (token scope read_repository or write_repository). Upload needs PushCode (write_repository) and is refused for archived repositories and pull mirrors.
  • Storage. Objects are content-addressed under Lfs:Root (default {ContentRoot}/lfs) and stored once. A repository can only download objects that were uploaded to it. Objects are removed with their repository unless another repository references them; a daily sweep removes leftovers after a one-day grace period.
  • Limit. Lfs:MaxObjectBytes (default 2 GB) per object; bigger uploads get 413.
  • In the file viewer an LFS pointer shows Stored with Git LFS with the real size and a Download link.
  • Not implemented: the LFS locks API (git-lfs prints a one-time warning; silence it with git config lfs.<url>.locksverify false) and git-lfs-authenticate over SSH. With an SSH remote, set lfs.url to the HTTPS LFS URL.
  • LFS objects are not copied by mirrors.

Pull and push mirroring

Under Settings, Mirroring (.../settings/mirroring, Maintainer or Owner) a repository can follow an upstream or copy itself elsewhere.

Pull mirror

At most one per repository. You enter an upstream URL, an optional username with a password or token, a sync interval (at least Mirroring:MinIntervalMinutes, default 5) and whether to mirror only protected branches or all of them.

  • A background service runs git fetch --prune of refs/heads/* and refs/tags/* into the bare repository when the mirror is due. With "only protected branches" it fetches only branches matching a branch protection rule (and all tags).
  • While a pull mirror is enabled the repository is read-only for pushes over HTTP and SSH, and tag changes in ByteBench and LFS uploads are refused too.
  • Push listeners (webhooks, CI, smart commits) do not run for mirrored commits.

Push mirrors

Up to 10 per repository. After every successful push, and on demand with Sync now, ByteBench runs a forced git push --prune of branches and tags to the target. With "only protected branches" it pushes the matching branches plus tags and deletes nothing.

Credentials and safety

  • Passwords and tokens are encrypted at rest and never shown again. Leave the field blank to keep a saved token; changing the URL drops it. During a sync the token goes through a temporary credential helper, never the URL or command line.
  • URLs must be http://, https:// or ssh:// (use ssh://git@host/path.git, not the scp-like form), with no embedded credentials.
  • SSRF guard. Loopback, private, link-local and cloud-metadata addresses are refused when the mirror is saved and again before every sync. Set Mirroring:AllowPrivateNetworks=true to allow private addresses; when unset it follows Webhooks:AllowPrivateNetworks.
  • ssh:// mirrors authenticate with the key in Mirroring:SshKeyFile; new host keys are trusted on first use and stored in Mirroring:KnownHostsFile.
  • Not mirrored: LFS objects, pull requests, issues and other refs such as refs/pull/*.

Forks

The Fork button in a repository's header (any user who can view it) copies the repository into a project where you can create repositories (Maintainer or higher). ByteBench has no personal namespaces, so for a fork of your own, create a project first (you become its Owner). The button shows the fork count and links to the list of forks.

  • The copy is a git clone --bare --local, which hard-links the object files: nearly free on disk and fully independent (deleting either side never breaks the other).
  • Sync fork fetches every upstream branch into the fork's refs/upstream/* and fast-forwards the fork's default branch. If the fork has its own commits it reports "ahead" or "diverged" and changes nothing.
  • PR to upstream opens a cross-fork pull request. Details, including how CI treats such PRs, are in Pull requests.
  • Forking is audited as repository.forked. API: POST /api/v1/projects/{key}/repos/{slug}/forks with { "project": "KEY", "slug": "...", "name": "..." }.

General

  • Name and description.
  • Default branch: a dropdown of existing branches. Changing it also points the bare repository's HEAD, so new clones check it out. Pull requests, the Source page and the web editor use it as the starting point.

Rename

Renaming changes the slug and moves {KEY}/{old}.git to {KEY}/{new}.git. It refuses if another repository or anything on disk already has the new slug.

  • Web URLs with the old slug redirect to the new one, keeping the query and #L anchors.
  • Git over HTTP and SSH keep serving the old slug, so existing clones keep working. Update remotes with git remote set-url origin ... when convenient.
  • Renaming back to a former slug removes that redirect. A real repository always wins over a redirect.

Archive and unarchive

An archived repository is read-only. It shows an Archived badge. git push fails with This repository is archived and read-only; creating, deleting and merging branches and pull requests is refused. Cloning, browsing and search still work. Use it for finished projects you want to keep.

Delete

Type the repository name to confirm. The database rows go first (pull requests with their comments, reviews and activity, watches, AI reviews, redirects, plus notifications linking into it), then the bare repository is moved aside and deleted. This cannot be undone, so take a backup first if in doubt. Deleting an upstream leaves its forks working, just no longer linked.
