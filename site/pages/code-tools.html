Code browsing and tools

Browse files and history in the browser, compare branches, search code, share links to exact lines, and publish tags, releases and source downloads.

The code browser

A repository's Source tab (/p/{KEY}/repos/{slug}) is the front door. Refs and paths travel as query parameters (?ref=feature/x&path=src/app.cs) because branch names contain /.

  • Ref picker: switch between branches and tags. A commit SHA works in the URL too.
  • Breadcrumbs show where you are; click a segment to go up.
  • Folder view: the file tree lists each entry with the last commit that touched it and when. The repository's README.md is rendered under the tree.
  • Last commit bar at the top of the listing: author, message, short SHA and age.
  • Toolbar: History (commits for the current path), Open in editor (the web editor on the current branch and file), Create pull request (when you are on a non-default branch), and a Latest badge linking to the newest published, non-pre-release release.
  • Clone box with HTTPS and SSH tabs (see Repositories).
  • An empty repository shows the command to push a first branch.

Anyone who can view the project (Viewer or higher) can browse. Users who cannot see the project get "Not found".

File view

  • Text files are shown with line numbers and syntax highlighting. Markdown files render as formatted text with a toggle to see the source.
  • Large and binary files: files over 1 MB show "too large to display", and binary files show "Binary file not shown".
  • Git LFS pointers show Stored with Git LFS with the real size and a Download link.
  • Submodules appear as plain names without links.
  • Line links: each line number is a link. #L42 highlights and scrolls to a line, shift-click selects a range (#L10-L20), and the address bar updates so you can share it.
  • Raw content is available through the API: GET /api/v1/projects/{key}/repos/{slug}/raw/{path}?ref=.

Blame

The Blame button next to History on a text file opens /p/{KEY}/repos/{slug}/blame/{rev}/{path}, which shows who last changed each line at that branch, tag or commit. Anyone who can view the file can view its blame.

  • Per line: author, short SHA (a link to the commit), relative date, and the commit subject as a tooltip. Consecutive lines from one commit are grouped, with a divider between groups.
  • Age gutter: a coloured bar beside each line, darker for recent changes, scaled between the oldest and newest commit in that file.
  • View blame before this commit: the arrow in a group opens the same file at that commit's parent, so you can step back through history. It follows a rename (the parent may know the file under an old name). It is missing for the commit that first added the file.
  • Line links and highlighting work as in the file view: #L12 and shift-click ranges, with the same syntax highlighting.
  • Renames are followed, so lines keep the commit that wrote them even if the file was moved later. Lines are attributed to the commit that last changed them, never to a merge commit that only combined branches.
  • Limits: binary files and files over Blame:MaxFileBytes (default 1 MB) or Blame:MaxLines (default 20,000) show a message with a link to the history instead. Results are cached per repository, commit and path (Blame:CacheChars, default about 32 MB of file text), so a commit's blame is computed once.

The API is GET /api/v1/projects/{key}/repos/{slug}/blame?rev=&path= (rev defaults to the default branch). It returns the resolved sha, the commits involved (author, date, subject, the file's path in that commit, and parentSha / parentPath to step back) and ranges of consecutive lines per commit. It answers 404 for an unknown ref or file, 422 for a binary file and 413 for a file over the limits.

History

/p/{KEY}/repos/{slug}/commits?ref=&path=&page= lists commits newest first for a branch, tag or SHA, optionally for one file or folder. Each row links to the commit view. Issue keys in messages (such as WEB-5) are links to the issue. After a push, commits that mention an issue key also appear in that issue's Development panel (smart commits).

Commit view

/p/{KEY}/repos/{slug}/commits/{sha} shows the full message, author, time, parent links and the full SHA, plus a unified diff of every changed file against the first parent (merge commits say so). The diff is highlighted per side, so multi-line strings and comments colour correctly. A button opens the tree at that commit.

Compare branches

/p/{KEY}/repos/{slug}/compare/{base}...{head} lets you pick two branches and shows the commits on head that are not on base, plus the diff since their merge base, with a prefilled Create pull request button. The Branches page links here from the toolbar (Compare) and from each branch. The same data is available as GET .../repos/{slug}/compare?base=&head=.

The Branches page (.../branches) lists every branch with ahead and behind counts against the default branch, protection badges, and buttons to create, delete or start a pull request. Creating a branch needs the Developer role; deleting needs Maintainer and is subject to branch protection.

Code search

RouteSearches
/p/{KEY}/repos/{slug}/search?q=&ref=&case=1&regex=1One repository at a branch, tag or commit (default branch if ref is empty). Also the Search tab and the search box in the repository header
/p/{KEY}/code-search?q=&case=1&regex=1The default branch of every repository in the project (Code search in the sidebar)
  • File contents are searched with git grep against the resolved commit. Matching is case-insensitive unless Match case is ticked. Regex uses Perl-compatible regular expressions, falling back to extended regular expressions if git was built without PCRE.
  • File names are matched against the full path (up to 50).
  • Limits: queries of at most 200 characters, at most 50 matches per file, 200 per repository and 400 per project search, and a 10-second timeout (the git process is killed).
  • Results are grouped by file with one line of context; each line number links to file#L{n} at the searched ref.
  • The query is passed to git without a shell and after -e, so it cannot be interpreted as an option. Everything requires ViewProject.
  • Wiki pages and issues are searched from the global search box, not from code search (see Fields, filters and search).

Only the files in the searched commit are indexed on demand; there is no background index, so very large repositories search slower. The web editor's find-in-files uses the same engine plus your uncommitted changes.

Languages and syntax highlighting

Code is highlighted in your browser with highlight.js 11.11.1, shipped inside ByteBench (no CDN is contacted). It covers about 35 common languages plus Dockerfile, PowerShell and F#. The language comes from the file extension or name. Highlighting applies to the file viewer, diffs (commit view, pull request files, new-PR preview) and fenced code blocks in Markdown (```csharp) in issues, comments, README files and wiki pages. Unknown file types, and files or diffs over 200 KB, stay plain. Token colours follow the light or dark theme.

ByteBench does not compute a per-language percentage bar for repositories.

Tags

The Tags tab (/p/{KEY}/repos/{slug}/tags) lists every tag, newest first, with its commit, the release that uses it, zip and tar.gz downloads, and for annotated tags the tagger, date and message.

  • Create (Developer or higher): a name, a branch or commit (anything git can resolve, such as main~3 or a SHA) and an optional message. With a message it is an annotated tag (tagger = you); without one, a lightweight tag. Names must be valid git ref names (no spaces, .. or ~^:?*[\, no leading -, at most 250 characters) and cannot equal a branch name.
  • Delete (Maintainer or higher). A tag used by a release cannot be deleted, in the UI or by git push --delete (the push prints tag 'v1.0' is used by a release). Delete the release first.
  • Tags pushed with git work as usual and raise tag.created and tag.deleted webhooks. Branch protection and CI triggers only look at branches.

Tag protection

Protected tag rules (who may create matching tags, and whether they can be deleted or moved) are covered in Branch protection, Protected tags. They apply to pushes, the Tags page, the release form and the API.

Releases

A release attaches a title, Markdown notes and files to a tag. Open the Releases tab (.../releases) and click New release (Developer or higher).

  1. Pick an existing tag or type a new name. A new tag is created from the branch or SHA you choose when you save, and is annotated if you give a tag message.
  2. Set a title (defaults to the tag), notes, and Pre-release if it applies.
  3. Click Publish release, or Save draft.
  • Drafts and their assets are visible only to Developers and above. Publishing a draft keeps its first publish date.
  • Edit changes title, notes and flags, not the tag. Delete (Maintainer or higher) removes the release and its asset files, and optionally the tag.
  • Every release lists Source code (zip / tar.gz).
  • Audit: release.created, release.published, release.deleted, tag.deleted. Webhooks: release.published, tag.created, tag.deleted.

Generating release notes

Generate notes fills the notes from git history since the previous release, which is the other release whose tag is the closest ancestor of this one. The notes list merged pull requests (matched by merge commit), non-merge commits, and the issues mentioned in their messages with linked keys. Without an earlier release the whole history is used, up to 300 commits. Edit the text before publishing.

Release assets

Upload files on the release page (Developer or higher). Limits: Releases:MaxAssetBytes per file (default 512 MB) and 50 files per release. Files are stored under random names in Attachments:Root. Downloads (/release-assets/{id}/{name}) are served as attachments with nosniff and a sandbox policy (only verified png, jpeg, gif and webp display inline). Download counts are shown.

Source archives

GET /p/{KEY}/repos/{slug}/archive/{ref}.zip or .tar.gz (also .tgz) works for any branch, tag or commit, with files under {slug}-{ref}/. Access needs ViewProject through a signed-in session or a Bearer token with any scope.
