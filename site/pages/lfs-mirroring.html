Git LFS and mirroring

Store large binary files outside your Git history with Git LFS, and keep a repository in sync with another server using pull and push mirrors.

Both features live in the repository: LFS needs no setup, and mirrors are configured under Settings, Mirroring. The basics of cloning and pushing are in Repositories and Git hosting; this page is the complete reference.

Git LFS

Git LFS replaces large files in your commits with small text pointers and keeps the real content on the server. ByteBench implements the LFS Batch API with the basic transfer adapter. There is nothing to turn on: every repository accepts LFS objects.

Using it from a client

Install the git-lfs client once per machine, then in your clone:

git lfs install                      # once per machine
git lfs track "*.psd" "*.zip"        # writes .gitattributes
git add .gitattributes
git add design.psd
git commit -m "Add the design file"
git push origin main                 # uploads the objects, then the commits

git-lfs finds the server by itself: it adds /info/lfs to the clone URL, so for https://bytebench.example.com/git/WEB/web-app.git it talks to https://bytebench.example.com/git/WEB/web-app.git/info/lfs/. Cloning a repository that has LFS files downloads them after the checkout.

Endpoints

All paths are relative to /git/{KEY}/{slug}.git/info/lfs/.

RequestWhat it does
POST objects/batchThe client lists the objects it wants (at most 1000 per batch). For download ByteBench returns a download action for every object the repository has, and a per-object 404 for the rest. For upload it returns an upload action and a verify action, or no action when the repository already has the object. Objects over the size limit get a per-object 422.
PUT objects/{oid}Upload. The body is streamed to a temporary file and hashed; the object is stored only if its SHA-256 equals the oid (otherwise 422). Larger than Lfs:MaxObjectBytes gives 413.
GET objects/{oid}Download. ?download=name adds a Content-Disposition: attachment header.
POST objects/verify200 when the repository has the object with that size, otherwise 404.

Authentication and permissions

  • Same credentials as Git over HTTP: Basic with your password or a personal access token, or Authorization: Bearer gbp_.... A missing or wrong login gets 401 with LFS-Authenticate, so git-lfs falls back to git's credential helper. Two-factor accounts must use a token (see Accounts, sign-in and SSO).
  • Transfer tokens. The batch response carries a one-hour Bearer token for the upload, download and verify actions. It is limited to one user, one repository and one operation, so your password is never echoed back to the client.
  • Download needs the Viewer role (ViewProject); a token needs scope read_repository or write_repository. A signed-in browser session can download too, which is what the file viewer's link uses.
  • Upload needs Developer or higher (PushCode); a token needs write_repository. Archived repositories and pull mirrors refuse uploads.

Storage and cleanup

  • Objects are content-addressed under Lfs:Root (default {ContentRoot}/lfs, /data/lfs in the Docker image) as {oid[0..2]}/{oid[2..4]}/{oid}, and stored once even when several repositories hold them.
  • A repository can only download objects that were uploaded to it, even if another repository stores the same content.
  • Deleting a repository deletes its objects unless another repository references them. A daily sweep removes objects left behind by deleted projects and stale temporary files, after a one-day grace period.

Not implemented: the LFS file locking API (git-lfs prints a one-time warning and carries on; silence it with git config lfs.<url>.locksverify false) and git-lfs-authenticate over SSH. With an SSH remote, set lfs.url to the HTTPS LFS URL:

git config lfs.url https://bytebench.example.com/git/WEB/web-app.git/info/lfs

Mirroring

A repository can follow an upstream server (a pull mirror) and copy itself to other servers (push mirrors). Open Settings, Mirroring (/p/{KEY}/repos/{slug}/settings/mirroring); you need the Maintainer role or higher. Each mirror shows its last status, time and message (or git's error) and a Sync now button.

Pull mirrorPush mirror

DirectionUpstream to this repositoryThis repository to the target
WhenOn the interval you set (default 60 minutes, at least Mirroring:MinIntervalMinutes, at most 7 days), and on Sync nowAfter every successful push, after a pull mirror changed something, and on Sync now

Pull mirror

  1. Open Settings, Mirroring and add a pull mirror.
  2. Enter the upstream URL, for example https://git.example.org/team/app.git.
  3. If the upstream needs a login, enter a username and a password or access token.
  4. Choose the sync interval and whether to mirror only protected branches.
  5. Save. The first sync starts at the next poll (the worker checks for due mirrors every Mirroring:PollSeconds, default 30); press Sync now to start it at once.
  • What is synced. All branches (refs/heads/*) and tags (refs/tags/*) are fetched, forced, straight into the bare repository, and branches or tags deleted upstream are pruned locally. With only protected branches the sync lists the upstream branches, fetches only those that match one of this repository's branch protection rules (tags are always fetched), and deletes matching local branches that are gone upstream. Branches that match no rule are neither fetched nor deleted.
  • Read-only repository. While an enabled pull mirror exists, every push over HTTP and SSH is refused with "this repository is a pull mirror...", creating and deleting tags in ByteBench is refused, and so are LFS uploads and web-editor commits.
  • Hooks do not run. Webhooks, CI pipelines and smart commits run on pushes, not on mirrored commits. A pull mirror that changed refs does queue the repository's push mirrors.

Push mirrors

Add a push mirror with the target URL and credentials. After every successful push to the repository, and on Sync now, a background queue runs a forced push of refs/heads/* and refs/tags/* with --prune, so the target follows this repository exactly, including deleted branches. With only protected branches it pushes the matching branches plus all tags and deletes nothing.

Because the push is forced, the target must allow force pushes and ref deletion for the account you give it. If the target has its own branch protection, the sync fails with git's message, which ByteBench shows on the mirror.

Credentials

  • Passwords and tokens are encrypted at rest (ASP.NET Core Data Protection) and never shown again. Leave the field blank when editing to keep the saved one. Changing the URL drops the saved token, so it can never follow the URL to another host: enter it again.
  • Credentials written into the URL itself (https://user:pw@host/...) are rejected. Use the fields.
  • ssh:// mirrors authenticate with the private key in Mirroring:SshKeyFile on the server (one key for all SSH mirrors); without one they cannot authenticate. New host keys are trusted on first use and stored in Mirroring:KnownHostsFile (default {ContentRoot}/keys/mirror_known_hosts). Add the matching public key to the other server's account or as a deploy key there. The username and token fields apply to HTTP(S) only.

URL rules and the SSRF guard

A mirror makes your server open connections to a URL a user chose, so the URL is checked when the mirror is saved and again before every sync.

RuleDetail
Schemeshttp://, https:// and ssh:// only. Write SSH as ssh://git@host/path.git, not the scp-like git@host:path.
No credentials, no optionsNo user info in the URL and no option-like host or path (nothing starting with -)
Blocked addressesLoopback, private (RFC 1918 and ULA), link-local, CGNAT and cloud-metadata addresses
No DNS tricksThe host is resolved right before git runs and git is pinned to the checked address, so DNS rebinding cannot swap it. Redirects are not followed.

To mirror from or to a server on your own network, set Mirroring:AllowPrivateNetworks=true. When it is unset the value of Webhooks:AllowPrivateNetworks applies (on in appsettings.Development.json). It is the same guard that webhooks use; see REST API and webhooks.

Protected branches and protected tags

  • Branch protection decides which branches the "only protected branches" option covers, in both directions. It does not block a pull mirror's sync, because the mirror is the one authority on this repository's refs while it exists.
  • Protected tags (Branch protection and merge queue) govern pushes and tag actions in ByteBench. A pull mirror writes tags directly and forces them, so a tag that moves or disappears upstream moves or disappears here as well, even if a rule says "block moving". The pull mirror's read-only rule is what stops people from changing tags by hand. A push mirror sends tags forced, so the target must allow tag updates.
  • Not mirrored: LFS objects, pull requests, issues and other refs such as refs/pull/*.

LFS and mirrors

A mirror copies Git history only, so a mirrored repository holds LFS pointers but not the files. To copy them, run git lfs fetch --all against the source and git lfs push --all <target> to a writable target repository.

Server settings

Mirroring:Enabled (default true) runs the background syncs; Mirroring:PollSeconds (30) is how often due pull mirrors are looked for; Mirroring:TimeoutSeconds (600) kills a slow sync; Mirroring:MinIntervalMinutes (5) is the shortest pull interval; Mirroring:AllowPrivateNetworks, SshKeyFile and KnownHostsFile are described above. All keys are in the Configuration reference. Audit events: mirror.created, mirror.updated, mirror.deleted, mirror.sync_requested.

SymptomCheck
"this repository is a pull mirror..." when pushingExpected while the pull mirror is enabled. Disable or delete it to make the repository writable again.

LFS upload answers 422The upload's SHA-256 differs from the pointer; the file changed after it was tracked. Run git lfs fsck locally and add the file again.
