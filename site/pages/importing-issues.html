Importing issues from GitHub, GitLab and Jira

Copy the issues of a GitHub repository, a GitLab project or a Jira project into a ByteBench project, with their comments, labels and milestones. You can run it again later to pick up what is new.

The importer reads the source's API with a token you provide, creates the issues here and remembers what it created, so nothing is duplicated. To import from a spreadsheet instead, see CSV import. For copying a Git repository, see Repositories and Git hosting.

Start an import

Open the project's issue list, then Menu, Import from GitHub, GitLab or Jira (/p/{KEY}/import/tracker). You need the Maintainer role in the project. The page also has a link from the CSV import page. There are three steps.

  1. Source. Choose GitHub, GitLab or Jira and fill in the fields (see the table below). Check connection asks the source for the project; a wrong address, project name or token is shown as an error. Nothing is created in this step.
  2. Review. The page shows the project's name, description, how many issues, labels and milestones it has, a few sample titles and any warning from the source. GitHub's issue count includes pull requests. Choose whether to include closed issues, comments and (GitHub only) pull requests as issues. When the source has statuses beyond Open and Closed, and always for Jira, a table maps each source status to one of this project's workflow statuses. Start import queues the import.
  3. Progress. A background job reads the source. The page updates every two seconds with a progress bar, counters (created, already imported, comments, labels, milestones, links) and, when it ends, the warnings. Cancel import stops it. The project's recent imports are listed under the wizard, and Open reopens the progress of any of them.
SourceFields
GitHubRepository as owner/name. Address: leave blank for github.com; for GitHub Enterprise Server enter the API root, for example https://ghe.example.com/api/v3. Token: optional for a public repository.
GitLabProject path (group/subgroup/project) or numeric id. Address: blank for gitlab.com, or your self-hosted GitLab. Token: optional for a public project.
JiraAddress (required, for example https://example.atlassian.net), project key (for example PROJ), and the credentials: on Jira Cloud your account email plus an API token; on Server or Data Center a personal access token (leave the user blank) or a username and password.

Tokens and the least access they need

  • GitHub: a fine-grained token limited to the one repository with Issues: read-only and Metadata: read-only, or a classic token with the repo scope (public_repo for a public repository).
  • GitLab: a personal or project access token with the read_api scope.
  • Jira Cloud: an API token created at id.atlassian.com for your own account, with your account email. Only the issues that account can browse are imported. Jira Server and Data Center: a personal access token, or a username and password.

The token is sent only to the source's own API for this import. It is kept in server memory for the one run and is never stored: not in the database, the import record, the audit log, the server log or any error message, and the page never shows it again. If the server restarts mid-import the token is gone, so you start the import again.

What is imported

Readers fill what the source has; a field the source does not have stays empty (GitHub and GitLab have no statuses beyond open and closed, for example). Text is converted to Markdown.

Not imported: sprints, attachment files, pull-request branches and code, reactions, watchers, time tracking, and anything the source's API doesn't offer. If a reader could not carry something over for one issue (for example a comment list that was cut short), the import records a warning naming the issue.

Each imported issue ends its description with a footer, Imported from GitHub #12 (linked to the original when the source gave an address) and the original author's name when no user matched. It also gets the activity entry imported from GitHub #12.

How things are matched

Statuses

Each issue gets a workflow status of the project in this order: the status you chose in the mapping table; otherwise the status with the same name (ignoring case); otherwise the first status of the same category (Backlog, To Do, In Progress, In Review, Done). If the project has no status of that category, closed issues go to the last status and open ones to the first To Do status. GitHub and GitLab only have open and closed, so open issues land in the first To Do status and closed ones in the first Done status unless you map them. A closed issue gets a closed date.

People

The author, assignee and each commenter are matched by email address first, then by user name. A person only counts when they can view the target project. People the source doesn't show an email for (GitHub and GitLab often hide it) are matched by user name. If nobody matches, the issue or comment is attributed to the person who ran the import and the original person's name is written into the text (the description's footer, or the comment's first line). The import ends with one warning listing the people who weren't matched; add them as members and run it again.

Labels and milestones

Labels are matched by name, ignoring case, against the project's labels and its groups' labels; missing ones are created (names are cut at 40 characters). Milestones are matched by title; missing ones are created.

Running it again

ByteBench remembers which source issue, comment, label and milestone became which here, per source project. Running the same import again therefore:

  • creates only issues it hasn't imported before (they show up as already imported in the counters for the others);
  • never changes an existing issue: edits you made here stay, and edits made in the source are not copied;
  • adds comments that are new in the source to the already imported issues;
  • completes parents (only for issues that have no parent yet) and links that were missing.

Re-running is also how you continue after a cancel, a failure or a restart, and how you import the issues past the per-import limit. The remembered source is identified by the kind, the address and the project name in lower case, so importing the same repository twice with a different address is treated as a different source.

Limits, rate limits and waits

  • Issues per import: at most TrackerImport:MaxIssues (default 20000) are read; the import then stops with a warning, and a second run continues with the rest.
  • Concurrency: TrackerImport:MaxConcurrent imports run at once on the server (default 2); a project can have TrackerImport:MaxActivePerProject (default 1) queued or running at a time.
  • Requests: one request is abandoned after TrackerImport:RequestTimeoutSeconds (default 60). Answers larger than 16 MB are refused, and redirects are not followed (use the project's current address). A server error (5xx) is retried a couple of times.
  • Rate limits: when the source answers 429, or 403 with a used-up limit, the import waits for the time the source gives (Retry-After or the reset header) and then continues, as long as the wait is at most TrackerImport:MaxRateLimitWaitSeconds (default 120) and it has not happened more than four times in a row for the same request. Otherwise it fails with a message saying about how long to wait. Anonymous access to GitHub and GitLab has low limits, so use a token for large projects.

Cancelling, restarts and failures

  • Cancel stops the run. Issues already written stay. The import is shown as Cancelled, and running it again continues where it stopped.
  • An import that is still waiting in the queue when you cancel it is simply marked Cancelled.
  • If the server restarts while an import is queued or running, it is marked Failed (The server restarted before this import finished) on the next start, because the token was only in memory. Issues already imported are kept; start it again.
  • A problem with the source (bad token, project not found, rate limit) ends the import as Failed with the source's message; the issues written before it are kept.

Safety

  • No notifications or webhooks. Importing creates issues, comments and activity directly, so nobody is emailed or notified, and no webhooks, automation rules or CI triggers fire for them. When an import finishes, open boards and issue lists refresh.
  • Audit log. project.tracker_import_requested when it is queued (source, project, address, and only whether credentials were given), project.tracker_imported when it finishes (counts), and project.tracker_import_cancel_requested when someone cancels. Credentials are never recorded.
  • SSRF rule. Addresses must be http:// or https:// without credentials, query or fragment. Loopback, private, link-local, carrier-grade NAT and cloud-metadata addresses are refused, both when you enter the address and again for every connection (so DNS tricks can't redirect it). To import from a GitLab, GitHub Enterprise or Jira server on your own network, set TrackerImport:AllowPrivateNetworks to true; when unset, Webhooks:AllowPrivateNetworks applies, the same rule as webhooks, mirrors and Workbench (see REST API and webhooks).

Self-hosted servers

  • GitHub Enterprise Server: put the API root in Address, typically https://HOST/api/v3, not the web address.
  • Self-hosted GitLab: put the GitLab address (for example https://gitlab.example.com) in Address.
  • Jira Server and Data Center: put the Jira address in Address and use a personal access token, or a username and password. Jira Cloud needs the account email and an API token.
  • If the server is on a private network, see the SSRF rule above.
