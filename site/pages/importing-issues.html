Importing issues from GitHub, GitLab, Jira, Trello, Linear and Asana

Copy the issues of a GitHub repository, a GitLab project, a Jira project, a Trello board, a Linear team or an Asana project into a ByteBench project, with their comments, labels and milestones. You can run it again later to pick up what is new.

The importer reads the source's API with a token you provide, creates the issues here and remembers what it created, so nothing is duplicated. To import from a spreadsheet instead, see CSV import. For copying a Git repository, see Repositories and Git hosting.

Start an import

Open the project's issue list, then Menu, Import from GitHub, GitLab or Jira (/p/{KEY}/import/tracker). You need the Maintainer role in the project. The page also has a link from the CSV import page. There are three steps.

  1. Source. Choose GitHub, GitLab, Jira, Trello, Linear or Asana and fill in the fields (see the table below). Check connection asks the source for the project; a wrong address, project name or token is shown as an error. Nothing is created in this step.
  2. Review. The page shows the project's name, description, how many issues, labels and milestones it has, a few sample titles and any warning from the source. GitHub's issue count includes pull requests. Choose whether to include closed issues, comments and (GitHub only) pull requests as issues. When the source has statuses beyond Open and Closed, and always for Jira, a table maps each source status to one of this project's workflow statuses. Start import queues the import.
  3. Progress. A background job reads the source. The page updates every two seconds with a progress bar, counters (created, already imported, comments, labels, milestones, links) and, when it ends, the warnings. Cancel import stops it. The project's recent imports are listed under the wizard, and Open reopens the progress of any of them.
SourceFields
GitHubRepository as owner/name. Address: leave blank for github.com; for GitHub Enterprise Server enter the API root, for example https://ghe.example.com/api/v3. Token: optional for a public repository.
GitLabProject path (group/subgroup/project) or numeric id. Address: blank for gitlab.com, or your self-hosted GitLab. Token: optional for a public project, but gitlab.com only serves a public project's labels, milestones, comments and issue links to signed-in callers, so without a token those four are skipped (a warning says so; issues keep their label names) and only the issues themselves are imported.
JiraAddress (required, for example https://example.atlassian.net), project key (for example PROJ), and the credentials: on Jira Cloud your account email plus an API token; on Server or Data Center a personal access token (leave the user blank) or a username and password.
TrelloBoard: the short link or id, or the board's address (https://trello.com/b/AbCdEfGh/name). API key and token (both needed; the token may be left out for a public board). No address field: the importer talks to api.trello.com.
LinearTeam key (the prefix of the issue numbers, for example ENG) or the team's id, and a personal API key. No address field: api.linear.app.
AsanaProject id (the long number in the project's address, app.asana.com/0/<project id>/list) and a personal access token. No address field: app.asana.com.

Tokens and the least access they need

  • GitHub: a fine-grained token limited to the one repository with Issues: read-only and Metadata: read-only, or a classic token with the repo scope (public_repo for a public repository).
  • GitLab: a personal or project access token with the read_api scope.
  • Jira Cloud: an API token created at id.atlassian.com for your own account, with your account email. Only the issues that account can browse are imported. Jira Server and Data Center: a personal access token, or a username and password.
  • Trello: an API key from trello.com/power-ups/admin (create a Power-Up, then copy its key) and a token generated for that key and authorized with read access. Enter the key in the API key field and the token in the token field. Trello takes both as the key and token query parameters of each request, so they are part of the request address; ByteBench never puts request addresses into messages, warnings, the audit log or the job record.
  • Linear: a personal API key from Settings, Account, Security & access (read-only is enough). It is sent as the bare Authorization header, as Linear expects for personal keys; a Linear OAuth access token (lin_oauth_...) is sent as Bearer automatically.
  • Asana: a personal access token from the developer console (app.asana.com/0/my-apps), sent as Authorization: Bearer.

The token is sent only to the source's own API for this import. It is kept in server memory for the one run and is never stored: not in the database, the import record, the audit log, the server log or any error message, and the page never shows it again. If the server restarts mid-import the token is gone, so you start the import again.

What is imported

Readers fill what the source has; a field the source does not have stays empty (GitHub and GitLab have no statuses beyond open and closed, for example). Text is converted to Markdown.

Not imported: pull-request branches and code, reactions, watchers, time tracking, GitLab iterations, and anything the source's API doesn't offer. If a reader could not carry something over for one issue (for example a comment list that was cut short), the import records a warning naming the issue.

Each imported issue ends its description with a footer, Imported from GitHub #12 (linked to the original when the source gave an address) and the original author's name when no user matched. It also gets the activity entry imported from GitHub #12.

Trello, Linear and Asana

These three have no statuses beyond what their own structure offers, so the status mapping table always appears for them. Each source fills the fields below; whatever a source lacks stays empty. Tokens never appear in messages (see tokens). People are matched as described under people: Linear gives the key owner people's email, Asana the assignee's email, Trello only a user name.

Issues are read oldest first, 50 per request, with cursor paging. If Linear refuses a query as too complex the page size is halved and the page is asked again. Linear rate limits (the RATELIMITED error, or HTTP 429 with a wait) end the import with a message saying to wait a few minutes, or are waited out when Linear names a short wait. Linear answers HTTP 400 for some refused queries without saying why in a form the importer can read, so a persistent 400 is reported as "Linear rejected the request".

Tasks are read in the project's own order (Asana has no creation-order listing) with limit=100 and an offset that is applied to ByteBench's own request address, never to a link Asana returns. With closed issues off, only incomplete tasks are asked for. Each task costs a few extra requests (comments, dependents, attachments, subtasks), so a big project is subject to Asana's per-minute limit: a 429 is waited out as described under limits.

How things are matched

Statuses

Each issue gets a workflow status of the project in this order: the status you chose in the mapping table; otherwise the status with the same name (ignoring case); otherwise the first status of the same category (Backlog, To Do, In Progress, In Review, Done). If the project has no status of that category, closed issues go to the last status and open ones to the first To Do status. GitHub and GitLab only have open and closed, so open issues land in the first To Do status and closed ones in the first Done status unless you map them. A closed issue gets a closed date.

People

The author, assignee and each commenter are matched by email address first, then by user name. A person only counts when they can view the target project. People the source doesn't show an email for (GitHub and GitLab often hide it) are matched by user name. If nobody matches, the issue or comment is attributed to the person who ran the import and the original person's name is written into the text (the description's footer, or the comment's first line). The import ends with one warning listing the people who weren't matched; add them as members and run it again.

Labels and milestones

Labels are matched by name, ignoring case, against the project's labels and its groups' labels; missing ones are created (names are cut at 40 characters). Milestones are matched by title; missing ones are created.

Sprints

Jira sprints become ByteBench sprints (they used to become sprint: ... labels). Jira Cloud and Server both report sprints through the agile API (/rest/agile/1.0/board/{id}/sprint, which includes the goal); when that isn't available to the token, they are read from the issues' Sprint field instead.

  • Fields: name (cut at 100 characters), goal (500), start and end date, and the state: future is Planned, active is Active, closed is Completed.
  • An issue in several sprints (Jira carries unfinished work over) goes to the latest: the active one, otherwise the one that started last.
  • Only one sprint can be active. If Jira has several active sprints, or the project already has an active sprint, the extra ones are imported as Completed when their end date has passed, otherwise as Planned, and the import adds a warning for each.
  • Completed sprints keep their dates, get a completion time (Jira's complete date, else the end date) and the same committed and completed counts and points that completing a sprint here stores, worked out from the imported issues, so velocity and sprint reports aren't empty. An active sprint gets its committed counts, like starting one. No burndown history is made up.
  • Fallback: if an issue's sprint can't be read or isn't one the token can list, the issue gets a sprint: NAME label and a warning instead.
  • Re-runs add only sprints that are new in Jira and never change a sprint that was imported before, even if you renamed, started or completed it here. New issues of a re-run go into the sprints that already exist.

Attachment files

With Copy attachment files on (IncludeAttachments, off by default), the files are downloaded from the source and stored as ordinary issue attachments, uploaded by the person who runs the import, using the same storage, content-type checks, hashes and limits as an upload in the issue page (Attachments:MaxBytes per file, Attachments:MaxPerIssue per issue). With it off, nothing is downloaded and attachments are only listed in the description, as before.

  • Jira: every file in the issue's attachment list is attached to the issue (downloads need the same credentials as the API). Jira's inline pictures stay as [image: name] placeholders in the text, since Jira refers to them by file name; the file is in the issue's attachments.
  • GitLab: files linked in issue and comment text as /uploads/HASH/NAME are downloaded from the project.
  • GitHub: files linked in issue and comment text from https://github.com/user-attachments/... and https://user-images.githubusercontent.com/.... The token is not sent to these hosts, so files of a private repository usually can't be fetched and are reported as warnings; keep their original link.
  • Links in the text: for issues and comments created by this run, the link or image in the text is rewritten to the local copy (/attachments/ID/NAME), so pictures show inline. A file that could not be copied keeps its original link. Issues that already existed are never edited: their files are attached but their text stays as it is. Jira's attachments that could not be copied are listed at the end of the description.
  • Limits: at most TrackerImport:MaxAttachmentBytes (default 500 MB) in total per import, files over TrackerImport:MaxAttachmentFileBytes (default: Attachments:MaxBytes, which is also the ceiling) are skipped, file types in TrackerImport:BlockedAttachmentExtensions (executables and scripts such as .exe, .bat, .ps1) are skipped, and an issue never gets more than Attachments:MaxPerIssue files. A file that is too big, blocked, deleted or forbidden is one warning naming the issue and file; it never fails the import. A second run retries those and does not copy a file twice (ImportedItem remembers each file per issue).
  • Safety: downloads go through the same address guard as the API calls, and again for every redirect. Attachment hosts often redirect to a CDN (GitHub uploads, Jira media, GitLab uploads): up to 3 redirects are followed, each checked against the private-address rule, a redirect from https to http is refused, and the Authorization or PRIVATE-TOKEN header is sent only to the source's own address (same scheme, host and port), never to another host. The size is enforced while streaming, whatever the source claims. Files are only ever written to the attachment storage under a random name; the file name is cleaned like an upload's. Warnings and the audit event contain file names and counts, never addresses or tokens.

Running it again

ByteBench remembers which source issue, comment, label, milestone, sprint and attachment file became which here, per source project. Running the same import again therefore:

  • creates only issues it hasn't imported before (they show up as already imported in the counters for the others);
  • never changes an existing issue: edits you made here stay, and edits made in the source are not copied;
  • adds comments, sprints and attachment files that are new (or that failed before) to what is already there;
  • completes parents (only for issues that have no parent yet) and links that were missing.

Re-running is also how you continue after a cancel, a failure or a restart, and how you import the issues past the per-import limit. The remembered source is identified by the kind, the address and the project name in lower case, so importing the same repository twice with a different address is treated as a different source.

Limits, rate limits and waits

  • Issues per import: at most TrackerImport:MaxIssues (default 20000) are read; the import then stops with a warning, and a second run continues with the rest.
  • Concurrency: TrackerImport:MaxConcurrent imports run at once on the server (default 2); a project can have TrackerImport:MaxActivePerProject (default 1) queued or running at a time.
  • Requests: one request is abandoned after TrackerImport:RequestTimeoutSeconds (default 60). Answers larger than 16 MB are refused, and redirects of API calls are not followed (use the project's current address); attachment downloads follow at most 3, see attachments. A server error (5xx) is retried a couple of times.
  • Rate limits: when the source answers 429, or 403 with a used-up limit, the import waits for the time the source gives (Retry-After or the reset header) and then continues, as long as the wait is at most TrackerImport:MaxRateLimitWaitSeconds (default 120) and it has not happened more than four times in a row for the same request. Otherwise it fails with a message saying about how long to wait. Anonymous access to GitHub and GitLab has low limits, so use a token for large projects.

Cancelling, restarts and failures

  • Cancel stops the run. Issues already written stay. The import is shown as Cancelled, and running it again continues where it stopped.
  • An import that is still waiting in the queue when you cancel it is simply marked Cancelled.
  • If the server restarts while an import is queued or running, it is marked Failed (The server restarted before this import finished) on the next start, because the token was only in memory. Issues already imported are kept; start it again.
  • A problem with the source (bad token, project not found, rate limit) ends the import as Failed with the source's message; the issues written before it are kept.

Safety

  • No notifications or webhooks. Importing creates issues, comments and activity directly, so nobody is emailed or notified, and no webhooks, automation rules or CI triggers fire for them. When an import finishes, open boards and issue lists refresh.
  • Audit log. project.tracker_import_requested when it is queued (source, project, address, and only whether credentials were given), project.tracker_imported when it finishes (counts), and project.tracker_import_cancel_requested when someone cancels. Credentials are never recorded.
  • SSRF rule. Addresses must be http:// or https:// without credentials, query or fragment. Loopback, private, link-local, carrier-grade NAT and cloud-metadata addresses are refused, both when you enter the address and again for every connection (so DNS tricks can't redirect it). To import from a GitLab, GitHub Enterprise or Jira server on your own network, set TrackerImport:AllowPrivateNetworks to true; when unset, Webhooks:AllowPrivateNetworks applies, the same rule as webhooks, mirrors and Workbench (see REST API and webhooks).

Self-hosted servers

  • GitHub Enterprise Server: put the API root in Address, typically https://HOST/api/v3, not the web address.
  • Self-hosted GitLab: put the GitLab address (for example https://gitlab.example.com) in Address.
  • Jira Server and Data Center: put the Jira address in Address and use a personal access token, or a username and password. Jira Cloud needs the account email and an API token.
  • If the server is on a private network, see the SSRF rule above.
