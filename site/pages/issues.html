Issues and workflows

Issues are the unit of work in a GitBench project: they have a type, a status from your project's workflow, people, labels, links to other issues, files, and a live view of the code that implements them.

Every issue belongs to one project and is numbered per project, so the third issue of project WEB is WEB-3. That key is what you type in commit messages, branch names, pull request titles and comments to refer to it. Open the issue list at /p/{KEY}/issues (sidebar: Issues) and an issue at /p/{KEY}/issues/{number}.

Creating and editing issues

Click New issue on the issue list (/p/{KEY}/issues/new). You need the Developer role or above (the EditIssues permission). Fill in:

On the issue page most fields are edited in place and saved when you change them. Every change adds a line to the issue's activity ("changed status from To Do to In Progress"), notifies watchers, refreshes other people's open pages live, and fires the issue.updated webhook.

If Claude is configured (AI setup), the new-issue page offers Draft with AI and a duplicate check, and the issue page offers Catch me up. AI never saves anything by itself.

Types and priorities

The five built-in types are Task, Bug, Feature, Story and Epic, plus Sub-task for the bottom level of the hierarchy. The list is fixed: you cannot add types, but you can add custom fields that apply only to certain types (for example a required Severity for bugs). Priorities are the five fixed levels above and sort Highest first in the issue list's priority sort and on boards with a priority swimlane.

Labels

Labels are coloured tags. A project has its own; a group can also define labels that every project below it inherits (shown read-only in the project and marked Group). Developers can apply labels; creating, renaming and deleting them needs Maintainer. Filter by label in the list, in GQL (labels = urgent) or in reports.

Workflows, custom statuses and transitions

Each project has its own workflow: an ordered list of statuses (name, colour and category) and, optionally, the moves allowed between them. Project Owners edit it at Settings, Edit workflow (/p/{KEY}/settings/workflow).

  • Categories. Every status belongs to one of five categories: Backlog, To Do, In Progress, In Review or Done. Done-category statuses count as closed. Sprints, burndown, the open/closed tabs, the API's status field and the delivery reports all work off categories, so you can rename statuses freely without breaking them.
  • Default workflow. A new project gets five statuses, one per category.
  • Editing. Add, rename, recolour, reorder and recategorise statuses. A status that still has issues can be deleted only after you move them elsewhere (the page offers it). The workflow must keep at least one Done status and one open status.
  • Transitions. A matrix of checkboxes: tick where issues may move to from each status. A status with nothing ticked may move anywhere. When transitions are restricted, the board greys out and refuses disallowed columns, the status picker disables them, and the API answers 422. Automation rules and bulk edits obey the same transitions.

Hierarchy: epics and sub-tasks

An issue can have a parent in the same project, up to three levels: Epic, then Story/Task/Bug/Feature, then Sub-task.

  • An epic has no parent; its children can be any type except Epic and Sub-task.
  • A sub-task must have a parent that is neither an epic nor a sub-task, and cannot have children.
  • Other types may have an epic as parent (or none); their children can only be sub-tasks.
  • No cycles. These rules are checked on every create and update, including through the API (violations are 422), so changing a type can be refused.

The issue page shows a parent breadcrumb, a Parent picker and a child panel with progress by count and points, where you can create or add children inline. The Epics page (/p/{KEY}/epics) lists each epic with child count, points and progress. Deleting an issue deletes its sub-tasks (the UI says how many first); an epic's children are kept and unlinked.

Issue links and link types

A link connects two issues with one of four built-in types, and each side shows its own phrase:

TypeSource side / target side
blocksblocks / is blocked by
relates torelates to / relates to
duplicatesduplicates / is duplicated by (the UI offers to close the duplicate)
clonesclones / is cloned by

You cannot define extra link types. Links can cross projects, but only to issues you can view; links to issues you cannot view are hidden. Self-links and a second link of the same type between the same two issues are refused. An open "is blocked by" link shows a blocked marker on the board card, list row and links panel; moving a blocked issue still works but warns you. "Blocks" links also appear as arrows on the roadmap.

# Link WEB-5 as blocking OPS-2
curl -X POST -H "Authorization: Bearer $GITBENCH_TOKEN" -H "Content-Type: application/json" \
  -d '{"type":"blocks","issue":"OPS-2"}' \
  https://gitbench.example.com/api/v1/projects/WEB/issues/5/links

The API also has GET /links, DELETE /links/{linkId} and GET /children under the issue path. Adding a link needs EditIssues on this issue and view access to the other.

Comments and mentions

Developers and above can comment (the Comment permission). Comments are Markdown, can have files attached, and can be edited; editing or deleting someone else's comment needs Maintainer. Writing @username notifies that person (only if they can view the project); mentions inside code spans and code blocks are ignored, and editing a description notifies only people newly mentioned. Editing a comment notifies nobody.

Watchers and notifications

The reporter, the assignee and everyone who comments watch an issue automatically. Use Watch / Watching on the issue to toggle it, or Mute to stay a watcher without watcher notifications (assignment and mentions still reach you). Watchers are notified of comments, status changes, closing and reopening, and link and parent changes. You never get notified of your own actions, and each person gets at most one notification per event. Channels and preferences are described in Notifications and email. Search by watcher with watcher = currentUser().

Attachments

Attach files from the Attachments panel, or by picking, dragging or pasting into a description or comment editor (images insert as ![name](url)). Uploading needs Developer or above. Limits are set by Attachments:MaxBytes (default 25 MB per file) and Attachments:MaxPerIssue (default 50); see Configuration reference. Files are stored on disk under Attachments:Root (default attachments/ next to the app) with random names. The uploader can delete their own files and Maintainers can delete anyone's.

Downloads need a signed-in user who can view the project. Only PNG, JPEG, GIF and WebP are shown inline, and only if the bytes match; everything else, including SVG, HTML and PDF, is served as a download with nosniff and a sandboxing Content-Security-Policy.

curl -H "Authorization: Bearer $GITBENCH_TOKEN" -F "file=@screenshot.png" \
  https://gitbench.example.com/api/v1/projects/WEB/issues/12/attachments

Bulk edit

With Developer or above, tick issues in the list (or select all on the page). A sticky bar offers status, assignee, priority, milestone, add label, remove label, and Delete (Maintainer only, with confirmation). Permissions and values are validated for every issue first, then everything is applied in one transaction with a per-issue activity entry. If one issue may not move (for example because of a workflow transition), nothing changes and the message names that issue. Each watcher gets one batched notification, for example "2 issues in WEB: WEB-5, WEB-10".

Issue templates

Templates pre-fill the new-issue form with a title prefix, type, Markdown body and default labels. Maintainers define them at /p/{KEY}/settings/fields (the Templates tab); pick one with the Template selector or open /p/{KEY}/issues/new?template=t{id}. GitBench also offers Markdown files from .gitbench/issue_templates/*.md on the default branch of the project's first repository, with optional front matter:

---
name: Bug report
title: "[Bug] "
labels: bug, needs-triage
type: Bug
---
## What happened

## Steps to reproduce

## Expected

The API lists them at GET /api/v1/projects/{key}/issue-templates.

Activity and history

The activity timeline on each issue records who changed what and when: field changes (including old and new estimates), status moves, parent and link changes (written to both ends of a link), attachments, sprint moves, and code references. It is the data behind the sprint burndown and the delivery reports, which rebuild an issue's time in each status from the status-change lines. Security-relevant events (deleted issues, CSV imports, workflow changes) also go to the audit log.

The Development panel and smart commits

The issue sidebar has a Development block showing, for the project's repositories:

  • Pull requests whose title or source branch contains the issue key.
  • Branches whose name contains the key.
  • The ten most recent commits whose message contains the key.
  • Deployments: the environments the issue's commits are deployed to (see Environments and deployments), or "Not deployed to any environment yet".

Key matching is case-insensitive and needs a word boundary, so web-12 matches but WEB-123 does not match issue 12.

Smart commits are references: after each push (over HTTP, SSH or the web editor), a commit whose message mentions an issue key is added to that issue's activity as "referenced this issue in commit sha", once per commit and issue.

git switch -c WEB-5-fix-avatars
git commit -m "WEB-5: fix Safari avatar scaling"
git push -u origin WEB-5-fix-avatars
Smart commits do not change status from keywords in the message. To move issues when code ships, use an automation rule such as the built-in template "When a PR is merged, move linked issues to Done".
