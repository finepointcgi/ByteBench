Estimates and Workbench

ByteBench plans work with story points and estimates, but it does not record time. Hours are logged in Workbench, and ByteBench links straight to your timesheet with the right charge code.

Why ByteBench does not record time

Hours worked are a financial record. In a company that bills by the hour, or that needs DCAA-compliant timekeeping (daily entry, a single system of record, corrections made with a reason), the timesheet is where hours are charged to a charge code, certified and approved, and from where they flow into labour cost, billing and the audit trail. A second set of hours inside an issue tracker would be a second record that can disagree with the books. So ByteBench has no work log and no timer. Instead it tells people which charge code to use and sends them to the timesheet.

The timesheet system is Workbench, an ERP project at github.com/finepointcgi/Workbench. ByteBench only needs its web address; nothing is installed or synchronised.

Older ByteBench versions had a time-tracking feature (work logs). The RemoveTimeTracking migration drops the WorkLogs table, so existing work logs are deleted when you upgrade. Take a database backup and export any hours you still need first. Estimates are kept.

Story points and estimates

Three planning fields describe the size of an issue. None of them records time spent.

FieldWhat it isUsed by
Story pointsA whole number, 0 to 100, entered on the issue or in bulk through the API or CSVSprint commitment, burndown, velocity, epic progress, roadmap, throughput
Original estimateYour first duration guessPlanning and GQL
Remaining estimateWhat is still leftPlanning, list column, GQL

Durations are written like 2h 30m, 1d, 1.5h or 1w. A bare number means hours. A day is the project's hours per day (default 8, 1 to 24, set under Settings, Fields, Estimates at /p/{KEY}/settings/fields, Maintainer), and a week is 5 days. If you set only the original estimate on an issue that has no remaining estimate, the remaining estimate starts at the same value; after that each is edited independently, and changes are recorded in the issue's activity ("changed the estimate from 3 to 5 story points"). Unestimated issues count as 0 points in sprint reports.

# Estimate via the API
curl -X PATCH -H "Authorization: Bearer $BYTEBENCH_TOKEN" -H "Content-Type: application/json" \
  -d '{"storyPoints":5,"originalEstimate":"1d 4h","remainingEstimate":"1d"}' \
  https://bytebench.example.com/api/v1/projects/WEB/issues/12

Search by estimate in GQL: remainingEstimate > "2d", storyPoints >= 8, originalEstimate is EMPTY.

Project WBS and charge codes

A Maintainer opens project Settings, then Workbench (time & cost), and sets:

  • Workbench charge code (WBS), for example 1.2.3: the code people should charge their hours to for this project's work.
  • An optional Workbench project code.

Codes are at most 50 characters made of letters, digits, ., -, _ and /, starting with a letter or digit. Changes are audited as project.workbench_changed with the old and new values.

The issue button and per-issue override

With a base URL and a charge code, the issue sidebar shows Log time in Workbench and "Charge to 1.2.3 · project ...". The button opens your Workbench timesheet at {BaseUrl}/time (the current week) in a new tab, with rel="noopener noreferrer". Workbench's timesheet address takes a date but no charge code, so you pick the code shown next to the button in the timesheet grid.

An issue whose work is billed elsewhere (a warranty fix, say) can carry its own code: Developers choose Use a different charge code in the issue sidebar. It is written to the issue's activity and audited as issue.workbench_changed. The effective code is the issue's own if set, otherwise the project's. If no code is set, Maintainers see a hint linking to the setting; everyone else sees nothing.

The Workbench integration

Beyond the link, ByteBench can talk to the Workbench REST API (/api/v1) with a scoped API key. It reads projects and WBS tasks for pickers and context, can create epics and issues from the plan, and can push work state back. It never reads or writes timesheets or time entries: time is the DCAA cost record and only the employee enters their own.

Setup: address, key and scopes

  1. In Workbench, an administrator opens Admin › Integrations › API keys and creates a key for ByteBench. The key is its own service user, so give it the narrowest roles that work (see key roles).
  2. Scopes: projects:read and sheets:read are required. Add sheets:write only if you turn on pushing work state. Do not grant time or any other area; the connection test warns if the key can reach timesheets.
  3. In ByteBench a site administrator opens Administration › Workbench (/admin/workbench), enters the address (this overrides Workbench:BaseUrl; leave it blank to use the configured one) and the key, and saves. The key is stored encrypted with Data Protection, never shown again (only its last four characters), and can be replaced or removed. Removing it here does not revoke it in Workbench: revoke it there as well.
  4. Test connection probes what the key can do without changing anything: reads of projects and sheets, the financials permission (planned vs charged hours), a scope-only check of the time area, and a deliberately invalid status update against ids that do not exist to learn whether sheets:write is present. The result and every change are in the audit log as workbench.connection_changed, workbench.key_removed and workbench.connection_tested and on the admin page.

The address is guarded like other outbound integrations: http(s) only, no credentials in the URL, and no loopback, private, link-local or metadata addresses unless Workbench:AllowPrivateNetworks allows it (default: follows Webhooks:AllowPrivateNetworks, which Development turns on). Every connection re-checks the resolved address, redirects are not followed, and a call times out after Workbench:TimeoutSeconds.

Key roles

The key sees only what its service user's roles allow. For planned vs charged hours (/projects/{id}/financials/wbs) the roles must include Finance or administrator; without them the hours are simply hidden. To push work state the key's user must be an Editor of the project's plan sheet (or be assigned the task).

Pickers and validation

With a connection, the project's Workbench card (Maintainer) offers searchable lists of Workbench projects and WBS tasks, and the issue-level override offers the project's WBS tasks. Saving checks that the project code and WBS element exist (a typo is refused). Lists are cached for Workbench:CacheSeconds. Not connected, or Workbench slow, down or refusing the key: the fields are free text as before.

Read-only context

On a mapped project (above the issue list), on the project's Workbench card and on a mapped issue, ByteBench shows the WBS task's title, status, % complete, dates, planned vs charged hours and a link to the project and plan in Workbench. It loads after the page renders, is cached, and degrades silently: a slow or down Workbench, or a key whose roles cannot read financials, hides the missing part and never slows or breaks the page. Anyone who can view the project sees it.

Deep links

Workbench's timesheet page honours only ?date=yyyy-MM-dd: it takes no project or charge code, so the button cannot preselect a row. For an issue that is closed, Log time in Workbench opens the timesheet period of the day it was closed; otherwise the current period. The charge code is shown next to the button. The context panel links to /projects/{id} and /sheets/{id} (the plan).

Plan to epics and issues

A Maintainer can create ByteBench epics and issues from a Workbench plan, the way Workbench's GitLab connector maps its plan. On the project's Workbench card, pick the Workbench project, optionally a WBS subtree, how many summary levels become epics, then Preview (writes nothing) and Create epics and issues. Later runs say Sync now. A project can also opt in to a periodic reconcile (Workbench:ReconcileMinutes, default 15; 0 turns it off).

A task added in Workbench appears as a new issue. A task removed or moved out of the synced part is not deleted: its issue gets an activity note and is listed on the card, and you decide. Nothing is dropped silently: every change is in issue activity (actor Workbench sync, a system account like the other bots) and in the sync report.

Limits, batching and notifications

  • Every create and update goes through the normal issue service as the Workbench sync account, so workflow, audit, automation and webhooks behave as usual. Maintainer or higher runs it.
  • Workbench:MaxTasksPerSync (default 2000): a bigger plan is refused with a message (choose a WBS subtree) rather than cut off.
  • Issues are written one transaction each, in plan order, with progress shown on the card. The run is idempotent, so a run interrupted by a restart is taken up again by the worker (a run stuck as "running" for ten minutes is re-run).
  • Notifications: issue creation notifies as usual, but staffing is applied without per-issue "assigned to you" notifications for a bulk creation.
  • No inbound webhook. Workbench's signed webhook outbox sends no plan or task events (its event types are timesheets, invoices, bills, purchase orders, projects created, employees, opportunities, periods, shipments, RFQs, NCRs and sheet form submissions), so the periodic reconcile and Sync now are the triggers. If Workbench adds plan events, a receiver for its Workbench-Signature scheme (t=...,v1= HMAC-SHA256 of t.body, 5 minute window) can be added without changing the rest.

Pushing work state

ByteBench owns work state, as Workbench's GitLab connector treats GitLab. Off by default; a Maintainer turns it on per project on the Workbench card. The Workbench API has a suitable write endpoint (POST /api/v1/sheets/{sheet}/tasks/{item}/status with status and percentComplete), so ByteBench uses it and nothing else: no dates, hours, WBS structure or time.

  • For each WBS code on the project's issues (an issue's own code, else the project's), the % complete is done / total (weighted by story points when all have them; epics excluded). Status is set to "Done" at 100% and "In Progress" once work started, using the plan sheet's own Status options (matched case-insensitively; with no matching option only the percentage is sent). A status is never moved backwards.
  • A background sweep (Workbench:PushIntervalSeconds) and Sync now queue a job when the desired state differs from the last push. Jobs live in a database outbox with retry and backoff (1 min, 5 min, 15 min, 1 h; five attempts) for timeouts and 5xx; refusals (403, unknown task or status option) fail at once with the reason. The same desired state is never queued twice, a queued job is superseded by a newer one, and a value Workbench already has is skipped.
  • Conflict notes: if Workbench's value changed since the last push, ByteBench still writes its value (it owns work state) and the log row says what it replaced. The log (state, attempts, error, note) and a Retry button are on the card; pushes are audited as workbench.push and workbench.push_failed. A sprint completing changes no issue's status, so it needs no separate trigger: the sweep covers state changes however they happen.

Common questions

  • Can I log hours on an issue? No. Use the Workbench button; hours live only in Workbench.
  • Is anything sent to Workbench? No. The link is a plain URL opened by your browser. ByteBench never calls Workbench's API.
  • Can I get cost reports from ByteBench? No; reports of time and cost come from Workbench. ByteBench's delivery reports measure how long issues take on the calendar (lead and cycle time), not hours worked.
