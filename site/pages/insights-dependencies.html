Repository insights and the dependency bot

See who works on a repository, how active it is and what it is written in, and let a bot open pull requests that bump outdated dependencies.

Both features belong to one repository. Insights is a tab next to Source and Commits (/p/{KEY}/repos/{slug}/insights); the dependency bot is under Settings, Dependencies (/p/{KEY}/repos/{slug}/settings/dependencies).

Insights

Anyone who can view the project (Viewer or higher) can open the Insights tab. It shows:

  • Contributors: commits, additions and deletions over the range you pick (7 days, 30 days, 90 days, 1 year or all time; the default is 1 year). People are merged by e-mail address and then by name, so one person with two addresses counts once. When the e-mail matches a ByteBench user, the name links to their profile. Merge commits are not counted.
  • Commit activity: commits per week for the last 52 weeks, and a commits per day heatmap for the same period. Weeks start on Monday.
  • Code frequency: additions (up) and deletions (down) per week.
  • Languages: a size breakdown of the default branch.
  • Busiest hours and weekdays: commits by hour of the day and by weekday.
  • Pull requests: opened, merged and the median time to merge, per month for the last 12 months.

All dates and hours are in UTC (the commit's author time). The charts are drawn on the server as plain SVG and CSS: no script runs in your browser, they follow the light and dark theme and fit a phone-width screen. Every bar has a tooltip with its value.

What is counted

  • Languages are decided by file extension (for example .cs is C#, .py is Python, .razor is Razor; Dockerfile and Makefile by name). Files with an extension that is not in the built-in table are not counted. Sizes are the files' bytes on the default branch.
  • Left out of both the language sizes and the additions/deletions: dependency and build directories (node_modules, vendor, third_party, bower_components, bin, obj, dist, out, target, ...), lockfiles (package-lock.json, yarn.lock, pnpm-lock.yaml, Cargo.lock, go.sum, poetry.lock, any *.lock, ...) and generated files (*.min.js, *.min.css, *.map, *.designer.cs, *.g.cs, *.generated.*, *.pb.go, ...). Binary files add no lines.

How it is computed

The numbers come from git log --numstat on the default branch, streamed and added up as it is read, never held in memory. It reads at most Insights:MaxCommits commits (newest first) and is stopped after Insights:TimeoutSeconds; when either limit cuts the history short the page says so and counts what it read. The result is cached per repository and default-branch head commit. A push moves the head, so the next view finds the cache stale and recomputes it in the background: one computation at a time per repository, never on the page's own request. The first view of a large repository shows "computing" and refreshes itself; during a recomputation the older numbers stay visible with a note.

REST API

GET /api/v1/projects/{key}/repos/{slug}/insights?range=7d|30d|90d|1y|all returns the same data as JSON (contributors, commitActivity, heatmap, codeFrequency, languages, hours, weekdays, pullRequests, and status, commitsScanned, truncated, headSha, computedAt). It needs the same access as viewing the repository and a token with the read scope (read_api or write_api); a project you cannot see answers 404. When the cache is stale the call waits up to Insights:ApiWaitSeconds (default 20) for the computation and otherwise answers 202 with status: "computing": ask again. status: "empty" means the default branch has no commits yet. See REST API and webhooks for tokens.

The dependency bot

The ByteBench dependency bot reads a repository's dependency manifests, asks the public package registries for newer versions and opens pull requests that change only the version text in the manifest. You need the Maintainer role or higher (the ManageRepositories permission) to see or change any of it. Pull requests are opened by a system account named bytebench-dependencies ("ByteBench dependency bot"), which has no password and cannot sign in.

It never runs a package manager. No npm install, dotnet restore, pip or go command is executed. Manifests are parsed as text and edited by replacing the one version string, so formatting, comments, line endings and a byte order mark are kept exactly. The consequence is that lockfiles are not regenerated: when package-lock.json, yarn.lock, pnpm-lock.yaml, packages.lock.json, poetry.lock, Pipfile.lock or go.sum sits next to a changed manifest, the pull request says so and asks you to regenerate it on the branch before merging.

The outdated dependencies table

Check now reads the manifests on the target branch, asks the registries and shows one row per outdated dependency and manifest: the current version, the version the bot would update to, the newest stable version, the kind of bump (major, minor or patch), and a status:

  • Update available: the row has a Create update PR button. Create all update PRs (or Create the grouped PR) opens everything at once, within the open pull request limit.
  • Pull request open: the bot already has an open pull request for that package; none is opened again.
  • Closed without merging: the bot's pull request for exactly that version was declined. It is remembered and not proposed again; a newer version is.
  • Held back: newer versions exist but the strategy or the ignore list does not allow them.

Rows with an open Night Owl dependency advisory for the current version show a shield note and say whether the proposed version fixes it; see Security scanning. A registry problem (an unknown package, an unreadable answer, a timeout) becomes a warning under the table for that package and never stops the check. A registry that refuses or does not answer ends the lookups for that ecosystem for this run.

The pull request

For each package (or once for the group) the bot creates a branch bytebench/deps/<ecosystem>-<name>-<version> (grouped: bytebench/deps/group-<date>-<sha>) from the target branch with one commit that changes only the manifest files, written with Git object plumbing in the bare repository, then opens a pull request from it. The description lists package, ecosystem, manifest, old and new version and the kind of bump, a release-notes link when the registry provides one (the project's GitHub releases page, the NuGet page, a PyPI changelog URL), the Night Owl advisory note when there is one, the lockfile note, and the configured labels. If the pull request cannot be opened (an archived repository, for example) the branch is removed again. Opening one writes the audit event repository.dependency_pr_opened, attributed to the person who clicked or, for a scheduled run, to the bot; saving the settings writes repository.dependency_bot_updated.

Registries, safety and limits

  • Public registries only. Private registries and registry tokens are not supported: the bot sends no credentials, and registry addresses with credentials in them are refused.
  • Addresses are server settings, not repository settings: DependencyBot:Registries:Npm, NuGet, PyPI and Go (defaults: the public npm, NuGet, PyPI and Go proxy hosts). A mirror or caching proxy that needs no login can be configured there.
  • SSRF guard, like webhooks, mirrors and the importers: http and https only, no loopback, private, link-local, CGNAT or metadata addresses (checked again on every connection, so DNS rebinding cannot swap them) unless DependencyBot:AllowPrivateNetworks is on; when it is not set, Webhooks:AllowPrivateNetworks decides. No redirects are followed. Package names from manifests are validated and escaped as a single path segment.
  • Traffic is capped: DependencyBot:RequestsPerSecond requests per second for the whole server, DependencyBot:MaxPackagesPerRun distinct packages per check, DependencyBot:MaxResponseBytes per answer and a per-request timeout.
