Package and container registry

Every project has its own private NuGet feed, npm registry and Docker (OCI) registry, with the same sign-in and roles as the rest of GitBench and a ready-made token for CI jobs.

What you get

KindAddress (replace the host and project key)
NuGet v3 feedhttps://gitbench.example.com/packages/WEB/nuget/index.json
npm registryhttps://gitbench.example.com/packages/WEB/npm/
Container registrygitbench.example.com/web/<image>:<tag> (host and port, then the project key in lowercase, then the image name, which may contain more path segments)

The Packages page for a project is at /p/{KEY}/packages (filter by type, search by name, click a package for versions, files, install commands and delete). It shows the exact commands for your server. Each project's registry is separate: a package in WEB is not visible from OPS.

Turn it on or off

The registry is on by default for every project. A Maintainer can switch it off under Project settings → Packages & container registry (/p/{KEY}/settings#packages). Turning it off hides the packages and makes every client get "not found"; nothing is deleted.

Credentials

CredentialUse
Personal access token (gbp_...)Create one under your profile, Access tokens (/account/profile#tokens). Use it as the password (any user name works for npm and NuGet) or as the NuGet API key. To publish or delete the token needs the write_repository or write_api scope; a read-only token can only download.
CI job token (gbj_...)Every CI job gets one as GITBENCH_JOB_TOKEN (also GITBENCH_REGISTRY_PASSWORD). It is valid only while that job runs, counts as a Developer in its own project (so it can publish and pull but not delete), and can read other projects only if the person who triggered the pipeline can view them.
Registry token (gbr_...)What docker login trades your credentials for at /v2/token; valid one hour. You never create it by hand.
Browser sessionOnly for downloading files from the Packages page.
Account passwords are refused. Registry clients must use a token. There is no anonymous access, even for readable projects: every request must be authenticated.

Permissions

ActionRole
Pull, restore, install, searchViewer (ViewProject)
Publish a package, push an imageDeveloper (PublishPackages)
Delete a package, version or image tagMaintainer (DeletePackages)
Registry settings and cleanup policyMaintainer (DeletePackages)

Projects you can't see, and projects whose registry is off, answer 404, so their existence isn't revealed.

NuGet

# one-time setup
dotnet nuget add source https://gitbench.example.com/packages/WEB/nuget/index.json \
  --name gitbench-web --username you --password <personal access token> --store-password-in-clear-text

# publish
dotnet nuget push MyLib.1.2.0.nupkg \
  --source https://gitbench.example.com/packages/WEB/nuget/index.json \
  --api-key <personal access token>

# install
dotnet add package MyLib --version 1.2.0

# delete a version (Maintainer)
dotnet nuget delete MyLib 1.2.0 --source https://gitbench.example.com/packages/WEB/nuget/index.json --api-key <token> --non-interactive

Pushing an existing id and version returns 409: versions are immutable. Ids may have letters, digits, _, ., - (up to 100 characters). The feed supports restore (flat container, registration, search).

npm

# point npm (or one scope) at the project registry
npm config set registry https://gitbench.example.com/packages/WEB/npm/
npm config set -- '//gitbench.example.com/packages/WEB/npm/:_authToken' "$GITBENCH_TOKEN"
# or only for a scope
npm config set @acme:registry https://gitbench.example.com/packages/WEB/npm/

npm publish                 # Developer
npm install @acme/widgets
npm dist-tag add @acme/widgets@1.2.0 beta
npm unpublish @acme/widgets@1.0.0   # Maintainer
npm deprecate @acme/widgets@1.0.0 "Use 1.2"

Publishing an existing version fails with 403, as on the public registry. Scoped and unscoped names both work; dist-tags, whoami, ping and search are supported. Setting the whole registry means third-party packages are not proxied: use a scope-only registry if you still install from npmjs.

Docker and container images

docker login gitbench.example.com -u you -p "$GITBENCH_TOKEN"

docker tag app:latest gitbench.example.com/web/app:1.4.0
docker push gitbench.example.com/web/app:1.4.0
docker pull gitbench.example.com/web/app:1.4.0

GitBench implements the registry API (/v2/) that docker push/pull use, including chunked uploads, manifest lists, GET /v2/_catalog and tag lists. The registry is served from the same host and port as GitBench, so it needs HTTPS in practice (Docker only allows plain HTTP for localhost or hosts listed as insecure registries). Deleting a tag is done on the package page.

Using the registry from CI jobs

Besides the token, each job gets these variables when the site's base URL is known (PublicBaseUrl setting, or learned from the first request):

VariableValue
GITBENCH_REGISTRYRegistry host and port, for docker login, e.g. gitbench.example.com
GITBENCH_REGISTRY_IMAGEThe project's image prefix, e.g. gitbench.example.com/web
GITBENCH_REGISTRY_USERgitbench-ci-token (any name is accepted)
GITBENCH_JOB_TOKEN, GITBENCH_REGISTRY_PASSWORDThe job token (secret, masked in logs)
GITBENCH_NUGET_SOURCE_URLNuGet index URL
GITBENCH_NPM_REGISTRY_URLnpm registry URL

Publish a NuGet package from CI

jobs:
  pack-and-push:
    image: mcr.microsoft.com/dotnet/sdk:10.0
    only: [main]
    steps:
      - name: Pack and push
        run: |
          dotnet pack src/MyLib -c Release -p:Version=1.0.$GITBENCH_PIPELINE_ID -o out
          dotnet nuget push out/*.nupkg --source "$GITBENCH_NUGET_SOURCE_URL" --api-key "$GITBENCH_JOB_TOKEN"

Publish an npm package from CI

jobs:
  publish:
    image: node:22
    only: [main]
    steps:
      - run: |
          echo "registry=$GITBENCH_NPM_REGISTRY_URL" > .npmrc
          HOST_PATH="${GITBENCH_NPM_REGISTRY_URL#https:}"
          echo "$HOST_PATH:_authToken=$GITBENCH_JOB_TOKEN" >> .npmrc
          npm version 1.0.$GITBENCH_PIPELINE_ID --no-git-tag-version
          npm publish

Push an image from CI

CI jobs have no Docker daemon and no Docker socket, so docker build and docker push do not work inside a job. Use a daemonless builder such as Kaniko, Buildah or Skopeo (in an image that provides it) and log in with the variables above. A complete example is on the CI page; adapt it to the tool you use. The job's network (Ci:Network) must reach the registry.

Cleanup policy

By default every version is kept forever. A Maintainer can enable Cleanup policy: keep only the newest versions in the project settings and choose 1 to 1000 versions (or image tags) per package. The policy runs after every publish and deletes the older ones. npm versions that carry a dist-tag and the image tag latest are always kept.

Storage

KeyDefaultMeaning
Packages:Root{ContentRoot}/packagesWhere blobs live. Include it in backups.
Packages:MaxBlobBytes5 GBLargest single blob (a NuGet package, an npm tarball, one image layer). Bigger uploads are refused with 413.

Blobs are content-addressed (SHA-256) and stored once, shared by every package with the same bytes, such as image layers. Deleting versions removes blobs nobody else references; a daily sweep (first run an hour after startup) removes orphaned blobs and abandoned partial uploads older than a day. Two further limits to know: manifests may be at most 4 MB.

Site administrators can see usage at Admin → Package registry storage (/admin/packages): bytes on disk, bytes used per project (each distinct blob counted once per project) and the blob size limit.

Rate limits

Registry requests (/packages/* and /v2/*) are limited by the RateLimiting settings, counting requests, never bytes. A docker push makes dozens of requests per layer, so the defaults are generous. Over the limit gives HTTP 429 with Retry-After.

KeyDefaultApplies to
RateLimiting:Registry3000 per 60 sPer credential (a hash of the token; IP when anonymous)
RateLimiting:RegistryIp6000 per 60 sPer client IP across all credentials (a CI farm behind one NAT needs headroom)

Each is a PermitLimit and WindowSeconds pair; RateLimiting:Enabled=false turns all limiting off. See Administration.

Webhooks and audit

  • Webhook events package.published and package.deleted, with package: { id, name, type (nuget, npm or container), version, size, url, pipeline_id }. pipeline_id is set when a CI job published it.
  • Audit events package.published, package.deleted, package.version_deleted and package.settings_changed. Publishes from a job are attributed to whoever triggered the pipeline.

API

There is no separate REST API for managing packages: the NuGet, npm and OCI protocol endpoints above are the API. To list what is in a project from a script, use the client protocols (for example GET /packages/WEB/nuget/v3/flatcontainer/{id}/index.json, GET /packages/WEB/npm/{name} or GET /v2/_catalog).

Troubleshooting

SymptomCause
401 or "Use a personal access token"You used your account password. Use a token.
403 "needs the write_repository or write_api scope"The token is read-only. Create one with a write scope.
404 "Project not found, or its package registry is off"Wrong project key, you aren't a member, or a Maintainer turned the registry off.
409 / 403 on publishThat version already exists (NuGet 409, npm 403). Bump the version.
docker push fails with an HTTP/TLS errorThe registry shares GitBench's host; put it behind HTTPS (see Production setup).
