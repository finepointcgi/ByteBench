Administration

What site admins can see and do: manage users, read the audit log, watch the system page, tune rate limits, check package storage and backups, and understand how long data is kept.

All pages in this chapter are for site admins only (see site admins). They appear in the admin part of the sidebar. Everyone else sees "Only site administrators can ..." messages.

User administration

At /admin/users you can search by username, display name or email (25 per page). Each row shows the username and display name, email, admin flag, status (active, locked until a date, or deactivated), whether two-factor is on, the last sign-in and the number of project memberships. The last sign-in comes from the newest auth.sign_in audit event, so it is limited by audit retention.

People register themselves at /account/register (an admin can close or limit that), or sign in through SSO or LDAP, which can create accounts automatically (see Accounts). Admins can also add people with Create user, which works while registration is closed. To have a first admin, set Bootstrap:AdminUsers to a list of usernames; they are made site admins at start-up.

Registration

The Registration panel at the top of /admin/users sets Open or Closed and the allowed email domains, stored in the database (no restart; audited as admin.registration_changed). It also creates and revokes invitations: single-use links, valid 1, 7 or 30 days, optionally tied to one address, that work while registration is closed (admin.invite_created, admin.invite_revoked, auth.invite_used). With Registration:LockedByConfig the panel is read-only. Closed mode also stops SSO and LDAP creating new accounts unless Registration:ApplyToSso=false. Details and precedence: Registration control.

Audit log

ByteBench records security-relevant events as append-only audit events: time, actor (user, or none for system and anonymous), IP address, user agent, a dotted action, target type and id, project, and JSON details. Rows cannot be updated or deleted through the app, and they outlive the users and projects they mention. Only retention removes them.

Where to read it

  • /admin/audit (site admins) filters by actor username (or system), action prefix (for example member.), project key and a UTC date range. It shows 50 events per page, and Details expands the JSON and user agent.
  • /p/{KEY}/settings/audit (project Owners) shows the same view limited to that project.
  • Export CSV downloads every matching event (up to 100,000) from GET /admin/audit/export.csv?project=&actor=&action=&from=&to=, with the same access checks. Cells that start like a spreadsheet formula are prefixed with an apostrophe. Exporting is itself audited as audit.exported.

What is never recorded

Passwords, tokens (not even a prefix) and webhook secrets are never stored. Webhook and mirror URLs are logged as scheme and host only. Detail keys that look like secrets (password, secret, token, hash and the like) are dropped as a backstop. Behind a reverse proxy, set ReverseProxy:Enabled so the recorded IP is the client's.

The system page

/admin/system gives an operator what they need at a glance:

  • Server: version, runtime, operating system, uptime, memory.
  • Database: provider, target (never the password), server version, size, applied and pending migrations.
  • Health: the checks behind /health/ready.
  • Storage: files and bytes in each data folder, measured on demand and cached for a minute.
  • Queues: webhook deliveries waiting, CI pipelines queued and running, merge queue entries, pending email and chat notifications, and failures in the last 24 hours.
  • Backups: schedule, folder, number and size of archives, last success and last error.
  • Hosting checks: the production review (TLS and proxy, Data Protection keys, demo data off, backups, rate limits, allowed hosts). The same review runs at start-up and writes warnings to the log. See Production setup.

Rate limiting

Rate limits protect sign-in, the API, Git and the registries. They are on by default (off in the Development configuration). Each section takes PermitLimit and WindowSeconds (fixed window); a PermitLimit of 0 switches that limit off. Over the limit a request gets 429 with a Retry-After header (problem+json for the API, plain text elsewhere).

Package storage (/admin/packages)

A read-only table of every project's package registry usage: number of packages, versions or image tags, and size (each distinct blob counted once per project), plus total bytes on disk, the storage folder (Packages:Root) and the largest blob allowed (Packages:MaxBlobBytes). Blobs are stored once by digest, and unreferenced blobs are swept daily. Project Maintainers manage individual packages from the project's packages page; see Package and container registry.

Backups (/admin/backups)

One archive (bytebench-backup-<UTC time>.tar.gz with a .sha256 file) holds the database, repositories, attachments, packages, LFS objects, Pages and, by default, the Data Protection key ring, with a manifest and checksums for every file. The page shows the folder, schedule, retention and database mode, a Back up now button, and for each archive a download, a SHA-256 file and a delete link. Backups and deletions are audited. Restoring is a command run with the server stopped.

Workbench connection (/admin/workbench)

Site administrators set Workbench's address and a scoped API key, test what the key can read and write, replace or remove the key, and see the recent workbench.* audit events. The key is stored encrypted and never shown back. See Setup: address, key and scopes.

Explore, search and profiles

These are open to every signed-in user, and everything is filtered to projects the user can view, so nothing from a project you cannot see shows up anywhere.

  • Explore (/explore): every project you can view, with visibility, open issues, repositories, stars and last activity. Tabs All, Starred and Mine; filter by key, name or description; sort by name, recent activity or stars. Anyone who can view a project can star it; starred projects come first in the sidebar.
  • Profiles (/u/{username}): avatar, display name, member since, the visible projects they belong to, an activity feed (issues opened and closed, comments, pull requests opened and merged, pushes) and a 52-week contribution calendar.
  • Global search: the app-bar box (press /) suggests issues, pull requests, projects and users, and /search?q= groups full results. A query that is a visible issue key (for example WEB-12) jumps straight to it. Code is a separate tab that runs git grep on the default branch of each visible, non-archived repository with caps (25 repositories, 20 matches each, 100 in all). Matching is a case-insensitive text match, not a full-text index. For regular expressions and other branches use a repository's own code search.
  • API: GET /api/v1/search, /users/{username}, /user/starred and PUT/DELETE /projects/{key}/star (see the API catalogue).
