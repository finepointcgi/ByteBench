SAML single sign-on and SCIM provisioning

Let people sign in to ByteBench with your company's SAML 2.0 identity provider (Microsoft Entra ID, Okta and others), and let that provider create, update and deactivate ByteBench accounts automatically through SCIM 2.0.

Both are set up by a site admin on Admin, Authentication (/admin/authentication). SAML sits next to the OpenID Connect providers and LDAP described in Accounts, sign-in and SSO and follows the same account rules. SCIM works with any sign-in method; it only manages the accounts.

SAML single sign-on

ByteBench is the service provider (SP) and trusts one SAML identity provider (IdP). Sign-in is SP-initiated: the person clicks Sign in with <name> on the ByteBench sign-in page, ByteBench sends an authentication request to the IdP (HTTP-Redirect binding), and the IdP posts a signed response back to ByteBench (HTTP-POST binding).

ByteBench's SAML addresses

The SP entity ID (the audience the IdP must put in its assertions) is {site}/saml/metadata unless you set another one. The admin page shows all of these with your site's address filled in.

Turn it on

  1. Open /admin/authentication, section SAML 2.0 single sign-on, and copy the SP entity ID and ACS URL into your IdP (see the walkthroughs below).
  2. From the IdP, take its metadata URL and press Fetch metadata: this fills in the IdP entity ID, the single sign-on URL (HTTP-Redirect binding), the logout URL and the signing certificates. Or type them in and paste the certificate as PEM.
  3. Check the attribute names, the allowed email domains and the admin group, switch Enable SAML sign-in on and press Save SAML settings. The sign-in page shows the button at once.

The settings saved on the page override Saml:* from the configuration (see the keys). Use appsettings instead forgets the saved copy. Metadata is fetched only when you press the button; when the IdP rotates its certificate, fetch again (or paste both certificates) and save. The fetch goes through the same outbound guard as mirrors and importers: only http/https, no credentials in the URL, no redirects, no loopback, private, link-local or cloud metadata addresses unless Saml:AllowPrivateNetworks (default: Webhooks:AllowPrivateNetworks) is on, at most 1 MiB, 10 seconds.

Accounts and attributes

After the response is validated, ByteBench handles the account exactly as for an OpenID Connect provider:

  • The NameID is the stable key of the link between the IdP account and the ByteBench account (login provider saml). Use a persistent or email NameID; a transient NameID changes every time and is refused.
  • The email comes from the email attribute (default email), or the NameID when that is an email address. Attribute names match an attribute's Name or FriendlyName, ignoring case. Display name, username and groups come from their attributes (defaults displayName, username, groups).
  • SAML has no "email verified" flag, so Trust the IdP's email as verified is on by default (right for your own company IdP). With it off, accounts are neither created nor linked by email.
  • Allowed email domains, Create accounts on first sign-in, Link existing accounts by email (only when the ByteBench account's email is confirmed or it has no password), the registration policy, the site admin group values (granted when the user is in a group, revoked again only if SAML granted it, never for the last admin) and group mappings (Saml:GroupMappings) behave as described in How sign-in works.
  • Accounts created this way have no ByteBench password. ByteBench two-factor sign-in still applies to users who turned it on. A locked or deactivated account can't sign in.

Signed requests

Requests are unsigned by default (most IdPs don't need signatures on them). To sign authentication and logout requests, press Generate signing key and switch Sign authentication requests on. ByteBench creates an RSA-2048 key with a self-signed certificate, stores it encrypted with ASP.NET Core Data Protection (it is never shown or logged) and publishes the certificate in /saml/metadata. Re-import the metadata at the IdP after generating or replacing the key. Requests are signed with RSA-SHA256 as the HTTP-Redirect binding specifies.

Signing out

Signing out of ByteBench always ends the ByteBench session. When the IdP has a single logout URL and the person signed in with SAML, ByteBench then sends the browser to the IdP with a logout request (SP-initiated single logout), and the IdP's answer comes back to /saml/logout, which shows the sign-in page. Logout requests started by the IdP are not supported.

What ByteBench validates

Every rule below has a test that sends a response breaking it and checks that nobody is signed in. A refused response sends the browser to the sign-in page with a generic error, and the audit log records auth.sso_failed with provider: saml and a reason code.

  • Signatures are checked against the configured IdP certificates only (several are allowed, for rollover), never against a key inside the message. Only the Response's and the Assertion's own signatures count; each one present must be valid, at least one must be present, and with Require signed assertions (on by default) the assertion itself must be signed. SHA-256 or better is required (SHA-1 only with Saml:AllowSha1). Only the enveloped-signature and exclusive canonicalization transforms are allowed.
  • Signature wrapping: the response must contain exactly one assertion, directly inside the Response; no two elements may share an XML ID; and a signature must reference the very element it sits in. So the element whose signature was checked is the element that is read. Encrypted assertions are refused.
  • Issuer of the response (if present) and of the assertion must be the IdP entity ID. Audience must include the SP entity ID. Destination must be the ACS URL (and is required on a signed response). The bearer subject confirmation's Recipient must be the ACS URL.
  • Time: NotBefore and NotOnOrAfter of the conditions and the subject confirmation, with a clock skew of 120 seconds by default (Saml:ClockSkewSeconds, at most 600).
  • InResponseTo must name an authentication request this server sent in the last 10 minutes, from the same browser (an encrypted, short-lived cookie holds the request ID), and each request can be answered once. Unsolicited responses are refused. Because the IdP posts the response from its own site, this cookie is SameSite=None; Secure over HTTPS; over plain HTTP (local testing) it can only be SameSite=Lax, so a test IdP must then run on the same host name as ByteBench (another port is fine).
  • Replay: an assertion ID is accepted once; sending the same assertion again is refused until it expires.
  • Status must be Success; an error response never signs anyone in.
  • XML parsing refuses DTDs, so there are no entity expansions or external entities. Responses over Saml:MaxResponseKilobytes (256 KiB by default) are refused.
  • RelayState is only used when it is a path on this site; anything else (an absolute URL, //host) is ignored and the browser goes to the return URL the sign-in started with.

IdP-initiated sign-in is not supported (starting from the IdP's app portal without visiting ByteBench first). Without a request to answer, nothing ties the response to a sign-in this browser started, which allows login CSRF, and there is no request to use only once. Point the IdP's app tile at {site}/saml/login instead, which starts an SP-initiated sign-in.

Setting up Microsoft Entra ID

  1. In the Entra admin center, create an Enterprise application (a non-gallery application) and choose SAML as the single sign-on method.
  2. Under the basic SAML configuration set Identifier (Entity ID) to ByteBench's SP entity ID and Reply URL (Assertion Consumer Service URL) to {site}/saml/acs. Set Sign on URL to {site}/saml/login and Logout URL to {site}/saml/logout.
  3. Under attributes and claims, keep the default NameID (user principal name or a persistent identifier). Entra names attributes with long URIs: either set ByteBench's email attribute to http://schemas.xmlsoap.org/ws/2005/05/identity/claims/emailaddress and the display name attribute to http://schemas.microsoft.com/identity/claims/displayname, or add claims with the short names email, displayName and username. For the admin group, add a group claim; Entra sends group object IDs (GUIDs) unless configured otherwise, so put the group's object ID in Site admin group values, and set the groups attribute to http://schemas.microsoft.com/ws/2008/06/identity/claims/groups.
  4. Copy the App Federation Metadata Url into ByteBench's metadata URL and press Fetch metadata. Make sure the token signing uses SHA-256 and that the assertion is signed (Entra's "Sign SAML assertion" or "Sign SAML response and assertion" options).
  5. Assign users or groups to the application, then test with Sign in with <name> on ByteBench's sign-in page.

Setting up Okta

  1. In the Okta admin console, create an app integration with SAML 2.0.
  2. Set Single sign-on URL to {site}/saml/acs (and keep "use this for Recipient and Destination URL"), and Audience URI (SP Entity ID) to ByteBench's SP entity ID. Choose Name ID format EmailAddress or Persistent and Application username Email.
  3. Under advanced settings keep the response and the assertion signed with RSA-SHA256, and leave assertion encryption off.
  4. Add attribute statements email (user.email), displayName, username, and a group attribute statement groups with a filter for the groups ByteBench should see.
  5. Copy the app's metadata URL into ByteBench and press Fetch metadata, or paste the IdP's SSO URL, issuer and signing certificate.
  6. Assign people to the app. For the Okta dashboard tile, use {site}/saml/login as the app's initiate-login URL (IdP-initiated responses are refused).

SCIM provisioning

SCIM 2.0 (RFC 7643 and 7644) lets the IdP push its users to ByteBench: create accounts before the first sign-in, keep names and emails current, and deactivate people who leave. The server is at {site}/scim/v2. Responses use application/scim+json, and errors are SCIM error bodies with a status, a detail and, where it applies, a scimType such as invalidFilter, uniqueness, invalidSyntax or mutability.

Turn it on

  1. On /admin/authentication, section SCIM provisioning, switch Enable SCIM provisioning on.
  2. Enter a name (for example the IdP's) and press Create token. The token (bbscim_…) is shown once: copy it into the IdP's provisioning settings as the bearer token, with the SCIM base URL {site}/scim/v2.

SCIM answers 403 while the switch is off or no unrevoked token exists. Only the SHA-256 of a token is stored, and checking a token compares hashes in constant time. Rotate revokes a token and creates a replacement with the same name; Revoke stops it at once. A missing, wrong or revoked token gets 401. After 10 failed attempts from one client address within 15 minutes (Scim:MaxFailuresPerIp, Scim:FailureWindowMinutes), that address gets 429 until the old failures age out, even with a good token. Request bodies over 64 KiB (Scim:MaxBodyKilobytes) get 413.

How SCIM users map to accounts

  • A new SCIM user gets a ByteBench account with a valid username made from the SCIM userName (an email's local part, made unique), the email marked confirmed and no password: they sign in with SAML or OIDC. The SCIM userName and externalId are kept separately, so later renames at the IdP don't change ByteBench URLs.
  • Accounts SCIM hasn't touched answer a userName eq filter with their ByteBench username or their email, and a POST with the email of such an account adopts it instead of failing. This lets an IdP match existing people before creating new ones. Another account with the same SCIM userName or email is a 409 uniqueness error.
  • Site administrators are read-only to SCIM: changing, deactivating or adopting one is refused with 403 unless Scim:ManageAdmins is on. SCIM can't grant site admin; use the SAML admin group or the user admin page. ByteBench's system bot accounts are not listed.
  • Deactivating (active: false or DELETE) uses the same mechanism as the admin user page and LDAP sync: the account is locked, every browser session ends within a minute, every personal access token is revoked, and password, LDAP, OIDC and SAML sign-in, git over HTTP and SSH, packages and the API all refuse it. active: true reactivates it; revoked tokens stay revoked.

Groups

ByteBench groups are project namespaces with roles, so SCIM may change them only in a conservative way:

  • Only groups SCIM manages. SCIM can change or delete a group only when it created the group, or when the group was adopted through an explicit mapping. Every other group (made in ByteBench) is read-only to SCIM: PUT, PATCH and DELETE on it answer 403.
  • Creating. POST makes a top-level group named after displayName (cut to 100 characters) with a path derived from it (Platform Team becomes platform-team, then platform-team-2 and so on if taken), visibility Scim:GroupVisibility (Private by default) and no Owner; site administrators manage its settings in ByteBench. The path never changes afterwards, so renaming the group at the IdP keeps its URLs.
  • Adopting. A Scim:GroupMappings entry (DisplayName and the full path of an existing Group) makes a POST with that displayName (ignoring case) take over the existing group instead of creating one. Its existing members, Owners included, are kept, and its ByteBench name doesn't follow later SCIM renames.
  • Member role. Members SCIM adds get Scim:GroupMemberRole (Developer by default). It is capped at Maintainer: SCIM can never grant Owner. Adding someone who is already a member changes nothing, so SCIM can't raise anyone's role. SCIM can't remove a member whose role is above its own (an Owner added in ByteBench, for example): the request is refused with 403.
  • Protected accounts. Adding or removing a site administrator is refused with 403 unless Scim:ManageAdmins is on. Deactivated accounts and unknown user ids can't be added (400 invalidValue), and system bot accounts are neither listed nor touched.
  • All or nothing. A request with one refused change applies none of its changes.

Connecting Entra ID and Okta

  • Entra ID: in the enterprise application, open Provisioning, set the mode to automatic, the Tenant URL to {site}/scim/v2 and the Secret Token to the SCIM token, and test the connection. Map userPrincipalName or mail to userName, mail to emails[type eq "work"].value, and keep Switch([IsSoftDeleted], …) to active. To push groups, turn on group provisioning and map displayName; Entra ID sends members as Add/Remove operations on members. Map existing ByteBench groups first with Scim:GroupMappings if they should be reused.
  • Okta: in the app's Provisioning tab, enable SCIM provisioning with the SCIM connector base URL {site}/scim/v2, unique identifier field userName, the actions "Push New Users", "Push Profile Updates" and "Import" as you need, authentication mode HTTP Header with the SCIM token as the bearer token. Then enable "Create Users", "Update User Attributes" and "Deactivate Users" for the app. "Push Groups" creates ByteBench groups (or adopts mapped ones) and keeps their members in sync with PATCH operations.

Audit events

  • SAML sign-in uses the SSO events: auth.sso_sign_in, auth.sso_link, auth.sso_failed (with provider: saml and the reason, for example signature, audience, replay, unsolicited, status), auth.external_sync, and auth.saml_logout for a single logout.
  • SAML settings: admin.saml_settings_saved, admin.saml_settings_reset, admin.saml_signing_key_generated.
  • SCIM writes, with the actor SCIM: scim.user_created, scim.user_updated, scim.user_deactivated, scim.user_reactivated, scim.group_created, scim.group_updated, scim.group_deleted, scim.group_member_added, scim.group_member_removed. SCIM settings: scim.enabled, scim.disabled, scim.token_created, scim.token_rotated, scim.token_revoked (with the token's prefix, never the token).
