Dashboards and delivery reports

Build dashboards of gadgets, read sprint burndown and velocity, and measure how work flows with cycle time, cumulative flow, throughput, WIP, pull request metrics and the four DORA metrics.

Project and personal dashboards

Dashboards live at /dashboards (sidebar Dashboards). Each is a grid of gadgets that you own. Without a pinned dashboard the home page / shows the classic layout (projects, assigned issues, activity). Customize copies that layout into a new dashboard and pins it; Use as Home on any dashboard you can see pins it, and Unpin from Home goes back.

Gadgets

Choose Add gadget, then the gadget's menu, Configure, for title, width and settings.

Charts have hover titles, a legend and a data table. Gadgets refresh on relevant live events at most once a second. Widths are one third, half, two thirds or full; use Move earlier / Move later to reorder.

Sharing and limits

Only the owner edits a dashboard. Settings shares it with one project (needs Developer there) or one group (Developer in the group); everyone who can view that project or group can open it, read-only. All gadget data is loaded as the viewer, so a shared dashboard never reveals more than the viewer could already see: a project, saved filter or repository they cannot access shows a short notice instead. Limits: 50 dashboards per user, 30 gadgets per dashboard. API: GET /api/v1/dashboards and /dashboards/{id} (yours and those shared with you; others are 404).

Sprint reports (the Reports page)

/p/{KEY}/reports (sidebar Reports) shows the sprint burndown for a chosen sprint and velocity for the last 8 completed sprints, with a toggle between story points and issue count. How they are computed is explained in Boards and sprints. A Delivery reports button on this page opens the flow reports below.

Delivery reports

Delivery reports are at /p/{KEY}/reports/delivery, in tabs: Cycle and lead time, Time in status and flow, Throughput and WIP, DORA and Pull requests. Anyone who can view the project can read them (the ViewProject permission). They are computed from existing data: issues, their status-change activity, sprints, pull requests and deployments. Nothing needs configuring except the production environment for DORA.

Filters

FilterEffect
Date rangeUTC calendar days, both ends inclusive. Default: the last 90 days. Ranges longer than 1,100 days are cut to the latest 1,100.
IntervalTrend and throughput buckets: weeks (starting Monday) or calendar months.
Type, label, component, assigneeNarrow the issues ("unassigned" is available for assignee). Pull request and DORA reports ignore these four.

Cycle and lead time

  • Lead time: issue created to done.
  • Cycle time: the first time the issue entered an In Progress or In Review category status to done. Finished issues that never entered such a status count only in lead time (the report shows how many).
  • Which issues: those finished (Done category, with a closed date) inside the date range. "Done" is the last time the issue entered a Done status.
  • Shown: average, p50, p85, p95 and max, a histogram with buckets of 1, 2, 3, 5, 8, 13, 21, 34 and 55 days, a weekly or monthly trend of p50 and p85, and a drill-down table (up to 5,000 issues) with links to each issue.

Percentiles use linear interpolation between closest ranks (the spreadsheet PERCENTILE.INC rule). Read p85 as "85 percent of issues finish within this many days": a good basis for forecasts.

Time in status

For issues that existed at some point in the range, GitBench rebuilds each issue's timeline from its status-change activity and sums the time spent in each non-Done status within the range. You get the issue count, average, median, total and share of total per status. A bottleneck flag marks a working status (not Backlog, not Done) whose average is at least 1.5 times the mean of the other working statuses. A table lists the issues that spent the longest in the workflow, with the status that took longest.

Cumulative flow

For every day in the range, the number of issues in each status at the end of that day, drawn as stacked bands from Done at the bottom to Backlog at the top. Widening bands show where work piles up; parallel bands show steady flow.

Throughput and WIP

  • Throughput: per week or month, issues created, issues done and story points done, plus completed sprints in the range with committed versus completed counts and points, and the average done per period.
  • WIP (work in progress): open issues per status right now, with story points, and the total in progress or in review. It uses the current state and the type, label, component and assignee filters; the date range does not apply.

DORA metrics

The DORA tab computes the four DORA delivery metrics for the project's production environment, from deployments.

Production environment setting

On the DORA tab an Owner (the ManageProjectSettings permission) picks the Production environment from the environments that exist in the project's repositories, and the Failure window in hours (1 to 720, default 24). The environment is matched by name, case-insensitively, in every repository of the project. If unset, GitBench looks for an environment named production, then prod, and labels it "found by name". With none, the tab shows a notice instead of numbers. The change is audited as project.dora_settings_changed.

# Set it with the API (Owner)
curl -X PUT -H "Authorization: Bearer $GITBENCH_TOKEN" -H "Content-Type: application/json" \
  -d '{"productionEnvironment":"production","failureWindowHours":24}' \
  https://gitbench.example.com/api/v1/projects/WEB/reports/dora/settings

Definitions

MetricHow GitBench measures it
Deployment frequencySuccessful production deployments that finished in the range, excluding rollbacks, per day and per week
Lead time for changesFor each counted deployment, every commit it shipped (those between the environment's previous successful deployment and this one) waited from its commit date until the deployment finished. Reported as percentiles over all commits. An environment's first deployment has no baseline and is skipped; at most the 200 most recent deployments are measured, up to 100 commits each
Change failure rateShare of counted deployments followed within the failure window by a failure signal: a rollback to production, a failed production deployment, or an issue labelled hotfix created in the project. A signal is attributed to the latest successful production deployment before it
Time to restoreFor each failed deployment, from when it finished until the first successful production deployment (the rollback or the fix) that finished at or after the first failure signal. Failures with no such deployment yet count as not restored. The headline is the median
The hotfix label must literally be named hotfix (any case) to count as a failure signal. Create it in project labels and apply it to incidents you want counted.

Bands

Each metric is placed in one of four bands, using the commonly published DORA ranges:

MetricEliteHighMediumLow

Treat the bands as a conversation starter, not a score: with only a handful of deployments in the range, one failure swings the rate a lot.

CSV and API

Every tab has CSV download buttons. In a browser session the downloads are GET /p/{key}/reports/{report}.csv with the same filter query string. Report names: cycle-time, time-in-status, cumulative-flow, throughput, wip, dora, pull-requests, and the alternative tables time-in-status-issues, throughput-sprints and dora-summary. Files are UTF-8 with a byte-order mark.

The API serves JSON, or CSV with format=csv:

curl -H "Authorization: Bearer $GITBENCH_TOKEN" \
  "https://gitbench.example.com/api/v1/projects/WEB/reports/cycle-time?from=2026-09-01&to=2026-11-30&type=Bug&interval=month"

# CSV of the sprints table of the throughput report
curl -H "Authorization: Bearer $GITBENCH_TOKEN" -o throughput.csv \
  "https://gitbench.example.com/api/v1/projects/WEB/reports/throughput?format=csv&view=sprints"
Query parameterValues
typean issue type, for example Bug
label, componentid or name
assigneeusername, id or none
from, toyyyy-MM-dd (UTC, inclusive)
intervalweek or month
formatcsv for a CSV download
viewissues (time-in-status), sprints (throughput) or summary (dora)

The endpoints are /api/v1/projects/{key}/reports/{name} for cycle-time, time-in-status, cumulative-flow, throughput, wip, dora and pull-requests, plus GET and PUT /reports/dora/settings. A bad filter value is a 400. See REST API and webhooks for tokens.

Caveats

  • Time-based reports rebuild history from status-change activity lines. Issues whose status was changed by code that bypasses the normal issue service (or imported with a status) may show their current status for their whole life.
  • Reports are computed on demand, with no stored snapshots, so they change if you edit the workflow's categories.
  • DORA needs real deployments recorded by CI. See CI pipelines and Environments and deployments.
