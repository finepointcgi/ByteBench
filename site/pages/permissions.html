Roles, groups and permissions

Every project has members with one of four roles, groups pass roles down to the projects inside them, and a single piece of code decides every access question, so the website, the API and Git always agree.

The four roles

Roles are ordered, and each one has everything the roles before it have:

Viewer < Developer < Maintainer < Owner.

  • Viewer reads everything in the project but changes nothing.
  • Developer does day-to-day work: issues, comments, pushing code, pull requests and reviews, publishing packages, toggling feature flags.
  • Maintainer manages the work and the code: labels, milestones, sprints, merging, repositories, deleting packages, creating flags.
  • Owner manages people and the project itself: members, settings, deleting the project.

The creator of a project becomes its Owner. A project's last Owner cannot be removed or demoted.

Site admins

A site admin is treated as Owner of every project and group, sees everything, and can open the administration pages. The first admin is usually created with the Bootstrap:AdminUsers setting (see production setup). Admins can be granted or revoked on /admin/users, and ByteBench refuses to revoke the last admin. SSO and LDAP can grant admin from a group claim (see SSO sign-in).

Visibility

ByteBench has two visibility levels for projects and groups. There is no public (anonymous) visibility: every page and API call needs a signed-in user.

VisibilityWho can see it
PrivateOnly members (directly, or through a group), and site admins
InternalEvery signed-in user. People who are not members get the Viewer role

The Owner changes a project's visibility under Settings (audited as project.visibility_changed). If you cannot view a project, its pages and its API paths answer "not found", so its existence is not revealed.

Managing members

Owners manage members at /p/{KEY}/members: add a person by username or email, change roles, and remove members. Members inherited from a group are listed read-only with their source ("via acme"). Changes are audited as member.added, member.role_changed and member.removed.

Groups and subgroups

A group is a namespace that owns projects and other groups, like a GitLab group. Groups nest up to 4 levels deep. A group's URL is /g/{full path} (for example /g/acme/platform) and its sections are tabs: Overview, Issues, Roadmap, Pull requests, Labels and milestones, Members, and, for Owners, Automation, Integrations and Settings.

  • Project keys stay globally unique, so /p/{KEY}, Git URLs, webhooks, CI and the API still find a project by key whatever group it is in.
  • A project optionally belongs to one group. Create one from the group page or the group picker on New project. Move it under Settings, Group (needs Owner of the project and Maintainer in the target group).
  • A subgroup cannot be more visible than its parent. A group's visibility never opens a Private project: an Internal group with a Private project still hides the project from non-members.
  • Group labels and milestones are defined once on the group and appear (read-only, marked "Group") in every project below it.
  • Group-level Slack and Teams integrations and automation rules apply to all projects below.
  • Old group paths keep working as redirects after a rename or move.

Role inheritance

A member of a group has at least that role in every subgroup and project below it. A user's effective project role is the highest of:

  1. their direct project role,
  2. their roles in the project's group and all its ancestor groups,
  3. Viewer, if the project is Internal,
  4. Owner, if they are a site admin.

If none of these apply, the project is invisible to them. Inheritance only raises: a direct Viewer role never lowers a group Developer role.

The creator of a group becomes its Owner. A top-level group must keep a direct Owner, and subgroups inherit their parents' Owners. Deleting a group with subgroups or projects requires typing its full path and deletes everything in it. Group changes are audited as group.created, group.settings_changed, group.path_changed, group.moved, group.deleted, group.member_* and project.transferred.

Forks, service desk, bots and CI tokens

Who or whatHow it is treated
ForksAnyone who can view a repository can fork it into a project where they have ManageRepositories (Maintainer or higher). A cross-fork pull request needs CreatePullRequest in the fork's project but only ViewProject in the target. The author can comment on, edit, decline and reopen it with view access alone. Reviewing and merging need the normal roles in the target. A fork pull request's pipeline gets no CI variables and waits for a Maintainer or higher to press Approve and run
Service desk requestersPeople who file requests by email or form have no account and no role. A system account named "Service Desk" creates the issues and posts their replies, and requesters see only a tracking page with the public conversation (never internal comments or activity). Configuring the service desk needs Maintainer
CI job tokensEvery job receives a short-lived token (gbj_... prefix) valid only while the job runs. It carries Developer rights in the job's own project, so scripts can publish to and read from that project's package and container registry. It cannot reach other projects
AI review bot, automation botSystem accounts without passwords that cannot sign in. They have no project role; the system vouches for them only for the single action they perform, such as posting review comments
Personal access tokensAct as their owner, limited by scope. They can never exceed the owner's roles. Locked or deactivated users' tokens are refused
Feature flag SDK keysEvaluate flags for one environment; they do not carry a user role

How it is enforced

  • Every service checks access at the start of each write, and reads return only projects you can view. The UI hides what you cannot do, but the server enforces it either way.
  • In the REST API, a project you cannot see answers 404 and a visible project where you lack the permission answers 403. Every area, including pipelines, packages, Pages and AI review, uses the same permission checks as its UI page, because the endpoints call the same services.
  • Notification and mention lookups are restricted to people who can view the project.
  • Locked and deactivated users lose access within about a minute.
